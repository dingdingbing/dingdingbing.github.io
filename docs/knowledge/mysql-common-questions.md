# MySQL常见问题

这篇文章不是一份标准八股清单，而是一次面试题复盘。每个问题都保留“我的原始回答”，再补上“纠错与校准”，方便我看到自己哪些地方理解对了，哪些地方还容易混。

## 一、MySQL 整体理解

### MySQL 是什么？

**我的回答**

MySQL 使用范围很广而且免费。刚开始我会把 MySQL 和存储引擎混在一起，以为 MySQL 是一个存储引擎，但其实 InnoDB 才是存储引擎，用来存储数据并提供高效查询、修改、插入、删除等操作。

**纠错与校准**

MySQL 不是存储引擎，而是一个关系型数据库管理系统。它包含 Server 层和存储引擎层。

- Server 层负责连接、权限校验、SQL 解析、预处理、优化、执行等。
- 存储引擎层负责真正的数据组织和读写。
- InnoDB 是 MySQL 默认且最常用的存储引擎。

**面试稳答**

MySQL 是一个关系型数据库管理系统。Server 层负责连接管理、权限校验、SQL 解析、优化和执行调度；存储引擎层负责真正的数据访问。InnoDB 是默认存储引擎，提供 B+ 树索引、事务、行锁、MVCC、redo log、undo log 等能力。

### 一条 SQL 的执行流程

**我的回答**

一条 SQL 由客户端发起，然后 MySQL Server 进行连接、权限验证、解析、预处理、优化、执行，最后返回结果。

**纠错与校准**

这个主线是对的，可以再补充“执行器调用存储引擎接口”这一步。权限校验也不只发生在连接时，执行 SQL 时还会检查表、列等权限。

**面试稳答**

一条 SQL 会先经过连接器建立连接并完成认证，然后经过权限校验、解析器、预处理器、优化器和执行器。执行器根据执行计划调用存储引擎接口，InnoDB 通过索引、Buffer Pool、锁和事务日志访问数据，最后将结果返回给客户端。

## 二、索引与查询优化

### 为什么 InnoDB 使用 B+ 树？

**我的回答**

B+ 树适合范围查询，同时也很高效，层高相对较低，磁盘 IO 次数稳定，综合查询效率比较稳定。

**纠错与校准**

这个方向对。更关键的是：B+ 树适合磁盘页模型。非叶子节点只存 key 和页指针，一个 16KB 页可以放更多 key，树的分叉多、层高低，访问磁盘页的次数更少。

B+ 树快不是因为“树天然都快”，而是因为它减少了磁盘 IO。

**面试稳答**

InnoDB 使用 B+ 树，是因为 B+ 树的非叶子节点只保存索引 key 和页指针，单页能容纳更多 key，树高更低，能减少磁盘 IO；叶子节点之间有序链表连接，范围查询可以先定位起点，再顺序扫描叶子节点，所以非常适合数据库查询场景。

### B 树、B+ 树、Hash 索引区别

**我的回答**

B 树的非叶子节点会存储数据或数据指针。B+ 树的非叶子节点仅保存索引字段和子页指针，叶子节点存储数据，并且叶子节点通过链表连接，适合范围查询。Hash 索引应该是对索引字段进行 hash 后存储，可以保证 O(1) 查询，适合精确查询，不适合范围查询。

**纠错与校准**

这段基本正确。B 树非叶子节点存的是“真实数据或数据指针”，不一定是完整行。重点是：B 树命中非叶子节点可以直接返回；B+ 树非叶子节点只做导航，所有查询最终都到叶子节点。

Hash 索引由于 hash 后无序，所以不适合范围查询、排序、最左前缀匹配，也不适合 `like 'abc%'` 这种前缀范围查询。

### 聚簇索引、二级索引、回表、覆盖索引

**我的回答**

聚簇索引就是主键索引，叶子节点存储完整行数据，通过聚簇索引查询无需回表。二级索引叶子节点只保存索引字段和主键 id，如果需要其他字段，需要根据主键 id 回表查询。覆盖索引就是查询字段都在索引列中。

**纠错与校准**

整体正确。更准确地说，InnoDB 表数据本身就是按主键聚簇索引组织的，所以一张表只能有一个聚簇索引。二级索引叶子节点保存“索引字段 + 主键值”。回表不是查“主表”，而是根据主键值再去聚簇索引中查完整行。

覆盖索引在 `EXPLAIN Extra` 中通常体现为 `Using index`。

容易混的点：

- `Using index`：覆盖索引，不需要回表。
- `Using index condition`：索引下推，先在索引层过滤，减少回表。

### 索引下推是什么？

**我的回答**

索引下推是指联合索引遇到范围查询时，范围查询后的字段无法直接命中数据，使用索引下推可以在范围查询之后的数据进行字段匹配。

**纠错与校准**

这个说法有点窄。索引下推不是专门为范围查询设计的，它的核心是：把可以用索引字段判断的条件下推给存储引擎，在回表前先过滤一部分记录，减少回表次数。

例如有联合索引 `(name, age)`：

```sql
select * from user
where name like '张%' and age = 18;
```

没有索引下推时，可能先找到所有 `name like '张%'` 的索引记录，再一条条回表，然后由 Server 层判断 `age = 18`。

有索引下推时，存储引擎扫描索引时就可以先判断 `age = 18`，符合条件的才回表。

### 联合索引和最左前缀

**我的回答**

最左前缀原则是因为 B+ 树存储数据时就是按索引列从左往右排序的。不满足最左前缀原则就无法利用索引。联合索引 `(a,b,c)` 可以用 `(a)`、`(a,b)`、`(a,b,c)`，`(a,c)` 中间断了，后面的字段用不上。

**纠错与校准**

主线正确，但要更细：

```sql
where a = 1                    -- 可以用 a
where a = 1 and b = 2           -- 可以用 a,b
where a = 1 and b = 2 and c = 3 -- 可以用 a,b,c
where a = 1 and c = 3           -- a 可用于定位，c 可能用于索引下推过滤
where b = 2                     -- 通常不能有效使用该联合索引
```

联合索引 `(a,b,c)` 的有序性是：

```text
先按 a 排序
a 相同再按 b 排序
b 相同再按 c 排序
```

如果跳过 `a`，`b` 和 `c` 在全局上并不是有序的，所以无法高效定位。

### 范围查询后面的字段还能用索引吗？

**我的回答**

可以用，索引下推。

**纠错与校准**

这个回答太绝对。以索引 `(a,b,c)` 为例：

```sql
where a = 1 and b > 10 and c = 3
```

通常：

- `a` 可以用于等值定位。
- `b` 可以用于范围扫描。
- `c` 通常不能继续用于缩小索引扫描范围。
- `c` 可能通过索引下推参与过滤。

所以更准确的表达是：

> 范围字段后面的索引列通常不能继续用于索引定位，但如果字段在索引中，可能通过索引下推过滤；如果查询字段都在索引中，也可能形成覆盖索引。

### 常见索引失效场景

**我的回答**

索引失效包括聚合运算、类型转换、不满足最左前缀、`like %x` 左模糊等。

**纠错与校准**

“聚合运算”不够准确，应改成“对索引列使用函数或表达式”。常见场景：

- 不满足最左前缀。
- 对索引列使用函数或表达式。
- 隐式类型转换。
- `like '%abc'` 左模糊。
- `or` 两边不是都有合适索引。
- `!=`、`not in`、`not like` 可能导致不走索引。
- 范围查询后联合索引后续列利用受限。
- 优化器认为全表扫描更划算。

### 为什么 `like '%abc'` 通常不走索引？

**我的回答**

因为数据结构存储的时候是从左边开始判断的。

**纠错与校准**

这个直觉对，但表达要专业一点：

> B+ 树索引是按照字符串从左到右排序的。`like 'abc%'` 有明确前缀，可以定位到以 `abc` 开头的范围；`like '%abc'` 前缀不确定，无法确定扫描起点，只能全量扫描判断后缀。

### 为什么不建议 UUID 做主键？

**我的回答**

UUID 无法做范围查询，而且没有规则，只能当字符串处理。

**纠错与校准**

核心不是范围查询，而是 UUID 无序且较长。InnoDB 数据按主键聚簇索引组织，UUID 会造成随机插入，容易导致页分裂、页移动和碎片增加。二级索引叶子节点也保存主键值，UUID 过长会让所有二级索引变大。

**面试稳答**

UUID 不适合作为 InnoDB 主键，主要因为它无序且占用空间大。无序会导致聚簇索引随机插入，增加页分裂和随机 IO；主键值过长还会放大所有二级索引的体积。相比之下，自增主键更短、更有序，对 B+ 树更友好。

### 深分页为什么慢？

**我的回答**

深分页慢是因为存在大量回表操作。它需要找到第 100 万条数据之后再拿之后的 10 条，前 100 万数据可能都需要回表判断。可以先查询 id，再通过 id 查询主表。

**纠错与校准**

方向对，但原因不止回表。深分页慢的核心是 offset 越大，需要扫描并丢弃的数据越多。

```sql
select * from user order by id limit 1000000, 10;
```

这条 SQL 需要先扫描前 1000000 条，再返回后面 10 条。如果走二级索引并 `select *`，还可能产生大量回表。

常见优化：

```sql
-- 游标分页
select * from user
where id > 1000000
order by id
limit 10;
```

```sql
-- 延迟关联
select u.*
from user u
join (
  select id from user order by id limit 1000000, 10
) t on u.id = t.id;
```

### `count(*)`、`count(1)`、`count(字段)` 区别

**我的回答**

`count(*)` 好像性能差一点，具体说不上来。

**纠错与校准**

InnoDB 中通常推荐 `count(*)`。它和 `count(1)` 语义上都是统计行数，优化器会做优化。`count(字段)` 统计的是字段不为 `NULL` 的行数，语义不同，还需要判断字段是否为 `NULL`。

```text
count(*)      统计行数，包括 NULL
count(1)      统计行数
count(column) 统计 column 不为 NULL 的行数
```

MyISAM 可以保存表行数，所以无条件 `count(*)` 很快；InnoDB 因为 MVCC，不同事务看到的行数可能不同，通常需要扫描统计。

## 三、事务、MVCC、锁

### ACID 分别是什么？

**我的回答**

A 是原子性，C 是一致性，I 是隔离性，D 是持久性。

**纠错与校准**

正确。可以补实现机制：

- 原子性主要依赖 undo log 支持回滚。
- 持久性主要依赖 redo log。
- 隔离性依赖锁和 MVCC。
- 一致性是目标，由原子性、隔离性、持久性、约束和业务逻辑共同保证。

### 四种隔离级别分别解决什么问题？

**我的回答**

读未提交没有解决什么问题；读已提交解决脏读；可重复读解决脏读和不可重复读；串行化解决幻读。

**纠错与校准**

标准隔离级别可以这样记：

| 隔离级别 | 可能问题 |
| --- | --- |
| 读未提交 | 脏读、不可重复读、幻读 |
| 读已提交 | 不可重复读、幻读 |
| 可重复读 | 幻读 |
| 串行化 | 基本避免并发读写异常 |

MySQL InnoDB 的 RR 比标准 RR 更强一些：

- 普通快照读通过 MVCC 解决幻读表现。
- 当前读通过 next-key lock 解决幻读。

所以面试中要区分“标准隔离级别”和“MySQL InnoDB 实现”。

### 脏读、不可重复读、幻读

**我的回答**

脏读是事务过程中能够读取到其他事务未提交的数据。不可重复读是同一个查询语句读取到的数据不一致。幻读是事务过程中读取到的数据行发生了变化。

**纠错与校准**

脏读对。不可重复读和幻读建议这样区分：

- 不可重复读：同一事务中，多次读取同一行，内容变了。
- 幻读：同一事务中，多次按同一条件查询，结果集行数变了。

简单记：

```text
不可重复读：同一行内容变了
幻读：符合条件的行变多或变少了
```

### 为什么 MySQL 默认可重复读？

**我的回答**

可能是因为这个隔离级别比较靠谱。

**纠错与校准**

更专业的回答：

> RR 能避免脏读和不可重复读，InnoDB 还通过 MVCC 和 next-key lock 较好处理幻读；相比串行化，它又能保留较好的并发性能，是一致性和性能之间的折中。历史上 MySQL 使用 statement binlog 时，RR 也更容易保证主从执行结果一致。

### 当前读和快照读

**我的回答**

当前读是加锁之后读到的数据。快照读是利用 MVCC 机制读取快照版本，通过 Read View 判断找到可读版本。

**纠错与校准**

正确。补充分类：

```text
普通 select：快照读
select ... for update：当前读，加排他锁
select ... lock in share mode / for share：当前读，加共享锁
update/delete/insert：当前读，加锁
```

`update` 读的是最新可见版本，不是普通 MVCC 历史快照。它会加锁，等待其他事务释放锁后，再基于最新数据继续修改。

### Read View 机制

**我的回答**

Read View 有四个字段：活跃事务 id 的最小值、当前系统分配的最大事务 id、当前事务 id、活跃事务 id 集合。通过行里的事务 id 和这些值比较，判断当前版本是否可见。

**纠错与校准**

字段理解基本正确，标准命名如下：

- `m_ids`：创建 Read View 时活跃事务 id 集合。
- `min_trx_id`：活跃事务中最小的 id。
- `max_trx_id`：下一个待分配的事务 id。
- `creator_trx_id`：创建该 Read View 的事务 id。

行记录中常见隐藏字段：

- `DB_TRX_ID`：最近一次修改该行的事务 id。
- `DB_ROLL_PTR`：回滚指针，指向 undo log 旧版本。
- `DB_ROW_ID`：没有主键时生成的隐藏 row id。

判断规则：

```text
row_trx_id < min_trx_id：可见，说明早已提交
row_trx_id >= max_trx_id：不可见，说明是 Read View 之后才出现的事务
row_trx_id 在 m_ids 中：不可见，说明创建 Read View 时还未提交
row_trx_id 不在 m_ids 中：可见，说明创建 Read View 前已经提交
```

RC 和 RR 的区别：

```text
RC：每次普通 select 都创建新的 Read View
RR：同一事务第一次普通 select 创建 Read View，后续普通 select 复用
```

### 为什么有 MVCC 还需要锁？

**我的回答**

MVCC 只能解决读写冲突，不能解决并发写冲突。

**纠错与校准**

这个回答对，但可以补全：

- MVCC 解决普通读和写之间的冲突，让读不阻塞写、写不阻塞普通读。
- MVCC 不能解决写写冲突。
- MVCC 不能保护当前读之后的数据不被别人修改。
- MVCC 不能阻止范围当前读中的新插入。

**面试稳答**

MVCC 解决的是可见性问题，锁解决的是互斥和范围保护问题。普通 `select` 可以通过 MVCC 读取历史版本，但 `update`、`delete`、`select for update` 这类当前读必须读取最新可见版本并加锁，否则无法保证并发修改的正确性。

### 行锁、间隙锁、临键锁

**我的回答**

行锁是对某一行数据加锁。间隙锁通常发生在范围查询，对范围内的行添加间隙锁，保证数据不会被其他线程篡改。临键锁不清楚。

**纠错与校准**

间隙锁不是防止已有行被改，而是防止往间隙里插入新记录。

- Record Lock：记录锁，锁住已有索引记录。
- Gap Lock：间隙锁，锁住两个索引记录之间的间隙，防止插入。
- Next-Key Lock：临键锁，记录锁 + 间隙锁。

可以把 next-key lock 理解为左开右闭区间：

```text
(前一个索引值, 当前索引值]
```

它既锁当前记录，也锁前面的间隙，用于 RR 隔离级别下当前读防幻读。

### 没有索引时行锁会退化成表锁吗？

**我的回答**

会吧。

**纠错与校准**

严格说不是退化成真正的表锁。

> InnoDB 的行锁是加在索引记录上的。如果查询条件没有走索引，InnoDB 只能扫描大量记录并对扫描到的索引记录加锁，锁范围会非常大，效果上接近锁表，但不是退化成真正的表锁。

### 死锁如何排查和避免？

**我的回答**

死锁是多个线程之间互相持有对方需要的资源，导致互相等待。MySQL 有死锁检测线程，但具体实现不清楚。如何排查和避免不清楚。

**纠错与校准**

InnoDB 会维护锁等待关系。当等待图中出现环，就说明发生死锁。InnoDB 会选择一个回滚代价较小的事务作为牺牲者回滚，让另一个事务继续执行。

排查：

```sql
show engine innodb status;
```

重点看最近一次死锁信息、事务持有什么锁、等待什么锁、涉及哪些 SQL 和索引。

避免：

- 事务尽量短。
- 按固定顺序访问资源。
- 让 SQL 命中合适索引，减少锁范围。
- 避免大事务和大范围更新。
- 捕获死锁异常并重试。

### 扣库存如何防止超卖？

**我的回答**

可以给字段加约束防止库存为负数，比如 unsigned；每次扣库存之前先判断有库存再扣。

**纠错与校准**

约束可以作为兜底，但核心方案应该是把判断和扣减放到同一条原子 SQL 中：

```sql
update product
set stock = stock - 1
where id = 1 and stock > 0;
```

然后判断影响行数：

```text
affected rows = 1：扣减成功
affected rows = 0：库存不足
```

这条 `update` 是当前读，会加排他锁。并发更新同一行时会串行化，不会出现先查有库存、真正扣减时已经被别人扣完的问题。

## 四、日志与恢复

### redo log、undo log、binlog

**我的回答**

redo log 是事务提交后的记录日志，防止事务提交后未刷盘导致事务丢失。undo log 是撤销日志，用于事务回滚，也用于 MVCC。binlog 是记录数据修改的日志，区别不清楚。

**纠错与校准**

redo log 不要说成“事务提交后的日志”。更准确：

- redo log：InnoDB 层物理重做日志，记录数据页的物理修改，用于崩溃恢复，保证已提交事务不丢。
- undo log：记录修改前的旧版本，用于事务回滚和 MVCC。
- binlog：Server 层逻辑日志，记录数据变更，用于主从复制、审计和基于时间点恢复。

redo log 和 binlog 的区别：

| 对比项 | redo log | binlog |
| --- | --- | --- |
| 所属层级 | InnoDB 层 | Server 层 |
| 日志类型 | 物理日志 | 逻辑日志 |
| 主要用途 | 崩溃恢复 | 主从复制、数据恢复 |
| 写入方式 | 循环写 | 追加写 |
| 关注点 | 数据页如何变化 | 执行了什么数据变更 |

### redo log 是物理日志还是逻辑日志？

**我的回答**

redo log 是逻辑日志吧。物理日志记录哪些数据发生了修改，逻辑日志记录从什么状态变为什么状态。

**纠错与校准**

redo log 是物理日志。它更关注某个表空间、某个 page、某个位置发生了什么物理修改。binlog 更偏逻辑日志，记录 SQL 或行级逻辑变更。

简单记：

```text
物理日志：数据页怎么变
逻辑日志：数据行或 SQL 语义怎么变
```

### binlog 三种格式

**我的回答**

不清楚。

**纠错与校准**

binlog 常见三种格式：

- `STATEMENT`：记录 SQL 原文，日志小，但遇到随机函数、时间函数等可能导致主从不一致。
- `ROW`：记录每一行的变更前后数据，日志大，但一致性最好。
- `MIXED`：MySQL 自动在 statement 和 row 之间选择。

现在更常见也更安全的是 `ROW`。

### WAL 是什么？

**我的回答**

WAL 指 write-and-？

**纠错与校准**

WAL 是 Write-Ahead Logging，意思是“先写日志，再写数据页”。

InnoDB 修改数据时，不需要每次提交都立刻把脏页刷盘。只要先把 redo log 持久化，脏页可以后续再刷。这样既能提高性能，也能在宕机后通过 redo log 恢复已提交事务。

### 为什么需要两阶段提交？

**我的回答**

不太清楚。

**纠错与校准**

一次事务提交涉及两个日志：

- redo log：InnoDB 用于崩溃恢复。
- binlog：Server 用于复制和恢复。

如果两个日志不一致，就会出问题：

```text
redo 有，binlog 没有：主库恢复后有数据，从库收不到
binlog 有，redo 没有：从库可能有数据，主库恢复后没有
```

两阶段提交流程：

```text
1. redo log 写入 prepare 状态
2. 写 binlog
3. redo log 写入 commit 状态
```

如果宕机发生在中间：

```text
redo 没 prepare：回滚
redo prepare 了，但 binlog 不完整：回滚
redo prepare 了，binlog 完整：提交
redo commit 了：提交
```

**面试稳答**

两阶段提交是为了保证 InnoDB redo log 和 Server 层 binlog 的一致性，避免主库崩溃恢复结果和从库复制结果不一致。

### 刷盘参数

**我的回答**

`sync_binlog` 看起来像同步 binlog 的设置，可能和主从延迟有关。

**纠错与校准**

`innodb_flush_log_at_trx_commit` 控制 redo log 提交时如何刷盘：

```text
0：每秒写入并刷盘，性能高，宕机可能丢 1 秒事务
1：每次事务提交都写入并刷盘，最安全，性能最低
2：每次提交写入操作系统缓存，每秒刷盘，宕机可能丢数据
```

`sync_binlog` 控制 binlog 刷盘：

```text
sync_binlog = 1：每次事务提交都刷 binlog，最安全
sync_binlog = 0：由操作系统决定何时刷盘，性能好但可能丢 binlog
sync_binlog = N：每 N 次提交刷一次
```

它主要影响 binlog 持久性、崩溃恢复和复制可靠性，不是直接控制主从延迟。

## 五、主从复制与高可用

### 主从复制原理

**我的回答**

主从复制原理是 binlog。主库有从库的节点信息，发生 binlog 日志后推送到从库，从库处理完成回复主库，超时没有回复会再次发送。

**纠错与校准**

主从复制确实基于 binlog，但不是主库主动推送为主，而是从库主动连接主库拉取。

流程：

```text
1. 主库提交事务并写 binlog
2. 从库 IO 线程连接主库，请求指定位置之后的 binlog
3. 主库 dump thread 发送 binlog
4. 从库 IO 线程写入 relay log
5. 从库 SQL 线程读取 relay log 并重放
```

### relay log 是什么？

**我的回答**

不清楚。

**纠错与校准**

relay log 是从库本地的中继日志。从库 IO 线程从主库拉到 binlog 后，先写到本地 relay log，再由 SQL 线程读取 relay log 并重放。

```text
binlog：主库的变更日志
relay log：从库本地保存的待执行日志
```

### 主从复制是同步还是异步？

**我的回答**

异步的吧。

**纠错与校准**

MySQL 默认主从复制是异步复制。主库提交成功后不等待从库执行完成，所以会有主从延迟，也可能短暂不一致。

还有半同步复制：

> 主库提交时，至少等一个从库确认已经收到日志后再返回成功。

但半同步通常只保证从库收到日志，不代表从库已经执行完成。

### 主从延迟原因和解决

**我的回答**

可能是网络延迟、节点坏了。如何解决不清楚。

**纠错与校准**

常见原因：

- 主库写入压力大，binlog 产生太快。
- 从库机器性能差，重放慢。
- 大事务导致从库长时间重放。
- 从库 SQL 线程执行慢。
- 网络延迟。
- 从库有复杂查询抢资源。
- 锁等待。

解决思路：

- 优化 SQL，减少大事务。
- 提升从库配置。
- 开启并行复制。
- 避免从库跑重查询。
- 强一致场景读主库。
- 做主从延迟检测，延迟高时切回主库。

### 读写分离如何保证读到最新数据？

**我的回答**

不清楚。

**纠错与校准**

读写分离不能天然保证强一致。写请求走主库，读请求走从库时，如果从库延迟，写后立刻读可能读不到刚写的数据。

常见方案：

- 写后读主库。
- 核心业务读主库。
- 一段时间内按用户维度读主库。
- 检测主从延迟，延迟过高读主库。
- 从库承接实时性要求不高的查询。

## 六、SQL 实战排查

### 一条 SQL 突然变慢怎么排查？

**我的回答**

先查看这条 SQL 的执行计划是否按照预想执行，主要看索引是否选择正确。

**纠错与校准**

这个是第一步，但完整排查应该包括：

- 看 `EXPLAIN`，确认索引、扫描行数、`Extra`。
- 看数据量是否增长。
- 看统计信息是否失准。
- 看是否有锁等待。
- 看是否有大事务。
- 看 CPU、IO、Buffer Pool 命中率。
- 看是否有其他 SQL 抢资源。

**面试稳答**

我会先用 `EXPLAIN` 看执行计划，确认是否走了预期索引、扫描行数是否异常、是否出现 `Using filesort` 或 `Using temporary`。如果执行计划没问题，再排查锁等待、大事务、数据量变化、统计信息变化、Buffer Pool 命中率、磁盘 IO 和并发压力。

### 慢查询日志怎么用？

**我的回答**

开启方式不清楚，分析只会 `EXPLAIN`。

**纠错与校准**

常见配置：

```sql
set global slow_query_log = on;
set global long_query_time = 1;
```

常见参数：

```text
slow_query_log
slow_query_log_file
long_query_time
log_queries_not_using_indexes
```

分析工具：

```text
mysqldumpslow
pt-query-digest
EXPLAIN
```

### CPU 高、IO 高怎么排查？

**我的回答**

CPU 高看正在跑的 SQL 线程。IO 高看是否有全表更新，还是看 SQL 线程。

**纠错与校准**

CPU 高可以先看：

```sql
show processlist;
show engine innodb status;
```

重点排查：

- 大量慢 SQL。
- 全表扫描。
- 排序、分组过重。
- 连接数过多。
- 锁竞争。

IO 高常见原因：

- 全表扫描。
- 大量回表。
- 大事务刷脏页。
- Buffer Pool 太小导致频繁读磁盘。
- 排序临时文件落盘。
- 批量 update/delete/insert。

### 连接数、连接池和 QPS

**我的回答**

连接数默认是 200，可以调大。曾经被问到“1 条 SQL 查询 1000 条数据”和“1000 条 SQL 每次查询 1 条”的区别，面试官说连接数，但我后面查资料感觉连接数过大也没啥问题。

**纠错与校准**

连接数不是越大越好。连接越多，线程、内存、上下文切换、锁竞争都会增加。

“1 条 SQL 查 1000 条”和“1000 条 SQL 每次查 1 条”的差别：

- 1000 条 SQL 有更多网络往返。
- 有更多解析、优化、执行开销。
- 占用连接时间更长。
- 更容易打满连接池。
- 更容易带来事务和锁竞争。

数据库连接数不是 QPS。一个连接可以被连接池复用。如果单条 SQL 只耗时 5ms，一个连接理论上一秒可以处理约 200 次请求；100 个活跃连接就能支撑较高吞吐。真正瓶颈取决于 SQL 耗时、锁竞争、IO、CPU 和缓存命中率。

### 大事务和长事务

**我的回答**

大事务会长时间占用连接，日志很大，回滚也很大。如果涉及锁，其他事务还要等待锁释放。长事务因为执行语句多，所以 undo log 会很长，会膨胀。

**纠错与校准**

大事务危害：

- 持有锁时间长。
- undo log 膨胀。
- 回滚成本高。
- 主从复制延迟。
- redo/binlog 压力大。
- 影响 purge 清理旧版本。

长事务导致 undo log 膨胀的关键不是“语句多”，而是：

> 长事务持有很老的 Read View，导致其他事务产生的旧版本不能被 purge 清理，undo log 版本链越来越长。

### 大表删除和大表 DDL

**我的回答**

大表字段变更可以备份一张一样的表，然后迁移，最后改表名。大表删除历史数据不清楚。

**纠错与校准**

大表删除不要一条 SQL 删完：

```sql
delete from log where create_time < '2025-01-01';
```

推荐：

- 按主键或时间分批 delete。
- 每批几千到几万。
- 批次之间 sleep。
- 避免长事务。
- 如果是分区表，可以直接 drop partition。
- 低峰期执行。

大表 DDL：

- 优先使用 online DDL。
- 使用 `pt-online-schema-change` 或 `gh-ost`。
- 影子表迁移后 rename。
- 必要时灰度双写、回填、切流。

## 七、表设计与架构

### char 和 varchar

**我的回答**

占用内存空间不一样，一个是字符，一个是字符串。

**纠错与校准**

不是“字符”和“字符串”的区别，而是定长和变长。

- `char`：定长，适合固定长度字段，比如性别、状态码。
- `varchar`：变长，适合长度变化大的字符串。

`char(10)` 会按固定长度存储；`varchar(10)` 按实际长度存储，并额外保存长度信息。

### datetime 和 timestamp

**我的回答**

datetime 是显式时间，易读；timestamp 是时间戳，long 类型。

**纠错与校准**

`timestamp` 不是简单的 long 类型。区别：

- `datetime`：保存日期时间，不受时区转换影响，范围更大。
- `timestamp`：时间戳类型，受时区转换影响，范围相对小，占用更小。

业务时间通常更推荐 `datetime`。跨时区场景使用 `timestamp` 要特别注意时区转换。

### 为什么字段尽量设置 NOT NULL？

**我的回答**

NULL 会造成误解，判断是否存在要用 `is null`，判断是不是 null 要用 `= null`，不易读。

**纠错与校准**

SQL 中判断 NULL 不能用 `= null`，要用：

```sql
is null
is not null
```

推荐 `NOT NULL` 的原因：

- 语义更清晰。
- 减少 NULL 判断。
- 避免三值逻辑 `true/false/unknown`。
- 索引统计更简单。
- 可以用默认值表达业务含义。

### 三范式

**我的回答**

第一范式字段有独立性，不可拆分。第二范式字段避免字段属性传递。第三范式忘了。

**纠错与校准**

- 第一范式：字段保持原子性，不可再拆。
- 第二范式：非主键字段必须完全依赖主键，避免只依赖联合主键的一部分。
- 第三范式：非主键字段不能依赖其他非主键字段，避免传递依赖。

实际项目中不一定严格遵守范式。为了查询性能，常常会适度反范式，冗余一些快照字段。

### 订单表怎么设计？

**我的回答**

需要根据具体要求设计。订单有主信息和订单明细信息，明细通过订单 id 关联订单表。

**纠错与校准**

这个思路对。可以答成：

- 订单主表：订单号、用户、总金额、订单状态、支付状态、创建时间、支付时间等。
- 订单明细表：订单 id、商品 id、商品名快照、购买价格、数量、优惠金额等。
- 订单状态流转表：记录状态变化、操作人、操作时间、备注。

商品名和价格通常要存快照，不能只关联商品表当前值，否则商品改价或改名会影响历史订单展示。

### 唯一订单号怎么生成？

**我的回答**

可以用数据库自增 id，也可以用一个自增表记录下一个 id。

**纠错与校准**

数据库自增 id 不建议直接当订单号。常见方案：

- 雪花算法。
- 号段模式。
- Redis `incr`。
- 数据库号段表。
- 业务前缀 + 时间 + 序列号。

订单号通常需要全局唯一、趋势递增、可读、可追踪，并能支撑高并发生成。

### 什么时候需要分库分表？

**我的回答**

没有绝对标准。当数据量或查询速度明显变慢，优化索引也解决不了，或者单库压力撑不住并发量时，可以考虑分库分表。

**纠错与校准**

这句话很稳。再补一句：分库分表是最后手段。

在分库分表前，优先考虑：

- SQL 优化。
- 索引优化。
- 缓存。
- 读写分离。
- 历史数据归档。
- 分区表。
- 垂直拆分冷热字段。

分库分表适合：

- 单表数据量过大。
- 单库写压力过大。
- 存储容量接近瓶颈。
- 索引树过大，查询明显变慢。
- 业务增长无法靠单库扩容解决。

### 分库分表后的问题

**我的回答**

分页可以通过 ShardingSphere 查询各分表数据，再汇总处理。跨库事务可能要用分布式事务。分库分表后很难做 join、分页等操作。

**纠错与校准**

分库分表确实会带来很多问题：

- 跨库 join 难。
- 分页排序难。
- 分布式事务复杂。
- 全局唯一 id。
- 扩容迁移复杂。
- 热点分片。
- 聚合查询复杂。
- 运维成本上升。

跨库 join 的解决方案：

- 尽量避免跨库 join。
- 按同一分片键分表，让关联数据落同库。
- 字段冗余。
- 宽表。
- 应用层 join。
- 同步到 ES 或数仓处理复杂查询。

跨库事务的解决方案：

- 尽量避免跨库事务。
- 本地事务 + 消息最终一致。
- TCC。
- Saga。
- Seata/2PC。

分页优化：

- 避免深分页。
- 使用游标分页。
- 按分片键查询。
- 使用中间件归并排序，但要意识到 offset 越大成本越高。

## 最后总结

这次复盘暴露出的主要问题不是完全不会，而是几个概念容易混：

- MySQL 不是存储引擎，InnoDB 才是存储引擎。
- B+ 树快的核心是降低树高、减少磁盘 IO。
- 覆盖索引是 `Using index`，索引下推是 `Using index condition`。
- 范围查询后的联合索引字段通常不能继续用于定位，但可能参与索引下推。
- MVCC 解决可见性，锁解决互斥和范围保护。
- 间隙锁锁的是索引间隙，主要防插入，不是防已有行被修改。
- redo log 是物理日志，binlog 是逻辑日志。
- 两阶段提交是为了保证 redo log 和 binlog 一致。
- 主从复制是从库拉取主库 binlog，写 relay log 后重放。
- 长事务导致 undo 膨胀，核心是老 Read View 阻止 purge 清理旧版本。

后续复习可以按这条主线继续打磨：

```text
索引结构 -> SQL 优化 -> 事务隔离 -> MVCC -> 锁 -> 日志恢复 -> 主从复制 -> 分库分表
```
