# 数据库表结构设计规范：从三范式到业务落地

数据库设计不是只会建表。面试里如果被问“你们表结构怎么设计”“三范式是什么”“为什么要冗余字段”“索引怎么提前考虑”，不能只回答：

> 我们大多数按照阿里 Java 开发规范来做。

这句话方向没问题，但还需要补上为什么这么做，以及真实业务里哪些地方会为了性能和可追溯性做适度反范式。

这篇文章整理一套更适合面试和项目复盘的回答。

## 我们通常怎么做表设计？

在业务系统里，我一般会从这几个维度看表结构：

- 表名和字段名是否能表达业务含义；
- 主键、唯一键、普通索引是否和查询场景匹配；
- 字段类型是否准确，尤其金额、数量、状态、时间；
- 表之间的关系是否清楚，是一对一、一对多还是多阶段流转；
- 是否需要保留业务快照，避免后续基础数据变化影响历史单据；
- 是否要做软删除、状态机、版本号、审计字段；
- 是否存在大字段、宽表、冷热数据、历史数据归档问题。

如果用一句话概括：

> 表结构设计不是把对象字段照搬到数据库，而是把业务事实、查询方式、数据生命周期和一致性边界落到稳定的数据模型里。

## 三大范式

范式是关系型数据库设计里的基础规则，目的是减少数据冗余和更新异常。

但项目里不是为了“追求范式”而设计表，而是先理解范式解决什么问题，再根据查询性能和业务追溯做适度取舍。

### 第一范式：字段原子性

第一范式要求字段不可再拆，也就是一个字段只表达一个明确含义。

不推荐：

```text
address = "上海市-浦东新区-张江"
```

更推荐：

```text
province = "上海市"
city = "上海市"
district = "浦东新区"
address_detail = "张江..."
```

再比如不推荐：

```text
goods_info = "螺纹钢|HRB400E|20mm|10吨"
```

更推荐拆成：

```text
category_name
material
spec
weight
```

第一范式解决的是：

- 字段无法单独查询；
- 字段无法单独建索引；
- 字段更新困难；
- 后续统计和筛选成本高。

面试表达：

> 第一范式强调字段原子性。一个字段不要混多个业务含义，否则后续查询、统计、索引和维护都会困难。

### 第二范式：完全依赖主键

第二范式建立在第一范式基础上，要求非主键字段必须完全依赖主键，不能只依赖联合主键的一部分。

这个问题常出现在联合主键表里。

例如订单明细表如果设计成：

```text
order_id
goods_id
goods_name
goods_category
order_quantity
```

如果联合主键是：

```text
(order_id, goods_id)
```

那么：

- `order_quantity` 依赖 `order_id + goods_id`，合理；
- `goods_name`、`goods_category` 只依赖 `goods_id`，不完全依赖整个联合主键。

这就违反第二范式。

更规范的设计是：

```text
goods 表：
id
goods_name
goods_category

order_detail 表：
order_id
goods_id
order_quantity
```

第二范式解决的是：

- 同一个商品信息在多个订单明细里重复存储；
- 商品名称变更时需要更新多行；
- 插入明细时可能带入不一致的商品信息。

面试表达：

> 第二范式主要解决联合主键下的部分依赖问题。非主键字段应该依赖整个主键，而不是只依赖主键的一部分。

### 第三范式：消除传递依赖

第三范式要求非主键字段不能依赖其他非主键字段。

例如员工表：

```text
employee_id
employee_name
dept_id
dept_name
dept_manager
```

这里：

```text
employee_id -> dept_id
dept_id -> dept_name, dept_manager
```

`dept_name` 和 `dept_manager` 不是直接依赖员工主键，而是依赖 `dept_id`，这就是传递依赖。

更规范的设计是拆表：

```text
employee 表：
employee_id
employee_name
dept_id

department 表：
dept_id
dept_name
dept_manager
```

第三范式解决的是：

- 部门信息在员工表里重复存储；
- 部门名称变化时要更新所有员工记录；
- 不同员工行里的部门名称可能不一致。

面试表达：

> 第三范式主要解决传递依赖。非主键字段之间不要互相决定，否则容易出现冗余和更新异常。

## 项目里为什么不一定严格遵守三范式？

真实业务里经常会适度反范式。

原因不是“不懂范式”，而是有些数据必须保留历史快照，或者为了减少复杂 join。

### 1. 历史快照字段

例如订单表里会冗余：

```text
buyer_name
seller_name
goods_name
category_name
spec
material
```

这些字段可能在主体表、商品表、资源表里都有，但订单创建时仍然要保存一份快照。

原因是：

```text
订单发生时的买家名称、卖家名称、商品信息，应该按当时的数据留痕。
不能因为客户改名或商品基础资料变更，导致历史订单展示变化。
```

这种冗余是合理的。

### 2. 查询性能冗余

如果一个列表页每次都要关联 5 张表，而且是高频查询，可能会在主表中冗余一些展示字段或统计字段。

例如：

```text
order_count
total_weight
total_amount
latest_status
```

这样可以减少实时聚合和多表 join。

但冗余字段必须考虑：

- 谁来维护；
- 什么时候更新；
- 是否允许短暂不一致；
- 是否有对账或修复机制。

### 3. 状态机字段

有些状态可以通过明细计算出来，但项目里仍然会在主表保存一个主状态：

```text
order_status
delivery_status
settle_status
```

原因是主流程查询和筛选都依赖状态字段，不可能每次实时从明细表聚合。

这类字段的关键不是“能不能冗余”，而是状态流转必须收口，不能到处散落更新。

## 阿里规约里常见的表设计习惯

很多公司会参考《阿里巴巴 Java 开发手册》里的数据库规约。面试时不用背条文，但要知道背后的原因。

### 1. 表名、字段名用小写和下划线

推荐：

```text
purchase_order
real_delivery
create_time
update_time
```

不推荐：

```text
PurchaseOrder
realDelivery
CreateTime
```

原因：

- MySQL 在不同系统上对大小写敏感性可能不同；
- 下划线命名更符合数据库习惯；
- 避免 ORM 映射和跨环境迁移时出现大小写问题。

### 2. 表必须有主键

每张业务表都应该有主键。

常见选择：

```text
id BIGINT
```

主键作用：

- 唯一标识一行数据；
- InnoDB 聚簇索引基于主键组织数据；
- 二级索引叶子节点会保存主键值；
- 方便更新、删除、关联和排查问题。

如果没有主键，InnoDB 会选择唯一非空索引作为聚簇索引；如果还没有，会生成隐藏 row_id。但这对业务查询和问题排查都不友好。

### 3. 主键尽量不要使用业务含义字段

例如不建议直接用订单号作为主键。

更常见的是：

```text
id BIGINT PRIMARY KEY
order_code VARCHAR(32) UNIQUE
```

原因：

- 业务编号规则可能变化；
- 业务编号可能需要展示、重发、迁移；
- 数字主键更适合 InnoDB 聚簇索引和二级索引存储；
- 业务唯一性可以用唯一索引保证。

面试表达：

> 主键负责数据库内部标识和关联，业务编号负责业务识别。两者最好分开，业务唯一性通过唯一索引约束。

### 4. 金额必须用 DECIMAL

金额不要用 `FLOAT` 或 `DOUBLE`。

推荐：

```sql
amount DECIMAL(18, 2) NOT NULL DEFAULT 0.00
```

原因是浮点数存在精度误差。

Java 里也对应使用：

```java
BigDecimal
```

如果是公司内部规范要求金额在 DTO 中用 `String` 传输，也要理解原因：避免前端或 JSON 序列化时发生精度丢失。

### 5. 时间字段要统一

常见字段：

```text
gmt_create
gmt_modified
create_time
update_time
```

无论使用哪种命名，都要团队统一。

建议：

- 创建时间不可变；
- 修改时间每次更新时自动维护；
- 查询条件经常按时间范围筛选时，要考虑索引；
- 不要用字符串保存时间。

常见类型：

```sql
DATETIME
TIMESTAMP
```

业务系统里很多会使用 `DATETIME`，避免 `TIMESTAMP` 的范围和时区自动转换带来的理解成本。

### 6. 字段尽量 NOT NULL

业务字段如果没有明确的“三态”含义，建议 `NOT NULL` 并给默认值。

例如：

```sql
status TINYINT NOT NULL DEFAULT 0
remark VARCHAR(500) NOT NULL DEFAULT ''
amount DECIMAL(18, 2) NOT NULL DEFAULT 0.00
```

这样可以减少：

- `NULL` 判断；
- 索引统计复杂度；
- Java 代码里的空指针；
- `NULL` 和空字符串混用。

但不是所有字段都必须强行 `NOT NULL`。

如果业务上确实存在“未知”和“空值”的区别，可以允许 `NULL`，但要明确语义。

### 7. 状态字段用小类型并定义枚举

状态字段常见：

```sql
status TINYINT NOT NULL DEFAULT 0 COMMENT '状态：0-待处理，1-处理中，2-成功，3-失败'
```

Java 里应该有对应枚举：

```java
enum OrderStatus {
    INIT,
    PROCESSING,
    SUCCESS,
    FAILED
}
```

注意点：

- 不要用魔法数字散落在代码里；
- 状态流转要收口；
- 状态含义写进注释；
- 多状态字段要区分主状态和子状态。

### 8. 删除要谨慎，优先软删除或状态化

很多业务表不会物理删除，而是使用：

```sql
is_deleted TINYINT NOT NULL DEFAULT 0
```

或者：

```sql
status = INVALID
```

原因：

- 业务数据需要审计；
- 后续可能对账、追溯、排查；
- 物理删除可能破坏关联关系。

但软删除也有成本：

- 所有查询都要带删除条件；
- 唯一索引要考虑删除数据的影响；
- 数据量增长后需要归档策略。

### 9. 大字段不要随便放主表

例如：

```text
content
remark_detail
request_json
response_json
file_content
```

如果字段很大、访问频率低，建议拆到扩展表或日志表。

原因：

- 主表行变宽，影响缓存命中；
- 查询列表时不需要大字段；
- 大字段会增加网络传输和 IO。

常见拆分：

```text
order_main
order_ext
order_log
```

### 10. 字段注释要写清楚

数据库表不是只给程序读，也给排查问题的人读。

字段注释至少要说明：

- 状态枚举含义；
- 金额单位；
- 数量/重量单位；
- 业务编号含义；
- 是否是快照字段；
- 是否允许为空。

好的注释可以减少很多排查成本。

## 索引设计规范

表设计时不能等到 SQL 慢了才想索引。至少要提前考虑：

- 主键索引；
- 唯一索引；
- 查询条件索引；
- 排序字段；
- 关联字段；
- 是否能覆盖索引。

### 1. 唯一性靠唯一索引兜底

例如订单号：

```sql
UNIQUE KEY uk_order_code (order_code)
```

不要只依赖代码判断：

```text
先查有没有，再插入
```

并发下两个线程都可能查不到，然后同时插入。

唯一索引是数据库层最后的兜底。

### 2. 联合索引要看查询方式

例如常见查询：

```sql
WHERE main_id = ?
  AND status = ?
  AND create_time >= ?
  AND create_time < ?
ORDER BY create_time DESC
```

可以考虑：

```sql
KEY idx_main_status_time (main_id, status, create_time)
```

联合索引不是字段越多越好，要考虑：

- 等值条件放前面；
- 范围条件后面的列可能无法继续高效使用；
- 排序字段能否利用索引顺序；
- 索引字段太多会增加写入成本。

### 3. 低区分度字段不要单独建索引

例如：

```text
is_deleted
status
gender
```

这类字段取值少，单独建索引效果通常不好。

但它们可以作为联合索引的一部分，例如：

```sql
KEY idx_main_deleted_time (main_id, is_deleted, create_time)
```

### 4. 索引不是越多越好

索引会提升查询，但会增加：

- 插入成本；
- 更新成本；
- 删除成本；
- 存储空间；
- 优化器选择成本。

所以索引设计要围绕高频查询，而不是看到字段就建。

## 常见表结构模板

一个业务主表通常会包含：

```sql
CREATE TABLE purchase_order (
    id BIGINT NOT NULL COMMENT '主键ID',
    order_code VARCHAR(32) NOT NULL COMMENT '订单号',
    buyer_id BIGINT NOT NULL COMMENT '买方主体ID',
    buyer_name VARCHAR(128) NOT NULL DEFAULT '' COMMENT '买方名称快照',
    seller_id BIGINT NOT NULL COMMENT '卖方主体ID',
    seller_name VARCHAR(128) NOT NULL DEFAULT '' COMMENT '卖方名称快照',
    total_amount DECIMAL(18, 2) NOT NULL DEFAULT 0.00 COMMENT '订单总金额',
    status TINYINT NOT NULL DEFAULT 0 COMMENT '状态：0-待确认，1-已确认，2-已取消',
    is_deleted TINYINT NOT NULL DEFAULT 0 COMMENT '是否删除：0-否，1-是',
    version INT NOT NULL DEFAULT 0 COMMENT '版本号，用于乐观锁',
    gmt_create DATETIME NOT NULL COMMENT '创建时间',
    gmt_modified DATETIME NOT NULL COMMENT '修改时间',
    PRIMARY KEY (id),
    UNIQUE KEY uk_order_code (order_code),
    KEY idx_buyer_time (buyer_id, gmt_create),
    KEY idx_seller_time (seller_id, gmt_create)
) COMMENT='采购订单表';
```

这个模板里体现了几个点：

- `id` 做主键；
- `order_code` 做业务唯一键；
- 名称字段保存快照；
- 金额使用 `DECIMAL`；
- 状态使用小类型；
- 软删除字段；
- 乐观锁版本号；
- 创建和修改时间；
- 索引围绕查询场景设计。

## 设计一张表时我会问自己的问题

### 1. 这张表表达的业务事实是什么？

例如订单表表达“交易关系”，明细表表达“交易项”，日志表表达“状态变化记录”。

如果一张表混了多个事实，后面很容易出现字段越来越多、状态越来越乱。

### 2. 主表和明细表怎么拆？

常见结构：

```text
order_main：订单主信息
order_detail：订单明细
order_log：订单流转日志
order_ext：低频扩展字段
```

主表保存主流程字段，明细表保存一对多数据，日志表保存过程，扩展表保存低频大字段。

### 3. 哪些字段需要快照？

会随时间变化，但历史单据要按当时口径展示的字段，通常要快照。

例如：

- 主体名称；
- 商品名称；
- 规格材质；
- 合同抬头；
- 税率；
- 单价。

### 4. 哪些字段需要唯一约束？

例如：

- 订单号；
- 合同号；
- 外部流水号；
- 幂等 key；
- 第三方回调 requestId。

唯一约束是防重复、保证幂等的重要手段。

### 5. 查询入口是什么？

设计索引前先看查询入口：

- 按主体查；
- 按订单号查；
- 按状态查；
- 按时间范围查；
- 按外部单号查；
- 按业务类型查。

不同入口决定不同索引。

### 6. 数据生命周期是什么？

要提前考虑：

- 数据会不会归档；
- 是否需要物理删除；
- 是否需要审计日志；
- 历史数据是否还参与查询；
- 表数据量增长到千万级后怎么办。

## 面试里怎么回答？

如果面试官问：“你们数据库表结构怎么设计？”

可以这样回答：

> 我们大多数会参考阿里 Java 开发规范里的数据库规约，比如表名字段名使用小写下划线，业务表必须有主键，金额用 DECIMAL，状态字段用小类型并配套枚举，时间字段统一维护，字段尽量 NOT NULL 并写清楚注释。
>
> 具体设计时，我会先看这张表表达的业务事实，再确定主表、明细表、日志表和扩展表的边界。主键一般用无业务含义的 BIGINT ID，业务编号用唯一索引保证唯一性。金额、数量、重量、状态、时间这类字段会特别注意类型和单位。
>
> 范式上，我会遵守第一范式的字段原子性，第二范式的完全依赖主键，第三范式的消除传递依赖。但真实业务里也会适度反范式，比如订单里冗余买卖方名称、商品名称和规格材质作为历史快照，或者为了列表查询冗余状态和统计字段。关键是冗余字段必须有明确维护口径和一致性兜底。
>
> 索引方面，我会根据实际查询入口设计主键、唯一索引和联合索引，不会看到字段就建索引。唯一性必须用数据库唯一索引兜底，高频查询会结合等值条件、范围条件、排序字段来设计联合索引，同时控制索引数量，避免影响写入。

## 总结

1. 第一范式讲字段原子性，第二范式讲完全依赖主键，第三范式讲消除传递依赖。
2. 项目里不是绝对追求范式，历史快照、查询性能和状态流转经常需要适度反范式。
3. 主键和业务编号最好分开，业务唯一性用唯一索引兜底。
4. 金额用 `DECIMAL`，Java 里用 `BigDecimal`，不要用浮点数。
5. 状态字段要有枚举和注释，状态流转要收口。
6. 大字段、低频字段、日志字段不要随便塞进主表。
7. 索引设计要从查询场景出发，唯一索引、联合索引和写入成本要一起考虑。
8. 好的表结构设计能减少后续代码复杂度、慢 SQL、数据不一致和排查成本。
