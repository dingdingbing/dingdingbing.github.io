# 业务数据对账与修复

## 场景：对账不是找不同，而是确认口径

在某批量对账任务中，需要核对主单据、处理记录和后续结算准备数据是否一致。最初的差异列表看起来很长，但进一步排查后发现，其中一部分是口径不一致造成的误报，另一部分才是真正需要修复的数据。

对账的第一步不是写复杂 SQL，而是确定“什么算一致”。

## 对账口径：先写清楚再执行

我会先确认这些口径：

- 业务范围：哪些业务模式纳入本次核对。
- 时间范围：按创建时间、完成时间还是结算时间统计。
- 状态范围：哪些状态代表有效数据，哪些状态应排除。
- 字段来源：数量、重量、金额分别以哪一侧为准。
- 关联关系：一对一、一对多还是多阶段关联。

口径确认后，再用简单查询验证样本。样本正确，再写批量对账 SQL 或任务逻辑。

## 排查：差异数据要分层处理

我通常把差异分成三类：

| 差异类型 | 处理方式 |
| --- | --- |
| 口径误差 | 调整对账条件，不进入修复 |
| 可自动补偿 | 通过补偿任务按既有规则处理 |
| 需要人工确认 | 保留证据，明确影响范围和处理建议 |

这样做可以避免把所有差异都当成脏数据。对账任务的目标是发现真实风险，而不是制造一批无法解释的修复动作。

## 修复：证据链比脚本更重要

修复前我会保存四类信息：

- 受影响的业务单号范围。
- 修复前的关键字段对比。
- 根因判断和修复策略。
- 回滚或二次处理方案。

修复时不只改一张表，还要检查关联记录、状态字段和后续处理数据。很多数据问题看起来是数量不一致，实际还伴随关联关系缺失或状态未推进。

## 验证：同一口径复跑

修复后必须用同一套口径重新对账：

1. 差异列表是否消失或缩小到可解释范围。
2. 修复样本的数量、重量和状态是否一致。
3. 后续处理是否能继续推进。
4. 是否出现重复记录或孤立记录。
5. 正常样本是否保持不变。

如果验证口径和发现问题时不一致，修复结果就无法证明。

## 总结

业务数据对账的核心是口径、证据和边界。能说明“为什么差异存在、为什么这样修、如何确认修完”，才算真正完成一次数据修复。
