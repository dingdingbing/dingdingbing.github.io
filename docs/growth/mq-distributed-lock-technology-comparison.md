# MQ&分布式锁技术选型横向对比

## 主问题

面试里经常会问：分布式锁为什么用 Redis，不用 Zookeeper？MQ 为什么选 RabbitMQ，不选 RocketMQ 或 Kafka？数据库连接驱动、连接池之间有什么区别？这些问题怎么横向对比？

这类问题考的不是“背优缺点”，而是你能不能根据业务场景、可靠性要求、团队成本和性能要求做取舍。

## 对比框架

横向对比可以固定从这些维度讲：

- 业务场景：解决什么问题。
- 一致性要求：强一致、最终一致，还是允许短暂不一致。
- 性能要求：吞吐、延迟、P99。
- 可靠性要求：故障恢复、消息不丢、锁不误删。
- 运维成本：部署、监控、扩容、排障。
- 团队熟悉度：是否已有成熟实践。
- 失败场景：网络分区、节点宕机、超时、重试。
- 代码复杂度：接入成本和后续维护成本。

## 分布式锁：Redis、Zookeeper、数据库

### Redis 分布式锁

适合：

- 高性能、低延迟的短临界区。
- 锁持有时间短。
- 允许通过过期时间兜底释放锁。
- 团队已经有 Redis 基础设施。

优点：

- 性能高。
- 接入简单。
- 适合大多数业务互斥场景。

风险：

- 需要正确设置过期时间。
- 需要用唯一 token 防止误删别人的锁。
- 锁过期但业务没执行完，会出现并发进入。
- 主从切换、网络分区下要理解一致性边界。

常见实现：

```text
SET key value NX PX expireMillis
释放时校验 value 后再删除
```

### Zookeeper 分布式锁

适合：

- 更强调一致性和顺序性的场景。
- 锁竞争不极端高。
- 已经有 Zookeeper 运维经验。
- 需要临时节点、顺序节点、监听机制。

优点：

- 临时节点随会话断开自动删除。
- 顺序节点适合公平锁。
- 一致性语义更强。

风险：

- 性能通常不如 Redis。
- 运维和理解成本更高。
- 监听和会话超时需要处理好。

### 数据库锁

适合：

- 低并发、强依赖数据库事务的场景。
- 不想引入额外中间件。
- 锁和业务数据强绑定。

优点：

- 简单直接。
- 和事务结合自然。

风险：

- 性能较低。
- 容易造成数据库锁等待。
- 不适合高频分布式锁。

### 面试回答

可以这样说：

> 如果是大多数业务里的短时间互斥，我优先用 Redis 锁，因为性能好、接入简单，但要保证 set nx px、唯一 token、释放锁校验和合理过期时间。如果业务更强调强一致和公平顺序，或者已经有 Zookeeper 体系，可以用 Zookeeper 临时顺序节点。如果并发低、锁和数据库事务绑定很强，可以用数据库锁。选型关键不是谁更高级，而是看一致性、性能、运维成本和失败场景。

## MQ：RabbitMQ、RocketMQ、Kafka

### RabbitMQ

适合：

- 业务消息。
- 路由规则相对灵活。
- 延迟要求不是极致。
- 需要比较成熟的确认、路由、死信机制。

优点：

- 路由模型灵活。
- 确认机制成熟。
- 对业务系统友好。

风险：

- 超大吞吐场景不如 Kafka。
- 大量堆积时要关注内存、磁盘和消费能力。

### RocketMQ

适合：

- 电商、交易、订单类业务消息。
- 事务消息、延迟消息、顺序消息。
- 高吞吐业务消息。

优点：

- 业务消息能力强。
- 对事务消息、延迟消息支持更直接。
- 吞吐能力好。

风险：

- 运维和治理成本高于简单 RabbitMQ 场景。
- 团队需要掌握它的模型和排障方式。

### Kafka

适合：

- 日志、埋点、流式数据。
- 超高吞吐。
- 数据可回放。
- 多消费者订阅同一份事件流。

优点：

- 吞吐高。
- 分区模型适合大规模数据流。
- 保留时间内可以回放。

风险：

- 单条业务消息的复杂路由不如 RabbitMQ 直观。
- 低延迟单消息确认和复杂业务语义要谨慎设计。

### 面试回答

可以这样说：

> RabbitMQ 更适合传统业务异步解耦，路由、确认、死信这些机制比较直观。RocketMQ 更偏业务消息中台，事务消息、延迟消息、顺序消息能力更强。Kafka 更适合日志、埋点、流式数据和高吞吐可回放场景。选 MQ 时我会看消息类型、吞吐、延迟、顺序性、事务性、堆积能力、运维成本和团队经验。

## 数据库连接池与驱动

### JDBC Driver

JDBC Driver 是应用和数据库通信的驱动，比如 MySQL Connector/J。它负责协议通信、认证、SQL 发送、结果集读取、类型转换等。

常见关注：

- 驱动版本是否匹配数据库版本。
- 时区、编码、SSL、连接参数。
- 批量写入参数。
- prepared statement 缓存。
- 结果集流式读取。

### 连接池

连接池负责复用数据库连接，避免每次 SQL 都创建和销毁连接。常见连接池包括 HikariCP、Druid 等。

HikariCP：

- 性能好。
- Spring Boot 默认常用。
- 功能相对专注，监控能力需要配合 Micrometer 等。

Druid：

- 监控和 SQL 统计能力强。
- 功能多。
- 配置复杂度更高。

### 面试回答

可以这样说：

> JDBC Driver 解决的是 Java 应用怎么和数据库协议通信，连接池解决的是连接复用和并发连接管理。Spring Boot 默认常用 Hikari，因为性能好、实现轻量。Druid 的监控和 SQL 统计能力更强，但功能更多、配置更复杂。选型时我会看性能、稳定性、监控需求、团队熟悉度和线上排查方式。无论用哪个，都要合理设置最大连接数、超时、空闲连接、连接存活检测，并结合数据库最大连接数和实例数一起算。

## 注册中心：Nacos、Zookeeper、Eureka

Nacos：

- 服务注册发现和配置中心结合得比较好。
- Spring Cloud Alibaba 生态常见。
- 适合国内微服务项目。

Zookeeper：

- 一致性能力强。
- Dubbo 早期常见注册中心。
- 运维和理解成本更高。

Eureka：

- Spring Cloud Netflix 早期常见。
- AP 倾向，服务发现简单。
- 现在新项目使用相对少。

## 配置中心：Nacos、Apollo、Spring Cloud Config

Nacos：

- 注册中心和配置中心一体。
- 接入 Spring Cloud Alibaba 方便。

Apollo：

- 配置管理能力成熟。
- 灰度、权限、审计、发布流程比较完整。

Spring Cloud Config：

- 基于 Git 管理配置。
- 简洁，但动态管理体验依赖配套建设。

## 可验证结论

横向对比不能只背结论。可以用小表格验证：

| 问题 | 优先方案 | 原因 |
| --- | --- | --- |
| 高频短锁 | Redis | 性能高、接入简单 |
| 公平锁/强一致锁 | Zookeeper | 临时顺序节点和一致性语义更强 |
| 业务异步解耦 | RabbitMQ/RocketMQ | 看事务、延迟、顺序要求 |
| 日志流/埋点 | Kafka | 高吞吐、可回放 |
| Spring Boot 默认连接池 | HikariCP | 性能好、默认集成成熟 |

## 面试表达版本

可以这样回答：

> 我做技术选型会先看业务场景，再看一致性、性能、可靠性、运维成本和团队熟悉度。比如分布式锁，如果是短时间互斥，我一般选 Redis，但要处理 token、过期时间和误删问题；如果要更强一致和公平顺序，可以选 Zookeeper；低并发且和事务强绑定可以用数据库锁。MQ 也类似，RabbitMQ 适合业务异步解耦，RocketMQ 更适合事务、延迟、顺序这些业务消息，Kafka 适合日志和流式高吞吐。数据库这块 JDBC Driver 和连接池不是一回事，Driver 负责协议通信，Hikari 或 Druid 负责连接复用和并发管理。选型不是固定答案，而是根据场景取舍。
