# Hikari 连接池与数据库连接数

## 主问题

数据库最大连接数默认是 200。如果代码写错了，在一个 for 循环里执行 1000 次查询同一条 SQL，会发生什么？

这个问题容易让人直接联想到“1000 次 SQL 会不会创建 1000 个数据库连接”，但真实执行结果取决于应用的线程模型、事务范围、连接池配置、SQL 执行耗时和数据库连接上限。

## 直觉答案

第一反应可能是：

- 循环 1000 次查询会给数据库造成很大压力。
- 数据库连接数默认 200，超过后可能报 `Too many connections`。
- 如果使用 Hikari，最大连接数会限制应用侧同时持有的连接数。

这些判断有方向，但还不够精确。关键要区分“SQL 执行次数”和“并发数据库连接数”。

## 真实执行场景

如果这 1000 次查询发生在同一个请求线程里，并且每次查询都是短 SQL，通常不是一次性打开 1000 个数据库连接。

常见执行过程是：

1. 业务线程进入循环。
2. MyBatis 或 JDBC 从 Hikari 连接池获取连接。
3. 执行 SQL。
4. 结果返回后释放连接，连接回到池里。
5. 下一次循环再复用池中的连接。

这种情况下，问题主要是 SQL 次数过多导致接口变慢、数据库 QPS 上升、CPU/IO 消耗增加，而不是单个线程直接把数据库连接打满。

但如果 1000 次查询被多个请求、多个线程、异步任务或并行流同时放大，情况就不同了。Hikari 的 `maximumPoolSize` 会限制单个应用实例同时借出的连接数。超过池大小后，新请求不会马上继续向数据库创建连接，而是在应用侧等待连接，直到拿到连接或超过 `connectionTimeout`。

## Hikari 最大连接数的作用

Hikari 的最大连接数控制的是“这个应用实例最多同时持有多少个数据库连接”。

例如：

```properties
spring.datasource.hikari.maximum-pool-size=20
spring.datasource.hikari.connection-timeout=30000
```

含义是：

- 单个应用实例最多同时使用 20 个连接。
- 第 21 个需要连接的线程会等待。
- 等待超过 30 秒还拿不到连接，会在应用侧报获取连接超时。

所以连接池可以保护数据库，不让某个应用实例无限制创建连接。但它不是性能问题的消除器，只是把“数据库被打爆”的风险，转换成“应用线程等待、接口变慢或超时”的风险。

## 数据库连接上限的作用

数据库自己的最大连接数是全局资源限制，约束所有应用、脚本、管理工具和其他服务的连接总数。

如果所有客户端连接总数超过数据库上限，数据库可能报：

```text
Too many connections
```

这通常说明不是单个 SQL 次数的问题，而是整体连接占用超过了数据库能承受的范围。需要看：

- 有多少个应用实例。
- 每个实例的 Hikari 最大连接数是多少。
- 是否有后台任务、定时任务、报表任务占用连接。
- 是否存在连接泄漏。
- 是否有慢 SQL 长时间占用连接。

## 如果 Hikari 最大连接数设置不正确

### 设置过大

如果每个应用实例都把 `maximumPoolSize` 设置得很大，实例数一扩容，总连接上限会快速膨胀。

例如 10 个应用实例，每个实例最大连接数 50，理论上应用侧最多可能占用 500 个数据库连接。如果数据库上限是 200，就可能出现连接争抢、数据库拒绝连接或其他服务拿不到连接。

常见后果：

- 数据库连接被应用实例耗尽。
- 数据库线程、内存和上下文切换压力变大。
- 慢 SQL 数量上升后，连接被长时间占用。
- 其他服务或管理操作连接失败。

### 设置过小

如果 `maximumPoolSize` 过小，数据库可能还有能力处理请求，但应用侧线程会排队等连接。

常见后果：

- 接口响应时间变长。
- 业务线程阻塞在获取连接阶段。
- 高峰期出现 Hikari 获取连接超时。
- Tomcat、Dubbo 或业务线程池被等待连接的线程占满，进一步放大故障。

### 设置和业务模型不匹配

如果一个请求里有长事务、慢 SQL、远程调用或循环查询，连接会被占用更久。同样的最大连接数，在短 SQL 场景下可能够用，在长事务场景下可能很快耗尽。

因此连接池参数不能只看一个数字，要结合：

- 单实例并发量。
- SQL 平均耗时和 P99 耗时。
- 事务持有连接的时间。
- 应用实例数量。
- 数据库最大连接数。
- 是否有读写分离、报表库或独立任务库。

## 延伸问题

### 1. for 循环 1000 次查询一定会打满连接池吗？

不一定。

单线程串行执行时，通常是反复复用少量连接。真正危险的是高并发下的 N 次循环查询，也就是 N+1 查询问题被并发放大。

### 2. 连接池满了，是数据库报错还是应用报错？

如果 Hikari 池满，通常先是应用侧等待连接，等待超时后报获取连接超时。

如果应用侧总连接数超过数据库连接上限，或者数据库已经没有可用连接，则可能出现数据库拒绝连接，例如 `Too many connections`。

### 3. 最大连接数是不是越大越好？

不是。

连接数过大可能让数据库承受过多并发，导致整体吞吐下降。连接池大小应该服务于稳定吞吐，而不是单纯追求更多并发。

### 4. 怎么优化循环查询？

优先考虑把循环查询改成批量查询。

例如把 1000 次：

```sql
select * from order_item where order_id = ?
```

改成一次或少量几次：

```sql
select * from order_item where order_id in (...)
```

然后在应用内按 `order_id` 分组。

### 5. 怎么判断是连接池问题还是 SQL 慢？

可以同时看：

- Hikari 活跃连接数、空闲连接数、等待连接线程数。
- 接口耗时和获取连接耗时。
- 数据库慢 SQL。
- 数据库当前连接数。
- 线程栈是否大量阻塞在获取连接。

如果等待连接线程多，但数据库负载不高，可能是池太小、连接泄漏或连接持有时间过长。如果数据库负载很高，可能是慢 SQL、循环查询或并发过高。

## 可验证结论

可以用一个小实验验证：

1. 设置 Hikari 最大连接数为 2。
2. 写 10 个并发请求，每个请求开启事务并执行慢 SQL 或 `sleep`。
3. 观察第 3 个之后的请求是否等待连接。
4. 调低 `connectionTimeout`，观察应用侧获取连接超时。
5. 再观察数据库当前连接数是否不会超过该应用实例的池大小。

这个实验能说明：连接池限制的是应用实例到数据库的并发连接数；循环 SQL 主要影响执行次数和耗时；真正的线上风险往往来自循环查询、慢 SQL、高并发、长事务和错误连接池配置共同叠加。
