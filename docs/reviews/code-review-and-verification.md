# Code Review 与验证闭环复盘

## 场景：评审意见不只改字面问题

在某交易链路的迭代中，评审意见指出两类风险：一类是入口参数校验只覆盖了主流程，另一类是数据修复说明缺少验证口径。表面看只是补几行判断和说明，实际风险在于后续维护者无法确认“改动是否真的覆盖异常分支”。

我的处理方式是先把评审意见拆成行为问题，而不是直接按评论逐条改文本：

- 哪个输入会触发错误路径。
- 哪个状态组合会影响后续处理。
- 哪些字段需要在修复前后保持一致。
- 哪条验证命令或查询可以证明改动生效。

## 约束：改动要小，但证据要完整

这类修改通常处在交付后段，不能把局部评审升级成大范围重构。我的边界是：

- 不改动已稳定的主流程结构。
- 不引入新的公共抽象，只在当前业务判断附近补齐分支。
- 不扩大数据修复范围，先确认差异样本和影响边界。
- 不用“看起来没问题”作为结论，必须留下可复查证据。

小改动和完整验证并不冲突。代码可以小，验证链路要完整。

## 执行：从评论到检查清单

我会把评审意见整理成一张短清单：

| 检查项 | 处理方式 | 验证方式 |
| --- | --- | --- |
| 入口参数缺失 | 在入口处返回明确失败结果 | 构造缺失参数用例 |
| 状态组合遗漏 | 补充分支并保持主流程直读 | 覆盖新增状态组合 |
| 修复说明不清 | 写明差异字段、修复范围和回滚方式 | 保存修复前后查询结果 |
| 异步通知重复 | 使用业务键做幂等判断 | 重放相同业务键确认只处理一次 |

如果评审意见涉及 SQL、消息、缓存或任务调度，我会优先补能证明行为的测试或脚本化查询，再调整实现。这样可以避免改完代码后只能靠人工回忆判断结果。

## 权衡：什么时候不抽象

评审中经常会出现“这几段判断能不能抽一个方法”的讨论。我的判断标准是：如果抽象只是为了让行数减少，但调用方仍然要理解同样多的业务条件，就不急着抽。

我更倾向于把一两处业务判断留在主流程附近，并用清晰变量名表达意图。只有当同一规则在多个入口重复出现，或者规则本身已经形成稳定边界时，再抽成可复用方法。这样既减少误复用，也方便后续排查从入口一路读到结果。

## 验证：让结论可以被复查

完成修改后，我会按风险从小到大验证：

1. 跑与改动最相关的单元测试或局部构建。
2. 对新增分支补充正向、反向和边界样例。
3. 如果涉及数据修复，保留修复前后的数量、状态和关联关系对比。
4. 如果涉及异步通知，验证重复投递、失败重试和补偿任务的行为一致。
5. 在评审回复中说明改动范围、验证命令和未覆盖原因。

验证的重点不是堆命令，而是让每个结论有证据来源。评审者可以快速确认风险被覆盖，后续维护者也能从记录中还原当时的判断。

## 结果与复盘

这种处理方式带来的价值是把评审从“改代码风格”推进到“降低交付风险”。一次评审结束后，留下的不只是更清晰的代码，还有可复用的检查口径：

- 入口判断是否覆盖异常输入。
- 状态流转是否覆盖边界组合。
- 数据修复是否有前后证据。
- 异步链路是否验证重复、失败和补偿。

我认为有效的工程实践不是追求流程复杂，而是把判断、改动和证据连成闭环。这样小问题不会被放大成线上风险，大问题也能被拆成可验证的步骤。
