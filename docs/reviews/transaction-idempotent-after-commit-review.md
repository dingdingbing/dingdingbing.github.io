# 大事务、幂等接口与提交后回查问题复盘

## 场景

这次问题来自一次 Code Review 收尾阶段的讨论。

在销售实提批量修改价格审核通过的场景中，入口方法大致是：

```text
com.banksteel.delivery.service.sales.impl.SalesRealDeliveryCreateServiceImpl#batchModifyPriceAuditPass
```

这个流程里本地会修改实提相关数据，同时还会调用资金和结算相关接口，例如：

```java
salesContractCapitalApi.updateCapitalUseInfo(updateCapitalUseDTO);
```

当时我的第一反应是想给这个接口加事务。原因也很直接：我不希望中途发生异常后，前面已经产生了一部分错误数据，后续流程却没有完整执行。

但是 Review 时提出了一个关键问题：

> 如果中途接口发生错误，我们要么保证这种数据没有产生影响，要么把错误明确暴露出来。

于是我倾向于加事务，把本地修改、资金更新、结算调用都放进一个大事务里。

真正的问题也在这里出现了：资金和结算接口内部会回查实提信息，而且我们又采用查询快照版本进行计算。如果本地事务还没有提交，远程接口通过自己的连接查询数据库时，就读不到我刚刚在当前事务里更新的实提数据。

也就是说，我虽然在当前事务里更新了数据，但后续还有流程没处理完，事务不能提交；而幂等的更新接口查询的是数据库已提交的实时数据，所以它拿不到我的最新结果。

这个场景的矛盾可以简化成：

```text
想用大事务保证异常时回滚
  -> 事务不提交
  -> 下游接口回查不到新数据
  -> 资金/结算按旧快照计算
  -> 反而产生更隐蔽的业务错误
```

## 当时的解决方式

最终思路不是继续扩大事务范围，而是重新划分事务边界：

```text
本地事务：只保证实提价格、审核状态、关联数据、待处理任务一致提交
提交之后：再触发资金重算、销售结算、采购结算等依赖新快照的动作
失败之后：通过任务状态、错误原因、告警和重试暴露出来
```

也就是把流程拆成两个阶段。

第一阶段是本地核心数据变更：

```text
前置校验
  -> 本地事务开始
  -> 修改销售实提明细价格
  -> 修改采购实提明细价格
  -> 修改审核状态
  -> 记录待资金/结算重算任务
  -> 本地事务提交
```

第二阶段是提交后的副作用处理：

```text
本地事务提交成功
  -> 调资金占用更新
  -> 调销售结算
  -> 调采购结算
  -> 成功：任务标记 SUCCESS
  -> 失败：任务标记 FAIL，记录错误原因，后续重试或人工处理
```

这样可以保证：

- 本地核心数据不会改一半。
- 下游接口回查实提时，一定能看到已经提交的新数据。
- 下游失败不会被吞掉，而是有状态、有日志、有任务可以追踪。

## 关键原理

### 1. 其他连接读不到当前事务未提交的数据

在常见数据库隔离级别下，一个事务中修改的数据，在提交前只对当前事务连接可见。

资金和结算接口如果是远程服务、另一个事务、另一个数据库连接，或者使用 `REQUIRES_NEW` 之类的独立事务语义，那么它查询到的是数据库里已经提交的版本。

所以这种写法有天然风险：

```java
@Transactional(rollbackFor = Exception.class)
public void batchModifyPriceAuditPass(...) {
    updateRealDeliveryPrice();

    salesContractCapitalApi.updateCapitalUseInfo(updateCapitalUseDTO);

    autoSettle();
}
```

当前方法里 `updateRealDeliveryPrice()` 已经执行了 `update`，但是事务还没有提交。远程资金接口回查实提时，读到的仍然是旧快照。

这个问题不能靠简单调整代码顺序解决，只要远程调用仍然发生在本地事务提交前，它就有可能读不到新数据。

### 2. 大事务不能解决跨服务读已提交快照的问题

这次一开始想加事务，是为了避免中途失败带来的脏数据。

这个诉求是对的，但“大事务包住所有动作”不是这个场景的答案。因为资金、结算这类接口不是简单的本地数据库写入，它们内部还有自己的查询和计算逻辑。

大事务只能保证当前本地连接里的数据库操作原子性，不能让另一个服务读到本事务未提交的数据。

甚至更危险的是：如果下游接口按旧数据计算并执行成功，当前事务后面也提交了，那么系统表面上没有报错，但业务结果已经偏了。

### 3. 幂等接口不应该依赖未提交的主表状态

幂等接口的核心目标是：

```text
同一个业务动作重复调用，结果仍然稳定
```

它更适合基于这些信息判断：

- 业务单号。
- 幂等 key。
- 操作流水号。
- 任务记录。
- 已处理结果表。

而不是依赖主流程当前事务里尚未提交的中间状态。

如果幂等接口必须依赖数据库实时状态，那么它应该在主事务提交后调用；如果必须在事务内调用，那么就应该把本次计算所需的新数据快照作为参数传入，而不是让它自己回查数据库。

### 4. `afterCommit` 能解决读不到新数据，但不能单独兜住失败

一个轻量处理方式是使用事务提交后回调：

```java
@Transactional(rollbackFor = Exception.class)
public void modifyPriceInTx(...) {
    updateLocalData();

    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
        @Override
        public void afterCommit() {
            salesContractCapitalApi.updateCapitalUseInfo(updateCapitalUseDTO);
            autoSettle();
        }
    });
}
```

`afterCommit()` 的好处是：它会在当前事务成功提交后执行。此时下游接口再回查实提，就能读到最新数据。

但它也有一个明显问题：

```text
afterCommit 执行失败时，本地事务已经提交，不能再回滚。
```

所以如果资金和结算是关键链路，只靠 `afterCommit` 打日志是不够的。更稳妥的是在事务里先落一条任务记录，然后由提交后的同步调用、异步消费或定时任务去处理。

### 5. 事务提交后失败，要靠状态机和补偿暴露

Code Review 提到的“错误要能感知”，不一定只能通过事务回滚实现。

在跨服务流程里，更常见的做法是业务状态机：

```text
INIT
  -> PROCESSING
  -> SUCCESS
  -> FAIL
```

例如这次价格审核通过可以拆成：

```text
审核通过处理中
  -> 本地实提价格已更新
  -> 资金重算成功
  -> 结算重算成功
  -> 审核通过完成
```

如果资金或结算失败，就停在：

```text
处理失败 / 待重试 / 待人工处理
```

这样数据不是“静默失败”，而是有明确状态暴露出来。后续可以通过定时任务重试，也可以通过人工处理入口修复。

## 更多思考

### 方案一：本地事务提交后同步调用

最直接的写法是用 `TransactionTemplate` 明确控制提交点：

```java
ModifyResult result = transactionTemplate.execute(status -> {
    updateLocalData();
    savePendingTask();
    return buildModifyResult();
});

salesContractCapitalApi.updateCapitalUseInfo(result.getUpdateCapitalUseDTO());
autoSettle(result);
```

`transactionTemplate.execute(...)` 返回时，本地事务已经结束。后续接口再查询数据库，能看到最新实提数据。

这个方案的优点是清晰，不依赖 Spring AOP 代理，也不会遇到同类自调用导致 `@Transactional` 不生效的问题。

它的缺点是：提交后远程调用失败时，本地数据已经提交，所以必须配合任务状态、重试和告警。

### 方案二：本地事务加任务表，再异步补偿

更稳妥的方式是本地事务里插入任务：

```text
任务类型：资金重算 / 销售结算 / 采购结算
业务键：handleId / orderCode / contractCode
状态：PENDING / PROCESSING / SUCCESS / FAIL
错误信息：last_error
重试次数：retry_count
```

本地事务提交后，由任务消费器处理。

这种方式更适合资金、结算这类不能静默失败的链路。因为它把失败变成了可查询、可重试、可告警的数据，而不是只存在于一行日志里。

### 方案三：改造下游接口，传入本次修改后的快照

还有一种更理想但改造更大的方案：资金和结算接口不要回查实提，而是接收本次修改后的明细快照。

类似：

```text
updateCapitalUseInfo(orderCode, realDeliverySnapshot)
```

这样即使主事务还没提交，下游也能基于传入的新数据计算。

但这个方案要求资金、结算链路统一支持快照入参，还要保证快照口径和数据库最终提交结果一致。改造成本和验证成本都比较高，通常不适合作为临时修复方案。

### 方案四：强一致需求下合并边界

如果这个幂等更新逻辑其实只是当前服务内部的一段本地数据库逻辑，那么就不要设计成远程接口回查数据库。

可以把它收敛成当前领域服务里的一个本地方法，复用当前事务内已经计算出的数据。

但只要它跨服务、跨连接、跨事务，就不能假设它能读到当前事务未提交的数据。

## 总结

1. 事务不是越大越安全。跨服务调用放进本地大事务里，可能让下游读不到新数据，反而产生隐蔽业务错误。
2. 如果下游接口依赖数据库已提交快照，它就应该在本地事务提交后执行。
3. 幂等最好基于业务幂等 key、任务表、操作流水，而不是依赖主事务未提交的中间状态。
4. `afterCommit` 可以解决“提交后再调用”的时机问题，但不能单独解决提交后失败的追踪和补偿问题。
5. 对资金、结算这类关键链路，推荐使用“本地事务 + 待处理任务 + 状态机 + 重试/告警”的方式，把失败显式暴露出来。

这次复盘给我的最大提醒是：Code Review 里说的“错误要能感知”，不等价于“把所有东西都塞进一个事务”。更准确的表达应该是：

```text
本地一致性靠事务；
跨服务一致性靠状态、幂等和补偿；
依赖提交态读取的动作，必须放在提交之后。
```
