# 业务系统 Code Review 规范复盘

## 场景：一次围绕业务边界的代码评审

刚刚参与了一次 code review，领导的一些思路很有必要整理下来。

这次评审不是只看代码能不能跑，也不是只看格式是否统一。领导首先看的是项目结构，其次特别关注系统里的业务代码是否存在定制化逻辑；再对比接口名字和注释，确认代码表达的含义是否一致；然后继续看应用内部的调用方式，比如 `Service` 调用 `Service`，或者 `Service` 调用 `Manager` 是否符合项目分层习惯。

查询逻辑也是重点：是否存在全量查询、无条件查询，是否会让第三方系统查询到不属于当前业务类型的订单。因为这个项目对接第三方系统，数据安全是底线，不能因为接口复用或查询条件缺失，把其他业务模式的数据暴露出去。

但另一方面，我们也不能把代码写成完全针对某一个第三方的定制实现。系统虽然对接了外部第三方，但内部已经抽象出一套自己的在线交易业务模式。这个时候，查询条件、业务类型、接口抽象和代码分层就需要同时考虑：既要隔离第三方可见的数据范围，又要保留内部业务模型的通用性。

最后是调用顺序和调用逻辑。团队并行开发时，每个人的编码风格不同，AI 生成代码的风格也不同，这也是领导非常在意的点。代码评审不只是找 bug，还要把团队的编码方式收拢到同一种业务表达方式上。

## 当时的整理方式

这次 review 后，我更倾向于把代码评审拆成几个层次，而不是只按文件从上往下看。

| 层次 | 关注点 | 典型问题 |
| --- | --- | --- |
| 项目结构 | 模块职责、包路径、分层边界 | 新代码是否放在正确模块，是否破坏原有分层 |
| 业务边界 | 第三方定制逻辑与内部业务模型 | 是不是把某个第三方的逻辑写死到通用流程里 |
| 接口表达 | 方法名、接口名、注释、参数 | 名字和注释是否能准确表达业务语义 |
| 内部调用 | `Controller`、`Service`、`Manager` 的调用关系 | 是否出现不符合项目习惯的跨层调用 |
| 查询安全 | 查询条件、业务类型、数据范围 | 是否存在全量查询、无条件查询或越权查询 |
| 执行顺序 | 校验、查询、状态判断、调用外部系统 | 调用顺序是否会导致脏数据、重复处理或错误暴露 |
| 风格一致 | 人工代码与 AI 代码的统一表达 | 是否出现同一规则多种写法、命名漂移或抽象不一致 |

这张表的价值在于，它把一次评审从“看代码细节”提升到“看系统边界”。代码细节当然重要，但业务系统更怕的是边界不清：该隔离的数据没有隔离，该抽象的模型没有抽象，该定制的差异又被混进了公共逻辑。

## 关键原理：Code Review 先看边界，再看实现

业务系统的 code review，第一层要看的不是某一行代码写得优不优雅，而是它放在系统里的位置是否正确。

### 1. 先看项目结构

项目结构能反映系统对业务的理解。一个新增能力如果放错了层，会带来两个问题：

- 后续维护者不知道这个逻辑属于通用能力还是特殊入口。
- 新需求复用时容易误用，把定制逻辑扩散到其他业务。

例如第三方对接相关的适配逻辑，通常应该和内部交易模型之间有一层边界。外部字段、外部状态、外部接口异常，不应该直接污染内部通用的交易流程。否则后面接入第二个第三方时，很容易出现“为了兼容 A，又影响了 B”的问题。

### 2. 区分定制化逻辑和内部抽象

这个项目的特殊点在于：它对接第三方系统，但内部又抽象了一套自己的在线交易业务模式。

所以 review 时不能只问“这个第三方接口能不能用”，还要问：

- 这段逻辑是第三方定制逻辑，还是内部业务规则？
- 这个业务类型是外部传入的识别条件，还是内部交易模型的稳定分类？
- 当前查询条件是在保护第三方数据范围，还是在限制内部通用能力？
- 后续新增第三方时，这段代码是复用、扩展，还是需要复制一份？

定制化逻辑并不是不能写，关键是要写在正确的边界内。对第三方的适配可以定制，但内部交易模型要尽量稳定；外部差异可以转换，但不要让差异穿透到所有业务层。

### 3. 接口名字和注释要对得上业务语义

接口名字和注释不是装饰，它们是 review 的第一层业务契约。

如果方法名叫 `queryOnlineTradeOrder`，但实际查询范围包含其他业务模式，这就是危险信号。如果注释写的是“查询当前业务类型订单”，但 SQL 没有带业务类型条件，这就不只是注释不准，而是可能存在数据安全问题。

好的命名至少要回答三个问题：

- 查什么对象。
- 按什么业务范围查。
- 返回结果是否已经做过权限或业务类型隔离。

对于对接第三方的接口，名字里如果能体现业务边界，会比笼统的 `queryOrderList` 更安全。例如：

```java
List<OrderDTO> queryThirdPartyOnlineTradeOrders(OrderQuery query);
```

这类名字不一定是最终标准，但它提醒维护者：这不是一个任意订单查询接口，而是有第三方、在线交易、订单范围三层含义。

### 4. 内部调用方式要符合分层习惯

领导关注 `Service` 调 `Service`，还是 `Service` 调 `Manager`，本质上是在看项目内部的职责边界。

常见分层可以粗略理解为：

| 层次 | 更适合承载的职责 |
| --- | --- |
| `Controller` | 参数接收、入口鉴权、返回结果封装 |
| `Service` | 应用流程编排、事务边界、业务用例 |
| `Manager` | 领域对象操作、外部系统适配、可复用业务能力 |
| `Repository/Mapper` | 数据访问 |

不同项目命名可能不同，但 review 时要看的是“调用关系是否稳定”。如果同一类逻辑有的地方走 `Service`，有的地方绕过 `Service` 直接调 `Mapper`，还有的地方把外部系统调用写进多个业务层，后面排查问题会很痛苦。

分层不是为了形式好看，而是为了让调用顺序、事务范围、异常处理和复用边界可以被预测。

## 查询安全：第三方对接场景的底线

这次 review 里最需要沉淀的一点，是查询条件不能只满足功能，还要满足数据边界。

第三方系统来查订单时，接口不能只根据订单号、公司 ID、时间范围这类通用条件查询。因为这些条件可能无法区分业务类型，最终导致第三方查到不属于它的订单。

更稳妥的检查方式是：

1. 查询入口是否明确第三方身份或来源。
2. 查询条件是否带上业务类型、业务模式或绑定关系。
3. SQL 是否存在空条件放行、默认全量查询。
4. 分页是否强制存在，是否限制最大页大小。
5. 返回字段是否只包含第三方需要的数据。
6. 异常或空结果是否会泄露其他业务信息。

尤其要警惕这种写法：

```java
if (query.getOrderCode() != null) {
    wrapper.eq(Order::getOrderCode, query.getOrderCode());
}
return orderMapper.selectList(wrapper);
```

如果没有业务类型、第三方绑定关系或数据权限条件，一旦请求参数为空或条件不足，就可能变成风险查询。对外接口的查询条件应该先收紧边界，再叠加筛选条件。

## 调用顺序：业务逻辑不是代码堆叠

业务代码的调用顺序也需要 review。很多问题不是某个方法错了，而是顺序错了。

一个对接第三方的查询或处理流程，通常应该先做边界判断，再做数据查询，最后做业务处理：

```text
入口参数校验
-> 第三方身份或来源识别
-> 业务类型/业务模式边界确认
-> 查询当前边界内的数据
-> 状态与权限二次判断
-> 返回脱敏后的结果或继续业务处理
```

如果顺序反过来，先查数据再判断业务类型，就算最后过滤掉了不该返回的数据，也已经让系统执行了一次不安全的访问路径。对于高风险业务，review 时要关注的不只是最终返回结果，还要关注中间过程是否越界。

## 团队并行开发与 AI 代码的一致性

领导在意编码风格，其实不是单纯追求“看起来一样”。真正的问题是：风格不一致会让业务规则变得不一致。

团队并行开发时，常见问题包括：

- 同一个业务类型在不同地方使用不同枚举、字符串或判断方式。
- 同一个查询边界，有的地方按第三方来源过滤，有的地方按业务模式过滤。
- 方法命名一会儿强调外部系统，一会儿强调内部模型。
- AI 生成代码为了“通用”抽了过大的方法，反而模糊了业务差异。
- AI 生成代码为了“快速完成”复制已有逻辑，导致新旧分支看似相似但边界不同。

所以 code review 要把“风格”具体化成可检查的规则：

- 业务类型使用统一枚举或统一常量。
- 第三方边界判断集中在固定入口或固定适配层。
- 查询条件必须显式包含业务范围。
- 方法命名优先表达业务语义，而不是只表达技术动作。
- 简单业务判断可以保留在主流程附近，避免为了抽象而抽象。
- AI 生成代码必须重新按项目分层、命名、查询安全和调用顺序审一遍。

## AI 编码后的结构复盘

还有一点是我自己在写代码时遗漏过的：现在越来越多时候会使用 AI 辅助编码。AI 把代码写完之后，我们很容易把注意力放在局部结果上，比如业务逻辑是否正确、当前修改点是否能跑通、某个判断条件是否补上了。

这些检查当然重要，但它们更多验证的是“局部正确”。真正容易被忽略的是“全局结构是否仍然正确”：

- 新代码是否放在了正确的模块和层级。
- AI 生成的通用方法是否真的符合项目已有抽象。
- 局部修复是否绕过了原来的业务入口或调用顺序。
- 新增查询是否遵守了全局的数据边界和业务类型约束。
- 同一类业务规则是否被 AI 写出了另一套表达方式。

这个问题的解决方式，我现在理解大概有两种。

第一种是**设计先行**：在编码前先定好结构，包括模块归属、调用层级、查询边界、业务类型表达方式和扩展点。这样 AI 生成代码时有明确约束，后续 review 的重点就是检查实现有没有偏离设计。

第二种是**开发先行**：先让业务逻辑跑通，确认核心流程、边界条件和数据结果是正确的；等业务正确后，再专门做一次结构调整，只处理分层、命名、抽象边界和重复表达，不在这一轮继续扩业务逻辑。

这两种方式没有绝对优劣，取决于当前项目阶段：

| 开发方式 | 适用场景 | Review 重点 |
| --- | --- | --- |
| 设计先行 | 业务边界清楚、多人并行、影响范围较大 | 结构是否按设计落地，是否越过既定边界 |
| 开发先行 | 需求仍在摸索、流程需要快速验证、局部试错成本低 | 业务正确后是否补做结构复盘，是否收敛临时代码 |

关键是不能只停在“业务能跑”。如果是设计先行，review 要检查代码有没有遵守设计；如果是开发先行，review 后半段就要主动切换视角，从业务正确性转到结构正确性。否则 AI 辅助编码越快，局部修改越多，项目整体结构反而越容易变散。

## 更多思考

- **Code Review 不是只抓问题，而是统一业务表达。** 评审时要把“为什么这样写”讲清楚，否则团队成员下次还是会按各自习惯写。
- **第三方对接要同时防止两种极端。** 一种是过度定制，导致内部模型被外部系统绑架；另一种是过度抽象，导致第三方数据边界被弱化。
- **查询接口要默认不信任输入。** 对外查询不能因为参数缺失就放宽条件，应该在条件不足时拒绝或返回空结果。
- **命名、注释、SQL 条件要互相校验。** 名字说“当前业务”，注释说“第三方订单”，SQL 却没业务类型条件，这种不一致就是 review 信号。
- **AI 代码要重点审边界。** AI 很容易写出语法正确、结构完整、但业务边界含糊的代码。越是看起来整齐，越要确认它是否符合项目里的真实业务模型。
- **业务正确之后还要复盘结构。** AI 编码容易让我们只关注当前修改点是否正确，但 code review 还要补一轮全局视角，确认模块、分层、抽象和调用方式没有被局部改动带偏。

## Code Review 检查清单

后续类似项目可以按这张清单快速过一遍：

| 检查项 | Review 问题 |
| --- | --- |
| 项目结构 | 新代码是否放在正确模块，是否符合已有分层 |
| 定制边界 | 第三方定制逻辑是否被限制在适配边界内 |
| 内部抽象 | 是否保留了系统自己的在线交易业务模型 |
| 接口命名 | 方法名、接口名是否准确表达查询范围和业务类型 |
| 注释一致 | 注释描述是否和实际代码、SQL 条件一致 |
| 调用关系 | `Service`、`Manager`、`Mapper` 的调用是否符合项目习惯 |
| 查询条件 | 是否存在全量查询、无条件查询、空条件放行 |
| 数据安全 | 第三方是否只能查到当前业务类型下的数据 |
| 调用顺序 | 是否先校验边界，再查询和处理 |
| 风格统一 | 同一业务规则是否只有一种表达方式 |
| AI 代码 | 是否重新审过分层、命名、边界、查询和异常处理 |
| 结构复盘 | 业务跑通后，是否单独检查过模块、分层、抽象和调用顺序 |

## 总结

这次 code review 给我的启发是：

1. 业务系统的评审要先看结构和边界，再看代码细节。
2. 第三方对接场景里，查询安全是底线，不能出现全量查询、无条件查询或业务类型缺失。
3. 定制化逻辑要被隔离，内部抽象也要被保护，不能让外部系统直接污染内部交易模型。
4. 接口名字、注释、SQL 条件和调用顺序要互相印证，任何不一致都值得停下来确认。
5. AI 辅助编码后不能只看局部业务正确，还要补一轮全局结构复盘。
6. 团队并行开发和 AI 辅助编码都会放大风格差异，code review 要把风格问题转化成可执行的业务规则。

我以前容易把 code review 理解成“检查代码有没有问题”。这次之后更清楚地意识到，真正有价值的 review 是在统一团队对业务边界、系统结构和代码表达的理解。代码最终会变，但这些判断标准应该沉淀下来，成为后续开发可以复用的规范。
