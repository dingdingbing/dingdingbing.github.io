# 复杂提货链路设计与排查复盘

## 场景：一条提货链路牵动多侧数据

在某交易链路中，一次提货会同时影响订单履约、采购侧记录、销售侧记录、实提确认、结算准备和库存占用。业务上希望前台看到的是一个“提货完成”的动作，但系统内部实际会拆成多次写入、多次状态流转和若干异步补偿。

这类链路的问题通常不是单个接口报错，而是过一段时间后暴露为“某侧已完成、另一侧未同步”“数量重量对不上”“后续结算无法继续”。如果只看报错点，很容易误判成数据偶发异常。

## 我的职责与边界

- 梳理订单、提货申请、实提记录、结算准备记录之间的关联关系。
- 还原采购侧与销售侧的同步路径，标记同步前置条件和失败补偿点。
- 参与异常数据排查，设计核对口径和修复步骤。
- 把排查经验沉淀成可复用的链路检查清单，避免每次从零开始查表。

我刻意没有把所有历史分支重构成统一模型，因为部分分支仍承载存量数据。更稳妥的方式是先明确主链路，再在边界处补齐校验和可观测证据。

## 关键约束

- 链路长：一次问题可能跨越入口、同步任务、状态机和后续结算。
- 状态多：同一个业务动作在不同阶段可能对应不同状态字段。
- 数据要求严格：数量、重量、金额口径和关联关系必须能相互解释。
- 修复窗口有限：异常修复不能影响已经正常推进的业务记录。

## 方法：先建对象地图，再查差异点

我会先用业务单号定位主链路，把每个对象放到同一张排查表里：

| 对象 | 需要确认的证据 | 判断目的 |
| --- | --- | --- |
| 订单记录 | 业务状态、数量重量、创建时间 | 确认入口动作是否成立 |
| 提货申请 | 申请状态、审批结果、关联单号 | 确认流程是否进入实提阶段 |
| 采购侧实提 | 实提数量、重量、关联关系 | 确认采购侧是否完整落库 |
| 销售侧实提 | 同步来源、数量重量、状态 | 确认销售侧是否跟随采购侧 |
| 结算准备 | 结算状态、引用记录 | 确认后续流程是否可推进 |

排查时不先下结论，而是按“创建是否成功、同步是否触发、状态是否推进、补偿是否执行”的顺序收集证据。这样可以把模糊的链路问题压缩成几个可验证的断点。

## 取舍：不急着做大一统抽象

这条链路里有普通模式、特殊模式和历史兼容路径。把所有分支强行抽成同一个流程图，短期看代码更整齐，长期可能掩盖业务差异。

我的取舍是：

- 主流程保持直读，关键判断写在靠近业务入口的位置。
- 同步和补偿逻辑使用同一套核对口径，避免修复侧和运行侧判断不一致。
- 对历史分支只补证据和边界保护，不在没有完整回归条件时做大范围重写。
- 把“对象关系”和“状态推进条件”写入文档，帮助后续排查快速定位。

## 验证与结果

修复或补偿前后，我会重新核对同一批样本：

- 采购侧与销售侧的数量、重量是否一致。
- 关键关联 ID 是否成对存在。
- 状态推进时间是否符合链路顺序。
- 后续结算准备是否能继续处理。
- 是否出现重复实提或孤立记录。

这种方式的结果不是简单地“改好一条数据”，而是形成了可以复查的证据链。后续遇到类似问题时，可以直接复用对象地图和核对顺序，把排查范围从全链路缩小到具体断点。

## 复盘沉淀

复杂提货链路最怕凭经验直接改数据。更可靠的处理方式是先还原业务对象之间的关系，再用字段、状态和时间证据确认每一步是否成立。只要链路证据完整，代码修复、补偿任务和人工处理都能有清晰边界。
