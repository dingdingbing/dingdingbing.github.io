# 下游接口请求超时导致数据丢失的复盘

## 场景

这次问题发生在一次 MQ 消息消费链路中。

我们的消费逻辑不是单一步骤，而是一次消费过程中会串行调用多个下游接口。正常情况下，消息消费后会依次完成订单相关状态处理、日志保存以及后续业务数据更新。但这次线上出现了数据缺失：某些后续接口没有执行，导致业务数据没有完整落库。

最开始看到的现象并不直观。监听端日志里只有比较笼统的错误文案，类似“创建合同订单日志失败”或“调用日志服务失败”，并且多个 catch 打印的是相似文案，缺少明确的业务单号、当前处理步骤、下游服务名、调用耗时和异常类型。单看应用日志，很难第一时间判断到底是哪个环节失败，也看不出为什么后续流程没有继续执行。

后续结合日志时间线和异常栈，发现消费链路中有一步会调用日志服务：

```text
MQ 消费消息
  -> 执行业务处理
  -> 调用日志服务保存业务日志
  -> 继续执行后续业务接口
```

日志服务内部会将业务日志写入 Elasticsearch。事故发生时，这个日志保存接口没有及时返回，最终触发了调用方配置的 20 秒 TimeLimiter 超时。由于日志保存发生在同步主流程中，超时异常导致后续接口没有继续执行，最终出现数据缺失。

当时调用方看到的异常类似：

```text
TimeLimiter 'BusinessStatusLogApi#saveBusinessLog(BusinessLogSaveParam)'
recorded a timeout exception.
```

日志服务侧还能看到 ES 写入失败和线程池拒绝相关异常：

```text
ElasticsearchStatusException:
type=es_rejected_execution_exception,
reason=rejected execution of processing ...

EsThreadPoolExecutor[
  name = HC_BANKSTEEL_BASE_ES06/write,
  queue capacity = 200,
  pool size = 28,
  active threads = 28,
  queued tasks = 252
]
```

进一步找运维同事确认后，发现事故时间段 ES 所在物理机磁盘 IO 达到 100%，并且断断续续持续了将近 50 分钟，大约从早上 8:40 开始。期间还发生过重启，导致内存队列中的部分任务丢失。

后续运维又补充了更明确的信息：当时运营侧有大量高频业务查询，查询了两个 ES 索引，其中一个慢日志里能看到 `user_notify_log`。这些查询的时间范围从 2018 年开始查，时间跨度很大，单次查询也比较慢。虽然这些请求是查询操作，不是写操作，但 ES 查询和写入共享同一批底层磁盘 IO、CPU、JVM heap 和文件系统缓存。当大量查询把物理机磁盘 IO 打满后，同集群内其他索引的写入也会被拖慢。

当时 ES slowlog 中有类似日志：

```text
[2026-06-08T09:01:00,998][WARN ][i.s.s.fetch] [HC_BANKSTEEL_BASE_ES06]
[user_notify_log][4] took[3.7s], took_millis[3700], total_hits[143 hits],
search_type[QUERY_THEN_FETCH],
source[{"size":1000,"query":{"bool":{"filter":[
  {"term":{"userId":{"value":139097}}},
  {"term":{"userType":{"value":2}}},
  {"term":{"status":{"value":3}}},
  {"term":{"channel":{"value":5}}}
]}},"_source":false}]
```

这条日志透露出几个信息：

- 慢查询发生在 `HC_BANKSTEEL_BASE_ES06` 节点上的 `user_notify_log` 索引分片；
- 日志类型是 search slowlog 的 fetch 阶段，单次查询耗时已经达到 3.7s；
- 查询条件本身是 `userId`、`userType`、`status`、`channel` 的精确过滤；
- 单次命中数并不大，但 `size=1000`，再叠加高频、大时间范围、多索引查询，就会持续制造磁盘 IO 压力；
- 查询和写入虽然不是同一个 ES 线程池，但会争抢同一套底层资源，所以慢查询可以间接拖慢写入。

所以这次问题的完整链路可以归纳为：

```text
运营侧对两个 ES 索引发起高频、大时间范围查询
  -> 查询从 2018 年开始查，单次查询慢且持续打到 ES 集群
  -> ES 物理机磁盘 IO 长时间达到 100%
  -> ES write 线程池 active 打满、队列堆积、部分请求 rejected
  -> 日志服务同步写 ES 变慢或失败
  -> 业务消费链路同步调用日志服务，等待返回
  -> 调用方 TimeLimiter 等满 20 秒后超时
  -> 后续业务接口没有继续执行
  -> 消费异常被 catch 后没有形成有效重试/补偿
  -> 最终出现业务数据缺失
```

这次事故最容易误判的点是：一开始看到的是“日志服务失败”和“ES rejected”，但真正影响业务结果的不是日志本身丢失，而是**日志这个辅助能力被放在了同步主链路中，导致下游基础设施故障向上传播，阻断了后续业务处理**。

## 当时的解决方式

### 1. 先从业务现象反推消费链路

最开始不是直接看 ES，而是先确认业务缺失的数据是在哪个流程里产生的。因为消费方法中存在多个接口调用，所以需要先还原一次消息消费后的完整调用链。

排查时重点看了几个问题：

- 这条消息消费后应该执行哪些步骤；
- 哪一步之前的数据是完整的；
- 哪一步之后的数据开始缺失；
- 日志中的错误时间点和业务数据缺失时间是否能对上；
- 消费方法异常后到底是抛出、重试、进死信，还是被 catch 后吞掉。

这一步把问题从“数据为什么没了”收敛成了“消费链路在调用日志服务后没有继续执行”。

### 2. 根据时间线定位到日志服务调用超时

由于应用日志不够清晰，排查中比较依赖时间线。

大致时间线是：

```text
消费消息开始
  -> 前置业务步骤执行
  -> 调用日志服务 saveBusinessLog
  -> 等待约 20 秒
  -> TimeLimiter 抛出 timeout exception
  -> 后续接口没有执行
```

这里的关键点是：20 秒不是 ES 线程池的拒绝策略导致的等待，而是调用方的超时控制。调用方通过 Feign/CircuitBreaker/TimeLimiter 调用日志服务，远程接口迟迟没有返回，最终由 TimeLimiter 在 20 秒后抛出超时异常。

### 3. 继续追到日志服务和 ES 写入

日志服务内部将业务日志写入 ES。当时 ES 返回了 `es_rejected_execution_exception`，并且异常信息中暴露了 write 线程池状态：

```text
queue capacity = 200
pool size = 28
active threads = 28
queued tasks = 252
```

这说明当时 ES 节点的写入线程已经全部忙碌，队列也发生了堆积。这里要注意一个细节：

```text
已经进入队列的写入任务不会立刻失败，而是等待 worker 线程执行；
后续再来的请求，如果线程池和队列都满了，才会立刻 rejected。
```

所以会出现一种现象：

```text
早一点进入 ES write queue 的请求：一直排队等待，直到上游 20 秒超时；
晚一点进入的请求：队列已经满了，直接返回 rejected。
```

这也解释了为什么某些日志没有立刻失败，而是把业务线程拖到超时。

### 4. 找运维确认 ES 物理机状态

仅靠业务日志和 ES rejected，只能证明 ES 写入线程池发生过拥塞，但不能证明为什么拥塞。

后续找运维查看事故时间段监控，确认 ES 物理机磁盘 IO 达到 100%，并且持续接近 50 分钟。这个信息把问题进一步落到了基础设施层：

```text
ES 写入变慢不是单个业务接口代码异常，
而是 ES 集群底层 IO 长时间打满，导致写入能力下降。
```

一开始只能确认“ES 集群 IO 很高”，还不能确定具体业务来源。后续运维进一步确认，当时运营侧有大量高频查询打到两个 ES 索引，查询时间范围从 2018 年开始，查询跨度大、频率高、单次查询也偏慢，最终把共享磁盘 IO 打满。

同时运维侧也确认期间发生过重启，队列中的部分任务因此丢失。

### 5. 梳理 MQ 消费异常语义

这次还顺带确认了 RabbitMQ 消费异常处理逻辑。

配置中有：

```yaml
rabbitmq:
  listener:
    type: simple
    simple:
      default-requeue-rejected: false
```

这个配置的含义是：如果消费方法抛出异常，Spring AMQP 会 reject/nack 当前消息，并且 `requeue=false`。

最终消息去向取决于队列是否配置了 DLX：

```text
消费方法抛异常 + 原队列配置 DLX
  -> 消息进入死信交换机，再路由到死信队列

消费方法抛异常 + 原队列没有配置 DLX
  -> 消息被丢弃

消费方法 catch 异常后不再抛出
  -> 容器认为消费成功，正常 ack，不会重试，也不会进死信
```

而这次比较危险的地方在于：消费逻辑中存在 catch，且死信队列基本没有被运营起来。也就是说，即使消息处理不完整，如果异常被吞掉，MQ 也可能认为这条消息已经成功消费。

## 关键原理

### ES write 线程池为什么会排队等待

ES 的写入请求不是每来一个都无限创建线程处理，而是进入固定大小的 write 线程池。

以当时异常信息为例：

```text
pool size = 28
queue capacity = 200
```

它的行为类似 Java 中的固定线程池加有界队列：

```java
new ThreadPoolExecutor(
    28,
    28,
    0,
    TimeUnit.MILLISECONDS,
    new ArrayBlockingQueue<>(200),
    new AbortPolicy()
);
```

提交任务时大致分三种情况：

```text
write 线程未满：直接执行；
write 线程已满但队列未满：进入队列等待；
write 线程已满且队列已满：触发拒绝，抛 es_rejected_execution_exception。
```

所以 ES 的 rejected 是“队列满之后的新请求被拒绝”，而不是“所有慢请求都会立刻失败”。

已经进入队列的请求，需要等待前面的 write worker 释放出来。如果底层磁盘 IO 打满，前面的写入任务执行很慢，后面的任务就会一直排队。

### ES 查询为什么会影响写入

ES 的查询和写入并不是完全使用同一个线程池。通常可以简化理解为：

```text
查询请求：主要走 search / fetch 相关线程池；
写入请求：主要走 write 线程池；
底层资源：共享 CPU、磁盘 IO、JVM heap、文件系统缓存和节点网络。
```

所以运营侧大量查询两个索引时，不一定是直接占满 `write` 线程池。但这些查询会持续读取大量 segment 数据，抢占磁盘 IO 和文件系统缓存。当磁盘 IO 达到 100% 后，写入线程在执行 translog、flush、merge、segment 写入等动作时也会变慢。

也就是说，查询影响写入不是因为“查询线程池等于写入线程池”，而是因为：

```text
高频查询
  -> 大范围扫描历史数据
  -> 磁盘读 IO 打满
  -> 写入时需要的磁盘 IO 也变慢
  -> write worker 长时间释放不了
  -> write queue 堆积
  -> 上游日志接口等待超时
```

这和 MySQL 慢查询拖垮接口很像。MySQL 中慢 SQL 会长时间占用连接、数据库执行线程、锁和磁盘 IO，导致后续请求在连接池或数据库侧排队，最终超过上游接口超时时间。ES 也是同样的资源模型：它查询很快是有前提的，如果查询范围很大、频率很高、数据不在缓存里，或者磁盘 IO 已经被打满，ES 也会出现慢查询。

### 为什么会等待 20 秒

20 秒不是 ES 的队列等待时间，也不是 ES 的拒绝策略。

它来自调用方的超时控制：

```text
业务应用调用日志服务
  -> Feign/CircuitBreaker/TimeLimiter 包装远程调用
  -> 日志服务同步写 ES，迟迟不返回
  -> 调用方等待 Future 返回
  -> 20 秒后 TimeLimiter 超时
```

所以 `catch` 不能解决这个问题。因为 catch 只能捕获已经抛出的异常，如果线程卡在远程调用或 ES 客户端等待响应上，异常还没有抛出来，catch 就没有机会执行。

### 为什么日志服务会影响主业务

日志保存本来是辅助能力，但它被放在了同步主流程中：

```text
核心业务步骤 A
  -> 同步保存业务日志
  -> 核心业务步骤 B
```

一旦日志服务变慢或不可用，主业务线程就会被日志调用拖住。这个设计的问题在于：

```text
日志失败不应该改变核心业务结果；
日志慢也不应该阻断后续业务步骤；
ES 属于下游基础设施，故障不可避免，调用方必须做隔离。
```

这次事故本质上就是辅助链路缺少降级隔离，导致下游 ES 故障扩大成业务数据缺失。

### DLX 不是消费时临时决定的

RabbitMQ 的死信交换机是队列级别配置，不是消费者运行时临时指定。

需要查看原业务队列是否有类似参数：

```text
x-dead-letter-exchange
x-dead-letter-routing-key
```

可以通过 RabbitMQ 管理后台或命令查看：

```bash
rabbitmqctl list_queues name arguments
```

如果只是在项目配置文件里写了：

```yaml
dead-letter:
  exchange: xxx.dlx
  queue: xxx.dead-letter
  routing-key: xxx.dead-letter
```

还不能证明队列真的配置了 DLX。最终要看队列实际 arguments，或者看代码是否用 `QueueBuilder.deadLetterExchange(...)`、`@QueueBinding` 等方式声明了死信参数。

## 更多思考

### 1. 调用方能做什么

这次 ES 集群 IO 打满、节点重启，不是业务调用方能直接修复的问题。但调用方可以控制故障传播范围。

比较合理的改造方向是：

```text
日志保存异步化；
日志调用短超时；
针对日志 Feign 接口单独配置超时时间；
日志失败降级，不阻断主流程；
日志线程池独立且有界；
关键业务步骤增加状态记录和补偿；
MQ 消费异常不要简单 catch 后吞掉。
```

如果不想改动大量代码，最小的治理方式是先对日志 Feign 接口做单独超时配置，让这个非核心下游接口快速失败，避免复用全局默认超时时间。

例如全局 Feign 配置是：

```yaml
feign:
  client:
    config:
      default:
        connect-timeout: 15000
        read-timeout: 30000
      businessStatusLogApi:
        connect-timeout: 3000
        read-timeout: 30000
```

这里的含义是：

```text
default.connect-timeout = 15000ms：默认建连最多等 15 秒；
default.read-timeout = 30000ms：默认读取响应最多等 30 秒；
businessStatusLogApi.connect-timeout = 3000ms：日志接口建连最多等 3 秒；
businessStatusLogApi.read-timeout = 30000ms：日志接口读取响应仍然最多等 30 秒。
```

这个配置已经把日志接口的建连等待从 15 秒降到了 3 秒，对“连不上下游”的场景有帮助。但这次事故里更核心的问题是：日志服务已经接收到请求，但同步写 ES 迟迟不返回，调用方卡在读取响应阶段。因此如果目标是避免主流程被日志接口拖住，`read-timeout` 也应该针对 `businessStatusLogApi` 单独压低，并且要小于外层 TimeLimiter 的 20 秒。

更符合快速失败目标的配置形态是：

```yaml
feign:
  client:
    config:
      default:
        connect-timeout: 15000
        read-timeout: 30000
      businessStatusLogApi:
        connect-timeout: 1000
        read-timeout: 2000
```

这里的取值不是固定标准，具体要结合日志接口正常耗时来定。原则是：

```text
日志接口是辅助能力，超时时间应该短于核心业务接口；
日志接口超时后只能降级记录，不能阻断后续业务步骤；
Feign read-timeout 要和 Resilience4j TimeLimiter、业务方法 catch 策略一起看；
如果 read-timeout 仍然是 30 秒，而 TimeLimiter 是 20 秒，最终还是会由 TimeLimiter 在 20 秒时打断主流程。
```

更强的落地方案是把日志调用从同步主链路中拆出去：

```java
try {
    businessLogExecutor.execute(() -> {
        try {
            businessStatusLogApi.saveBusinessLog(param);
        } catch (Exception e) {
            log.warn("保存业务日志失败, orderCode={}", orderCode, e);
        }
    });
} catch (RejectedExecutionException e) {
    log.warn("日志异步线程池已满，丢弃日志任务, orderCode={}", orderCode, e);
}
```

这里不建议直接使用无界线程池，也不建议使用 `CallerRunsPolicy`。因为 `CallerRunsPolicy` 会把压力重新打回消费线程，主流程仍然可能被拖慢。

日志这种非核心能力更适合：

```text
独立线程池
有界队列
AbortPolicy + catch
或者自定义拒绝策略并记录指标
```

更彻底的方案是日志 MQ 化：

```text
业务消费链路
  -> 完成核心业务处理
  -> 投递日志事件
  -> 日志服务异步消费并写 ES
```

这样 ES 故障时影响的是日志积压，而不是订单主流程。

### 2. 消费链路要有步骤状态

这次数据缺失暴露出另一个问题：一次消费中串行调用多个接口，如果中间步骤失败，系统需要知道处理到了哪一步。

可以考虑为关键业务步骤增加处理状态：

```text
消息已接收
业务步骤 A 已完成
日志事件已投递
业务步骤 B 已完成
业务步骤 C 已完成
消费完成
```

这样即使中间失败，也能通过补偿任务识别：

```text
哪些消息没有处理完；
卡在哪一步；
是否可以重放；
是否需要人工介入。
```

这比单纯依赖一条消费日志可靠得多。

### 3. 死信队列要能运营

死信队列不是“配置了就算完成”。它至少需要：

```text
有告警；
能查询；
能看到失败原因；
能按业务单号检索；
能人工重放；
能避免重复处理；
能区分可重试和不可重试错误。
```

否则死信队列只是另一个没人看的垃圾桶。

### 4. 日志要为排查服务

这次排查困难，很大程度来自日志信息不完整。

以后类似消费链路，日志至少要包含：

```text
messageId
businessCode / orderCode
traceId
当前处理步骤
下游服务名
调用入参摘要
调用耗时
异常类型
异常 message
是否会继续后续流程
是否 ack / retry / dead-letter
```

尤其是 catch 里的日志，不能所有异常都打印同一句话。否则排查时只能靠时间猜。

### 5. 面试中如何讲这次经历

这次经历适合在面试中体现三个能力：

第一，排查问题不是只看最后一个异常，而是会还原完整链路：

```text
我先从数据缺失反推 MQ 消费链路，确认一次消费中有哪些同步接口调用，再通过时间线定位到日志服务调用后流程中断。
```

第二，能区分超时、拒绝和排队：

```text
ES rejected 说明写入线程池发生过拥塞，但 20 秒超时不是 ES 拒绝策略，而是调用方 TimeLimiter 等远程接口返回。已经进入 ES write queue 的请求不会立刻失败，而是等待 worker 线程执行。
```

第三，能给出架构改进，而不是只停留在“ES 挂了”：

```text
最终确认运营侧高频查询两个 ES 索引，并且从 2018 年开始做大范围查询，导致 ES 物理机磁盘 IO 长时间打满并发生重启。这不是业务应用能直接解决的。但业务侧的问题是把日志这种辅助能力放在了同步主链路中。后续应该通过异步化、短超时、降级、独立线程池、补偿状态和死信运营，避免下游故障扩大成主流程数据缺失。
```

如果面试官追问“你具体能做什么”，可以这样回答：

```text
短期我会把日志调用从主链路拆出去，使用独立有界线程池异步处理，日志失败只记录告警，不阻断后续业务。

中期我会为消费链路补充步骤状态和补偿任务，避免中间步骤失败后只能依赖人工查日志。

长期我会推动日志服务改成 MQ/Outbox 异步写 ES，并补齐 ES write queue、rejected、磁盘 IO、GC、日志服务接口耗时等监控告警。
```

## 总结

这次事故可以提炼成几个结论：

- 超时异常通常不是根因，它只是“等待失败”的结果。排查时要追问这 20 秒里调用方在等谁。
- ES 的 write 线程池是固定线程池加有界队列。已经进入队列的任务会等待 worker 执行，队列满之后的新任务才会被 rejected。
- ES 查询和写入不是同一个线程池，但会共享磁盘 IO、CPU、JVM heap 和文件系统缓存。高频、大范围慢查询可以间接拖慢写入。
- 日志、通知、埋点这类辅助能力不能轻易放进同步主链路，更不能因为它们失败而阻断核心业务。
- MQ 消费异常要明确最终语义：是 ack、重试、死信，还是被 catch 后吞掉。
- 跨应用问题排查要建立共同时间线，标出每一步的同步等待点、超时边界和失败传播路径。
- 基础设施故障不可完全避免，业务系统要通过隔离、降级、补偿和可观测性控制影响面。

如果把这次经历压缩成一句面试表达，可以这样说：

> 这次问题最终定位到运营侧对两个 ES 索引发起高频、大时间范围查询，查询从 2018 年开始，导致 ES 集群磁盘 IO 长时间打满并发生重启，进而拖慢日志服务写入 ES；业务侧真正的问题是日志这种辅助链路同步阻塞了 MQ 消费主流程。我的排查思路是先还原消费调用链和时间线，再区分 TimeLimiter 超时、ES write 队列排队和 rejected 的关系，最后把改进点落到异步降级、步骤补偿、死信运营和监控告警上。
