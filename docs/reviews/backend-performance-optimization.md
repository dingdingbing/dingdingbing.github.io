# 深分页&慢SQL&JVM&线程池优化

## 主问题

如果线上接口慢、吞吐上不去，常见性能优化场景有哪些？比如深分页怎么优化？慢 SQL 怎么优化？JVM 参数怎么调整？还有哪些容易被忽略的优化点？

这个问题的重点不是背优化清单，而是先定位瓶颈，再选择对应优化手段。没有证据直接优化，很容易把问题从一层转移到另一层。

## 直觉答案

第一反应可能是：

- SQL 慢就加索引。
- 深分页就改成游标分页。
- JVM 慢就调大堆内存。
- Redis 能缓存就加缓存。
- Tomcat 线程数调大一点。

这些都可能有效，但都需要条件。比如索引加错了可能让写入变慢，游标分页不适合任意跳页，调大堆可能让 Full GC 更久，缓存可能带来一致性问题，线程数调大可能把数据库打爆。

## 优化前先定位

性能优化前先回答四个问题：

1. 慢在哪里：入口、RPC、Redis、MQ、MySQL、JVM、网络，还是锁？
2. 慢到什么程度：平均耗时、P95、P99、错误率、超时率分别是多少？
3. 哪个资源先到上限：CPU、内存、GC、线程池、连接池、队列、磁盘 IO、网络？
4. 优化目标是什么：降低 P99、提高吞吐、减少数据库压力、降低资源成本，还是提高稳定性？

如果没有定位，优化动作很可能变成“凭经验改参数”。

## 深分页优化

### 问题现象

典型 SQL：

```sql
select *
from order_record
where status = 1
order by id desc
limit 100000, 20;
```

MySQL 需要先找到并跳过前 100000 条，再返回 20 条。偏移量越大，扫描和丢弃的行越多。

### 优化方式

### 1. 游标分页

如果业务只需要“下一页”，可以用上一页最后一条记录作为游标：

```sql
select *
from order_record
where status = 1
  and id < #{lastId}
order by id desc
limit 20;
```

优点：

- 不需要跳过大量数据。
- 性能稳定，页数越深优势越明显。

限制：

- 不适合任意跳到第 N 页。
- 排序字段要稳定，最好有唯一递增或组合唯一条件。

### 2. 延迟关联

先用覆盖索引查出主键，再回表查详情：

```sql
select *
from order_record o
join (
  select id
  from order_record
  where status = 1
  order by id desc
  limit 100000, 20
) t on o.id = t.id;
```

优点：

- 减少深分页时回表和大字段读取。

限制：

- 仍然有 offset 成本，只是降低每行扫描代价。

### 3. 限制最大翻页深度

很多业务不需要无限翻页。可以限制最大页数，深层数据通过搜索条件缩小范围。

### 4. 搜索引擎或离线查询

如果是复杂检索、排序、筛选，可以考虑 Elasticsearch 或离线宽表。不要让 MySQL 承担不适合它的检索压力。

## 慢 SQL 优化

慢 SQL 优化一般按这个顺序：

1. 看慢 SQL 日志，确认真实 SQL、执行时间、扫描行数。
2. 用 `explain` 看执行计划。
3. 判断是否走索引，索引区分度是否足够。
4. 看返回行数和回表次数。
5. 看排序、分组、临时表、文件排序。
6. 看锁等待和事务持有时间。
7. 结合业务改查询方式，而不是只改 SQL。

常见优化点：

- 给高频过滤条件建立合适索引。
- 联合索引遵守最左前缀，区分度高的字段放前面要结合查询形态判断。
- 避免在索引列上使用函数、隐式类型转换、前置模糊匹配。
- 只查需要字段，避免 `select *`。
- 大列表查询必须分页。
- 循环查询改批量查询，避免 N+1。
- 大事务拆小，减少锁持有时间。
- 排序字段尽量利用索引，避免大范围 `filesort`。
- 读多写少场景可以考虑冗余字段、汇总表、缓存或读写分离。

一个容易被追问的点是：加索引不是越多越好。索引会增加写入成本、占用磁盘、影响优化器选择，也可能因为区分度低而收益有限。

## JVM 参数优化

JVM 参数优化不能脱离业务和 GC 日志。一般先看：

- 堆使用曲线。
- Young GC 频率和耗时。
- Full GC 次数和耗时。
- 对象分配速率。
- 老年代增长速度。
- 容器内存限制和 JVM 识别的内存。
- 是否有 OOM、频繁 GC、长时间 STW。

### 堆大小

堆太小：

- GC 频繁。
- 对象很快晋升老年代。
- 高峰期容易 OOM。

堆太大：

- 单次 Full GC 可能更久。
- 容器内存被堆挤占，非堆、线程栈、Direct Memory 空间不足。

常见思路是让堆大小和容器内存匹配，并预留非堆空间：

```text
容器内存
-> Java Heap
-> Metaspace
-> Direct Memory
-> Thread Stack
-> Code Cache
-> Native Memory
```

### GC 选择

Spring Boot 常见服务多用 G1。优化目标通常是降低停顿和稳定 P99，而不是只追求平均吞吐。

常见关注：

- `-Xms` 和 `-Xmx` 是否一致，避免运行时扩缩容抖动。
- `-XX:MaxGCPauseMillis` 是否合理。
- 年轻代是否过小导致 Young GC 频繁。
- 是否存在大对象直接进入老年代。
- 是否存在内存泄漏或无边界集合。

### 元空间和堆外内存

如果使用大量动态代理、字节码增强、反射、脚本、Netty、NIO，也要关注：

- `Metaspace`。
- `Direct Memory`。
- 线程数和线程栈。
- 容器 OOMKilled。

JVM 优化的底线是：参数只能缓解容量和停顿问题，不能修复业务代码无边界加载数据、连接泄漏、线程泄漏和缓存失控。

## 缓存优化

缓存优化不是“加 Redis”这么简单。

常见场景：

- 热点数据缓存，降低数据库 QPS。
- 本地缓存，减少 Redis 网络调用。
- 批量获取，减少多次 Redis 往返。
- 大 value 拆分，避免序列化和网络压力。
- 热 key 拆分或多级缓存，避免单点 key 压力。
- 合理过期时间，避免同一时间大批 key 过期。

要同时考虑：

- 缓存一致性。
- 缓存穿透、击穿、雪崩。
- 缓存内存占用。
- key 设计。
- 降级策略。

## 接口和线程池优化

常见优化点：

- 接口只返回必要字段，避免大 JSON。
- 批量接口代替循环远程调用。
- 慢操作异步化，但要配套 MQ 消费能力。
- 核心链路和非核心链路线程池隔离。
- 合理设置超时、限流、熔断、降级。
- 避免在事务里做远程调用。
- 避免锁粒度过大。

线程池优化要看任务类型：

- CPU 密集型：线程数接近 CPU 核心数。
- IO 密集型：可以更多，但要受下游连接池和限流控制。
- 混合型：最好隔离，不要一个线程池承载所有任务。

## 可验证结论

性能优化要用压测验证，不能只看上线后感觉。

可以这样验证：

1. 固定数据量和环境。
2. 记录优化前 QPS、P95、P99、错误率、CPU、GC、连接池、慢 SQL。
3. 每次只改一个变量。
4. 优化后重复同样压测。
5. 对比指标，确认收益和副作用。

## 面试表达版本

可以这样回答：

> 性能优化我会先定位瓶颈，再选手段。比如深分页，如果业务只需要下一页，我会优先用游标分页；如果要保留 offset，可以用覆盖索引加延迟关联降低回表成本，同时限制最大翻页深度。慢 SQL 我会先看慢日志和 explain，判断索引、扫描行数、回表、排序、临时表、锁等待，再决定是加联合索引、改写 SQL、减少返回字段、分页、批量查询，还是从业务上做缓存和汇总表。JVM 参数不会直接乱调，我会看 GC 日志、堆曲线、对象分配、Full GC 和容器内存，再调整堆大小、GC 目标、元空间和堆外内存。除此之外，还会看缓存、线程池、接口返回、远程调用、MQ 消费能力和限流降级。优化一定要压测验证，看 P99、吞吐、错误率和资源指标是否真的改善。
