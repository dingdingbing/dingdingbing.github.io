# Redis 面试复盘：缓存、分布式锁与高频追问

Redis 在项目里经常被当作缓存使用，但它不只是缓存。更准确地说，Redis 是一个基于内存的数据结构存储，常见场景包括缓存、分布式锁、计数器、排行榜、限流、会话、轻量消息和签到统计。

面试回答 Redis 时，不要只停留在“我用过 String、Hash、List、Set”。更稳的方式是围绕三个问题展开：

- Redis 用来解决什么业务问题。
- 每个方案解决哪一段风险。
- Redis 本身又会引入什么一致性边界。

## 错误示范：容易被追问的回答

> Redis 对我来说是一个缓存中间件，通常在项目中当缓存使用，其次可以用分布式锁。常用数据结构有 String、Hash、List、Set。String 保存字符串，Hash 存对象，List 用于一对多场景，Set 用于去重和排序。
>
> Redis 的 String 做了特殊处理，C 语言字符串需要遍历到 `\0` 才知道长度，Redis 使用 SDS，保留字符串长度字段和空闲字段，所以可以很快获取长度。
>
> 分布式锁基于 Lua 脚本实现，Lua 可以原子执行。加锁用 `setnx`，key 不存在就加锁，存在就等待或返回。解锁时要判断 value，保证加锁和解锁的是同一个线程。通常使用 RedLock。
>
> 缓存穿透是 Redis 中没有数据，导致大量无效请求跳过 Redis 访问数据库，可以用布隆过滤器。击穿是热点数据过期，大量请求打到数据库，可以给热点数据设置不同过期时间或永不过期。雪崩是大量 Redis 数据失效，可以分散过期时间。

这版回答有方向，但几个点不够严谨：

- Redis 不只是缓存，它是内存数据结构存储。
- Set 只负责去重，不负责排序；排序应该说 ZSet。
- List 不是“一对多场景”，更常见是队列、栈、最新列表。
- `SETNX` 不如 `SET key value NX PX` 严谨，因为加锁和设置过期时间应该在一条命令里完成。
- Lua 原子性不是因为“脚本天然原子”，而是 Redis 执行脚本期间不会穿插执行其他客户端命令。
- RedLock 不是默认答案，很多项目实际使用的是普通 Redis 锁或 Redisson `RLock`。
- 击穿和雪崩的解决方案容易混淆：热点 key 加互斥锁/逻辑过期更贴近击穿，TTL 随机化更贴近雪崩。

## Redis 常用数据结构

| 类型 | 特点 | 常见场景 |
| --- | --- | --- |
| String | 二进制安全字符串，也可以做整数自增 | 缓存 JSON、计数器、分布式锁 value |
| Hash | field-value 结构 | 用户信息、商品信息、配置对象 |
| List | 按插入顺序排列，可两端 push/pop | 队列、栈、最新 N 条记录 |
| Set | 无序去重集合，支持交并差 | 标签、点赞用户集合、共同好友 |
| ZSet | member 去重，按 score 排序 | 排行榜、延迟任务、按时间排序 |
| Bitmap | 基于 bit 位操作 | 签到、在线状态、是否标记 |
| HyperLogLog | 基数估算 | UV、独立 IP、大规模去重计数 |
| Stream | 追加消息流，支持消费组 | 轻量消息流、事件流 |

面试里要特别区分：

```text
Set：去重，不排序。
ZSet：去重 + 按 score 排序。
```

所以排行榜更适合 ZSet，而不是 Set。

## Redis String 和 SDS

Redis 没有直接使用 C 原生字符串，而是使用 SDS，也就是 Simple Dynamic String。

C 字符串以 `\0` 作为结束标记，获取长度需要从头遍历到结束位置，并且对二进制数据不友好。如果字符串中间包含 `\0`，C 字符串会把它当作结束。

SDS 在字符串内容外维护元数据：

```text
len：当前字符串长度
alloc/free：已分配空间或剩余空间
buf：真实字符串内容
```

SDS 带来的好处：

- 获取长度是 O(1)。
- 二进制安全，字符串内容里可以包含 `\0`。
- 拼接字符串时可以通过空间预分配减少频繁扩容。
- 写入时更容易检查空间，降低缓冲区溢出风险。

所以不要只说“SDS 有长度字段，所以快”。更完整的表达是：

> SDS 通过维护长度和容量信息，让 Redis 可以 O(1) 获取字符串长度，同时支持二进制安全和空间预分配，减少 C 字符串遍历、扩容和缓冲区溢出的风险。

## 缓存穿透、击穿、雪崩

### 缓存穿透

缓存穿透是指请求的数据在缓存和数据库里都不存在。大量这类请求会绕过缓存，直接访问数据库。

常见解决方案：

- 参数校验：非法 id、非法参数直接拒绝。
- 缓存空值：数据库查不到时缓存 null，并设置较短 TTL。
- 布隆过滤器：先判断 key 是否可能存在于业务数据集合中，不可能存在就直接拦截。

布隆过滤器要说清楚：

```text
判断不存在：一定不存在。
判断存在：可能存在，有误判。
```

误判率和位数组大小、Hash 函数数量、插入元素数量有关。

### 缓存击穿

缓存击穿是指某一个热点 key 过期，大量请求同时访问这个热点 key，瞬间打到数据库。

常见解决方案：

- 热点 key 永不过期，后台异步刷新。
- 互斥锁，只允许一个线程回源数据库，其余线程等待或快速失败。
- 逻辑过期，发现过期后先返回旧值，同时异步刷新。

注意：给过期时间加随机值主要解决的是雪崩，不是击穿的核心方案。击穿关注的是一个热点 key 被打穿。

### 缓存雪崩

缓存雪崩是指大量 key 在同一时间失效，或者 Redis 整体不可用，导致大量请求同时打到数据库。

常见解决方案：

- TTL 加随机值，避免大量 key 同时过期。
- 热点数据分批预热。
- Redis 高可用，比如主从、哨兵、Cluster。
- 限流、降级、熔断，保护数据库。
- 多级缓存，比如本地缓存 + Redis。

一版好记的区分：

```text
穿透：查不存在的数据。
击穿：一个热点 key 失效。
雪崩：大量 key 失效或 Redis 不可用。
```

## 缓存和数据库一致性

使用缓存前要先确认“数据多久可以不新鲜”。缓存是性能工具，但会引入一致性边界。

我会先确认：

- 这类数据是否允许短时间延迟。
- 更新数据后是删除缓存、更新缓存，还是等待缓存过期。
- 查询为空时是否需要缓存空值。
- 缓存 key 是否包含稳定的业务维度。
- Redis 不可用时是否允许回源数据库。

常见策略是：

```text
读：先读缓存，未命中再查数据库并写入缓存。
写：先更新数据库，再删除缓存。
```

为什么很多场景选择删除缓存，而不是更新缓存？

- 删除缓存简单，下一次读取时重新加载权威数据。
- 更新缓存容易遗漏复杂关联字段。
- 如果多个写请求并发，更新缓存可能产生旧值覆盖新值。

但删除缓存也不是绝对安全。极端并发下仍可能出现旧值回写，所以高一致场景还需要结合延迟双删、版本号、消息通知或业务兜底。

涉及状态流转判断的数据，我不会只依赖缓存结果做最终决策，而是回查权威数据。

## Redis 为什么快？

Redis 快不是因为“单线程”本身快，而是多个因素叠加：

- 基于内存操作，避免频繁磁盘 I/O。
- 命令执行主要是单线程，减少锁竞争和线程切换。
- 使用 I/O 多路复用，一个线程可以处理大量连接事件。
- 内部数据结构高效，比如 SDS、Hash table、跳表、listpack。
- Redis 命令通常设计得比较短小，避免长时间阻塞主线程。

面试可以这样回答：

> Redis 快主要是因为基于内存操作，命令执行单线程减少锁竞争，再配合 I/O 多路复用处理大量网络连接。同时 Redis 内部数据结构比较高效，所以适合高频读写场景。

## RDB 和 AOF

Redis 持久化常见有 RDB 和 AOF。

| 方式 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| RDB | 按时间点生成数据快照 | 文件紧凑，恢复快，适合备份 | 两次快照之间宕机可能丢数据 |
| AOF | 追加记录写命令日志 | 数据丢失更少，可配置 everysec | 文件更大，恢复通常更慢，需要 rewrite |

RDB 更像快照备份，AOF 更像操作日志。

实际项目可以两者结合使用。恢复时如果 AOF 可用，通常优先用 AOF，因为它记录的数据更新。

## 过期删除和内存淘汰

这两个概念容易混。

过期删除回答的是：

```text
设置了 TTL 的 key，到期后 Redis 怎么删？
```

Redis 主要使用：

- 惰性删除：访问 key 时发现过期，再删除。
- 定期删除：后台周期性抽样检查一批 key，删除过期 key。

内存淘汰回答的是：

```text
Redis 达到 maxmemory 后，写入新数据时淘汰谁？
```

常见淘汰策略：

| 策略 | 含义 |
| --- | --- |
| noeviction | 不淘汰，写入报错 |
| allkeys-lru | 所有 key 中淘汰最近最少使用 |
| volatile-lru | 设置过期时间的 key 中淘汰 LRU |
| allkeys-random | 所有 key 中随机淘汰 |
| volatile-random | 设置过期时间的 key 中随机淘汰 |
| volatile-ttl | 优先淘汰更快过期的 key |
| allkeys-lfu | 所有 key 中淘汰最近最少频率使用 |
| volatile-lfu | 设置过期时间的 key 中淘汰 LFU |

一句话区分：

```text
过期删除：key 到期后怎么删。
内存淘汰：内存不够时删谁。
```

## 分布式锁

分布式锁解决的是多个服务实例同时操作同一份共享资源的问题，比如重复提交、库存扣减、批量任务多实例并发执行。

### 正确加锁

推荐使用：

```text
SET lockKey uniqueValue NX PX expireMillis
```

这条命令同时满足：

- `NX`：key 不存在才设置，保证互斥。
- `PX/EX`：设置过期时间，避免服务宕机后锁永远不释放。
- `uniqueValue`：标识锁属于哪个请求，避免误删别人的锁。

不建议只说 `SETNX`，因为如果 `SETNX` 成功后，还没来得及设置过期时间应用就宕机，可能产生死锁。

### 正确释放锁

释放锁不能直接 `DEL lockKey`，要先判断 value 是否属于自己，再删除。

Lua 脚本：

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

为什么要用 Lua？

因为判断 value 和删除 key 必须原子执行。否则可能出现：

```text
线程 A get 发现是自己的锁
锁刚好过期
线程 B 加锁成功
线程 A 执行 del，把 B 的锁删了
```

Lua 脚本在 Redis 中执行时不会被其他客户端命令插入，所以可以保证这两个动作的原子性。

### Redisson Watchdog

如果项目里使用 Redisson，常见还会涉及 watchdog 看门狗机制。

业务执行时间可能超过锁的初始过期时间。如果锁提前过期，其他线程可能抢到锁并发执行。Redisson 在加锁成功后，会在业务线程未释放锁时定期续期，避免业务没执行完锁就过期。

但 watchdog 不是万能的：

- 必须最终在 `finally` 中释放锁。
- 如果业务线程长时间阻塞，仍然要关注锁持有时间。
- 如果 Redis 主从切换导致锁丢失，watchdog 也不能从根上解决强一致问题。

### Redis 锁和 ZooKeeper 锁怎么选？

Redis 锁偏高性能、高可用，适合对偶发锁失效可以通过幂等和补偿兜底的场景。

ZooKeeper/etcd 基于一致性协议，锁语义更强，但性能和复杂度更高，适合对一致性要求更强的场景。

面试里不要说“Redis 锁一定安全”。更稳的说法是：

> Redis 分布式锁可以解决大多数业务互斥问题，但它不是强一致锁。主从切换、锁过期时间设置不合理、业务执行超时都可能带来风险，所以要结合唯一 value、Lua 解锁、watchdog、幂等和补偿一起设计。

## 主从、哨兵和 Cluster

### 主从复制

主从复制是一个 master，多个 replica。master 负责写，replica 复制 master 数据，可以承担读请求。

它解决的是：

```text
读扩展、数据副本。
```

但它不解决自动故障转移。

### 哨兵 Sentinel

哨兵是在主从基础上增加监控和自动故障转移。master 挂了，Sentinel 会选一个 replica 提升为新的 master。

它解决的是：

```text
高可用、故障自动切换。
```

但它不解决单 master 的容量瓶颈。

### Cluster

Cluster 会把数据按 hash slot 分布到多个 master 上，每个 master 可以有 replica。

它解决的是：

```text
数据分片、容量扩展、吞吐扩展、高可用。
```

一句话总结：

```text
主从解决读扩展和副本。
哨兵解决故障自动切换。
Cluster 解决分片扩容和高可用。
```

## Big Key 和 Hot Key

### Big Key

Big Key 是指单个 key 的 value 特别大，或者集合元素特别多。

风险：

- 网络传输慢。
- 单次操作耗时高。
- 删除可能阻塞 Redis。
- 迁移和持久化成本更高。

处理方式：

- 拆分 key。
- 控制集合大小。
- 删除大 key 使用 `UNLINK` 异步删除。
- 使用 `redis-cli --bigkeys` 或监控工具扫描。

### Hot Key

Hot Key 是指某个 key 被超高频访问。

风险：

- 单节点压力过高。
- 请求倾斜。
- 可能打满网络或 CPU。

处理方式：

- 本地缓存。
- 热点 key 副本，例如 `hotKey_1` 到 `hotKey_N` 分散读取。
- 限流和降级。
- 提前识别热点并预热。

区别很好记：

```text
Big Key 是“大”。
Hot Key 是“热”。
```

## 高频追问回答模板

### 缓存问题怎么回答？

> 穿透是查不存在的数据，常用参数校验、缓存空值和布隆过滤器。击穿是一个热点 key 过期，大量请求同时打到数据库，常用互斥锁、逻辑过期或热点 key 不过期。雪崩是大量 key 同时过期或 Redis 不可用，常用 TTL 随机化、预热、高可用、限流降级和多级缓存。

### Redis 为什么快？

> Redis 快主要是因为基于内存操作，命令执行单线程减少锁竞争，网络层使用 I/O 多路复用处理大量连接，同时内部数据结构比较高效。但如果出现 big key、慢命令或阻塞操作，Redis 也会变慢。

### 分布式锁怎么回答？

> 加锁使用 `SET key value NX PX`，NX 保证互斥，PX 设置过期时间，value 使用唯一标识。释放锁时用 Lua 判断 value 一致再删除，保证校验和删除原子执行。如果使用 Redisson，还可以利用 watchdog 自动续期。但 Redis 锁不是强一致锁，主从切换和锁过期时间不合理都可能带来风险。

### ZSet 为什么适合排行榜？

> ZSet 既能保证 member 唯一，又能通过 score 排序。排行榜可以用用户 id 作为 member，用分数、金额、时间等作为 score，通过 `ZREVRANGE`、`ZRANK`、`ZINCRBY` 等命令实现排名查询和分数更新。

### HyperLogLog 适合什么？

> HyperLogLog 用来做基数估算，典型场景是 UV 统计。它占用内存很小，但有误差，也不能拿到具体元素列表。所以它适合大规模去重计数，不适合要求精确结果或需要明细的场景。

## 总结

Redis 的价值不只是“加一层缓存”。缓存、锁、计数、排行榜、限流和消息流都要分别看清楚问题边界。

面试里更稳的回答方式是：

```text
先说明场景，再说明 Redis 用什么机制解决，再说明这个机制有什么风险和补偿。
```

如果能把缓存穿透、击穿、雪崩，分布式锁，持久化，过期删除，内存淘汰，高可用，Big Key/Hot Key 这些问题串起来，Redis 的回答就会从“用过”变成“知道怎么落地和兜底”。
