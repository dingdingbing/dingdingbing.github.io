# Redis 实践

## 场景：缓存和锁都在提升速度，也在引入一致性边界

在某查询链路中，热点数据读取频繁，直接查库会放大数据库压力；在某批量处理任务中，又需要避免同一批业务单号被多个任务实例重复处理。Redis 可以分别用于缓存和分布式锁，但这两类用法的风险完全不同。

缓存要回答“数据多久可以不新鲜”，锁要回答“业务执行多久必须完成”。如果这两个问题没有想清楚，Redis 会从性能工具变成一致性问题来源。

## 缓存：先定义可接受的不一致

我使用缓存前会先确认：

- 缓存的数据是否允许短时间延迟。
- 数据更新后是主动删除、异步刷新还是等待过期。
- 查询为空时是否需要缓存空结果。
- 缓存键是否包含足够稳定的业务维度。
- 缓存失效时系统是否能降级到数据库查询。

例如某列表查询可以接受短时间延迟，就适合设置较短过期时间并在写入后删除缓存；但涉及状态流转判断的数据，我不会只依赖缓存结果做最终决策。

## 分布式锁：锁住业务键，不锁住整个世界

批量任务里，我会优先用业务单号或批次号作为锁粒度。锁粒度太粗会降低并发能力，太细又可能挡不住重复处理。

锁的过期时间要基于实际处理耗时估算，并留出失败释放策略。释放锁时必须确认锁仍属于当前执行上下文，避免释放其他执行实例刚获得的锁。

## 常见风险与取舍

| 风险 | 表现 | 取舍 |
| --- | --- | --- |
| 缓存穿透 | 不存在的数据反复查库 | 对空结果设置短过期 |
| 热点击穿 | 单个热点失效后瞬时打到数据库 | 使用互斥加载或预热 |
| 缓存过期过长 | 用户看到旧状态 | 缩短过期并在写入后删除 |
| 锁过期过短 | 任务未完成就被其他实例接手 | 基于耗时设置过期并监控超时 |
| 锁粒度过粗 | 批量任务吞吐下降 | 按业务键或批次拆分 |

## 验证方式

上线前我会关注两类验证：

- 缓存：命中、未命中、空结果、数据更新后读取是否符合预期。
- 锁：重复触发、执行超时、异常退出、释放失败时是否会造成重复处理。

如果 Redis 不可用，系统也应该有明确降级方式：缓存场景回源数据库，锁场景停止批量处理或转为保守执行，而不是继续冒险写入。

## 总结

Redis 的价值在于把读写压力和并发控制放到更合适的位置，但前提是清楚说明一致性边界。缓存、锁、计数和限流都要分别设计失败处理，不能只用“加 Redis”概括。
