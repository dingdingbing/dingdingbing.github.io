# MQ 实践

## 场景：把同步链路拆开后，失败也被拆开了

在某异步通知链路中，主流程完成后会发送消息，通知后续模块生成处理记录。引入 MQ 后，入口响应更快，模块之间也更解耦，但问题不再只发生在一个接口里，而是分散到生产、投递、消费、重试和补偿。

如果没有设计好幂等和追踪，异步链路出现问题时，排查会变成“消息到底有没有到、有没有处理、处理了几次”。

## 设计前先确认三件事

我在接入 MQ 前会先确认：

- 这条消息是否必须和数据库事务保持一致。
- 消费者重复收到同一业务事件时应该怎么处理。
- 消费失败后靠重试、补偿任务还是人工处理恢复。

只有这三件事明确，异步化才是降复杂度，而不是把复杂度推迟暴露。

## 实践：每条消息都要能追踪到业务对象

消息体里不需要塞入所有业务字段，但必须包含稳定的业务键、事件类型和必要版本信息。消费者拿到消息后，应该回查权威数据，再决定是否处理，而不是完全相信消息快照。

消费者处理时，我会把“是否已处理”做成显式判断。例如同一个业务键已经生成过后续记录时，重复消息直接返回成功，避免因为重试造成重复写入。

## 常见问题与处理策略

| 问题 | 风险 | 处理策略 |
| --- | --- | --- |
| 事务提交前发送消息 | 消费者查不到数据或查到旧状态 | 事务提交后发送，或使用本地事件表 |
| 重试导致重复消费 | 重复写入、状态重复推进 | 按业务键做幂等判断 |
| 消息缺少业务键 | 无法定位问题样本 | 统一记录业务键和事件类型 |
| 消费逻辑和补偿逻辑不一致 | 补偿后状态仍然异常 | 两者复用同一判断口径 |
| 失败只记录技术异常 | 复盘时不知道业务影响 | 日志记录业务键、失败阶段和处理结果 |

## 验证方式

我会至少验证这些场景：

1. 正常发送和消费后，后续记录按预期生成。
2. 同一消息重复投递，不会产生重复记录。
3. 消费时权威数据暂不可处理，消息会进入重试或补偿范围。
4. 消费最终失败时，能通过业务键定位到影响样本。
5. 补偿任务处理结果与正常消费路径一致。

## 总结

MQ 不是“把接口调用改成发消息”这么简单。它真正需要设计的是失败边界、重试策略、幂等判断和问题追踪。只要这些边界清楚，异步链路才会更稳，而不是更难查。
