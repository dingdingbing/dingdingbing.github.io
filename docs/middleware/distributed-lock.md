# 分布式锁对比：Redis 和 ZooKeeper 怎么选？

分布式锁面试里很容易被追问，因为它不是“会加锁”就结束了。面试官通常会继续问：

- Redis 锁为什么可能不安全？
- ZooKeeper 锁为什么一致性更强？
- ZooKeeper 是怎么用节点实现锁的？
- Redis 和 ZooKeeper 到底怎么选？
- 业务里用 Redis 锁会不会有问题？

我之前的回答大概是：

> Redis 锁偏高可用，ZooKeeper 锁偏强一致。ZooKeeper 是通过创建节点的方式获取锁，因为节点只能创建一个，所以谁创建成功谁就拿到锁。

这个回答方向没完全错，但太粗了。问题在于：

- Redis 和 ZooKeeper 都可以做高可用，不能简单说一个高可用、一个强一致。
- ZooKeeper 锁不只是“创建一个节点”，更常见的是创建临时顺序节点。
- “节点只能创建一个”只能解释最简单的互斥锁，解释不了公平性、等待队列、锁释放通知。
- 分布式锁不能只讲加锁，还要讲释放锁、异常宕机、锁超时、误删、羊群效应和业务兜底。

## 分布式锁解决什么问题？

分布式锁解决的是：多个应用实例同时操作同一份共享资源时，只允许一个实例进入临界区。

常见场景：

- 防止重复提交；
- 多实例定时任务只允许一个实例执行；
- 扣库存、改状态、生成批次号；
- 同一业务单据只能被一个节点处理；
- 防止多个服务同时刷新同一份缓存。

但分布式锁不是万能的。它只能减少并发进入临界区的概率和范围，真正的资金、库存、订单状态，最后还要靠数据库唯一约束、状态机、乐观锁、幂等和补偿兜底。

## Redis 分布式锁

### 基本加锁方式

Redis 锁常见写法是：

```text
SET lockKey uniqueValue NX PX expireMillis
```

含义：

- `NX`：key 不存在才设置，保证互斥。
- `PX`：设置毫秒级过期时间，防止服务宕机后锁永远不释放。
- `uniqueValue`：标识锁属于哪个线程或请求，释放锁时防止误删别人的锁。

不要只说 `SETNX`。

因为 `SETNX` 和 `EXPIRE` 如果拆成两条命令，中间应用宕机，就可能出现：

```text
SETNX 成功
应用宕机
EXPIRE 没执行
锁永远不释放
```

所以加锁要用一条原子命令：

```text
SET key value NX PX timeout
```

### 正确释放锁

释放锁不能直接 `DEL lockKey`，要判断 value 是不是自己的。

常见 Lua 脚本：

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

为什么要判断 value？

因为可能出现这种情况：

```text
线程 A 获取锁，过期时间 10s
线程 A 执行业务超过 10s，锁自动过期
线程 B 获取同一把锁
线程 A 执行完成，直接 DEL lockKey
线程 A 把线程 B 的锁删了
```

所以释放锁必须保证：

```text
只有锁的持有者才能释放自己的锁。
```

为什么要用 Lua？

因为“判断 value + 删除 key”必须原子执行。如果先 `GET` 再 `DEL`，中间锁可能刚好过期并被别人重新获取。

### Redis 锁的优点

Redis 锁最大的优点是简单、高性能、接入成本低。

适合：

- 短时间互斥；
- 高频加锁解锁；
- 业务允许通过幂等、重试、补偿兜底；
- 团队已有 Redis 基础设施；
- 对公平性要求不高。

比如防止重复点击、刷新缓存、普通后台任务抢占，Redis 锁通常就够用。

### Redis 锁的风险

Redis 锁的问题主要来自几个边界。

第一，锁过期时间不好设置。

过期时间太短：

```text
业务没执行完，锁先过期，其他线程进入临界区。
```

过期时间太长：

```text
持锁线程宕机后，其他线程要等很久。
```

Redisson 的 watchdog 可以自动续期，但它也不是绝对安全。它解决的是“业务执行时间超过初始过期时间”的问题，不解决 Redis 主从切换导致的锁丢失问题。

第二，主从切换可能带来锁丢失。

Redis 主从复制通常是异步的。可能出现：

```text
客户端 A 在 master 上加锁成功
锁还没同步到 replica
master 宕机
replica 升级为新 master
客户端 B 在新 master 上也加锁成功
```

这时 A 和 B 都认为自己拿到了锁。

所以面试里不要说 Redis 锁是强一致锁。更稳的说法是：

> Redis 锁适合大多数短临界区、高性能互斥场景，但它不是强一致锁。需要配合唯一 value、Lua 解锁、合理过期时间、watchdog、幂等和补偿一起使用。

## ZooKeeper 分布式锁

ZooKeeper 的核心能力不是“快”，而是通过一致性协议维护一棵强一致的节点树。客户端可以创建节点、监听节点变化，并通过临时节点感知客户端会话是否存活。

### 最简单的互斥锁：固定节点

最简单的 ZooKeeper 锁可以这样做：

```text
多个客户端同时创建 /lock/order-lock
谁创建成功，谁获取锁
谁创建失败，说明锁已被别人持有
```

为什么能互斥？

因为 ZooKeeper 同一路径下同名节点只能存在一个。

但这种方式有缺点：

- 不公平，谁下次抢到不确定；
- 所有等待者都可能 watch 同一个节点，锁释放时一起被唤醒，形成羊群效应；
- 不适合表达等待顺序。

所以真实项目里更常用临时顺序节点。

### 更常见的方式：临时顺序节点

加锁流程可以理解成这样：

```text
1. 所有客户端都在 /locks/order 下创建临时顺序节点
   例如：
   /locks/order/lock-000000001
   /locks/order/lock-000000002
   /locks/order/lock-000000003

2. 客户端获取 /locks/order 下所有子节点，并按序号排序

3. 如果自己创建的节点序号最小，说明自己拿到锁

4. 如果自己不是最小节点，就 watch 自己前一个节点

5. 前一个节点删除后，再判断自己是不是最小节点

6. 业务执行完成后，删除自己的临时节点释放锁
```

这里有三个关键词。

### 临时节点

临时节点和客户端 session 绑定。

如果客户端宕机、网络断开并超过 session timeout，ZooKeeper 会删除这个客户端创建的临时节点。

这意味着：

```text
持锁客户端挂了，锁节点会自动释放。
```

这点比 Redis 单纯依赖过期时间更贴近“客户端存活状态”。

### 顺序节点

顺序节点会带递增序号。

谁的序号最小，谁先拿锁。

这带来两个好处：

- 可以实现近似公平锁；
- 等待顺序明确，不是谁抢得快谁拿到。

### watch 前驱节点

没有拿到锁的客户端，不是所有人都 watch 最小节点，而是 watch 自己的前一个节点。

例如：

```text
lock-000000001 持有锁
lock-000000002 watch lock-000000001
lock-000000003 watch lock-000000002
lock-000000004 watch lock-000000003
```

这样 `lock-000000001` 释放时，只需要唤醒 `lock-000000002`，不会把所有等待者都唤醒。

这就是避免羊群效应的关键。

### ZooKeeper 锁的优点

ZooKeeper 锁的优势在于锁语义更强：

- 临时节点随 session 失效自动删除；
- 顺序节点天然支持排队和公平性；
- watch 机制可以感知锁释放；
- 一致性协议保证节点状态在集群内有明确顺序；
- 比 Redis 更适合强一致、低频、高价值的互斥场景。

适合：

- 主节点选举；
- 分布式调度抢占；
- 配置中心变更协调；
- 对锁顺序、公平性、一致性要求更高的场景；
- 锁竞争不特别高、临界区比较重要的场景。

### ZooKeeper 锁的成本

ZooKeeper 锁不是银弹。

它的成本主要是：

- 性能通常不如 Redis；
- 运维和接入复杂度更高；
- 客户端要处理 session 过期、连接断开、watch 丢失后的重试；
- 不适合高频短锁；
- 如果业务执行很慢，仍然会阻塞后续等待者。

## Redis 锁和 ZooKeeper 锁对比

| 对比维度 | Redis 分布式锁 | ZooKeeper 分布式锁 |
| --- | --- | --- |
| 核心机制 | `SET key value NX PX` + Lua 解锁 | 临时顺序节点 + watch 前驱节点 |
| 互斥基础 | key 不存在才设置成功 | 同路径节点顺序和最小序号 |
| 锁释放 | 主动删除或 TTL 到期 | 主动删除或 session 失效删除临时节点 |
| 一致性 | 依赖 Redis 部署模式，主从切换有边界 | 基于一致性协议，锁语义更强 |
| 性能 | 高，适合高频短锁 | 相对低，适合低频强一致协调 |
| 公平性 | 默认不公平，谁抢到算谁 | 临时顺序节点天然支持排队 |
| 阻塞等待 | 通常轮询、重试、Redisson 条件通知 | watch 前驱节点，锁释放后通知 |
| 典型风险 | 锁过期、误删、主从切换、业务执行超时 | session 过期、连接抖动、watch 处理复杂 |
| 适合场景 | 重复提交、缓存刷新、短任务互斥 | 主从选举、调度协调、强一致互斥 |
| 兜底要求 | 幂等、状态校验、补偿、唯一 value | 处理 session、重试、业务状态校验 |

## 面试里怎么回答？

不要只说：

```text
Redis 高可用，ZooKeeper 强一致。
```

这个回答太短，容易被继续追问。

更好的回答是：

> Redis 分布式锁一般用 `SET key value NX PX` 加锁，用唯一 value 标识持有者，释放时用 Lua 判断 value 再删除。它性能好、接入简单，适合短时间、高频的业务互斥。但 Redis 锁不是强一致锁，主从切换、锁过期时间设置不合理、业务执行超时都可能导致并发进入临界区，所以要配合幂等、补偿和状态校验。
>
> ZooKeeper 分布式锁更常用临时顺序节点实现。每个客户端在同一个目录下创建临时顺序节点，序号最小的客户端获得锁，其他客户端 watch 自己的前一个节点。前驱节点删除后，再判断自己是否变成最小节点。临时节点可以在 session 失效后自动删除，顺序节点可以表达排队顺序，所以 ZooKeeper 锁的一致性和公平性更强，但性能和接入复杂度也更高。
>
> 如果是普通业务里的短时间互斥，我会优先用 Redis 锁；如果是主节点选举、调度协调、对锁顺序和一致性要求更高的场景，我会考虑 ZooKeeper 或 etcd。真正落地时，不管用哪种锁，都不能只依赖锁本身，还要有幂等、状态校验和异常补偿。

## 常见追问

### 1. Redis 锁为什么要设置过期时间？

防止持锁服务宕机后锁永远不释放。

但过期时间也带来新问题：如果业务执行时间超过过期时间，锁会提前释放，其他线程可能并发进入临界区。

所以过期时间要结合业务耗时设置。如果使用 Redisson，可以通过 watchdog 自动续期，但仍然要关注主从切换和业务幂等。

### 2. Redis 锁为什么要用唯一 value？

防止误删别人的锁。

锁过期后，其他线程可能已经拿到同一个 key。如果旧线程执行完成后直接 `DEL key`，就会把新线程的锁删掉。

唯一 value 可以保证只有锁持有者才能释放自己的锁。

### 3. ZooKeeper 为什么用临时节点？

临时节点和客户端 session 绑定。客户端宕机或断开连接超过 session timeout 后，ZooKeeper 会自动删除临时节点。

这可以避免持锁客户端挂掉后锁永远不释放。

### 4. ZooKeeper 为什么用顺序节点？

顺序节点可以表达等待队列。

序号最小的节点获得锁，后面的节点按顺序等待。这样比所有客户端一起抢锁更公平，也更容易控制唤醒顺序。

### 5. ZooKeeper 为什么 watch 前一个节点？

为了避免羊群效应。

如果所有等待客户端都 watch 当前锁节点，锁释放时所有客户端都会被唤醒，瞬间请求 ZooKeeper。

watch 前一个节点后，每次释放锁只唤醒下一个等待者。

### 6. ZooKeeper 锁一定比 Redis 锁好吗？

不是。

ZooKeeper 锁语义更强，但性能、运维成本、客户端处理复杂度更高。

Redis 锁更轻、更快，更适合普通业务里的短时间互斥。

技术选型不是看谁更高级，而是看业务是否真的需要更强的一致性和公平性。

## 总结

1. Redis 锁的核心是 `SET NX PX`、唯一 value、Lua 原子释放。
2. Redis 锁适合高频短锁，但要接受主从切换、锁过期和业务超时带来的边界。
3. ZooKeeper 锁更常见的实现是临时顺序节点，不是简单创建一个固定节点。
4. 临时节点解决客户端宕机释放锁，顺序节点解决排队公平性，watch 前驱节点避免羊群效应。
5. Redis 更偏性能和接入成本，ZooKeeper 更偏一致性、顺序和协调能力。
6. 分布式锁只是第一层保护，最终仍然要靠幂等、状态机、数据库约束和补偿兜底。
