# 数据一致性问题排查

## 现象：上下游结果都“有数据”，但对不上

在某批量对账任务中，业务方反馈一批单据无法进入后续处理。初看每个环节都有数据：入口单据存在，处理记录存在，异步通知也有消费记录。但按业务单号串起来后，发现上下游数量不一致，部分状态也停在中间态。

这类问题的危险在于“不是完全失败”。如果只看某张表是否有记录，会误以为链路正常；如果直接补单侧数据，又可能制造重复处理。

## 排查入口：先固定样本，再扩范围

我先选取少量异常样本，按同一个业务单号建立排查表：

- 主单据状态和数量。
- 上游处理记录的数量、重量和更新时间。
- 下游处理记录的数量、重量和来源关系。
- 异步通知的发送、消费和重试记录。
- 后续处理是否已生成准备数据。

样本确认后，再扩大到同一时间窗口和同一业务模式，避免把单点异常误判成批量问题。

## 根因定位：不是消息失败，而是口径分叉

排查过程中，最容易怀疑的是异步通知丢失。但对比正常样本后发现，通知被正常消费，真正的断点在消费后的状态判断：某个边界状态被视为“暂不可处理”，补偿任务却按另一套口径认为“已处理完成”。

这导致异常记录既不会继续推进，也不会再次进入补偿范围，最终表现为上下游数据停在不同阶段。

## 修复策略：先统一口径，再处理存量

修复分两步：

1. 代码层面统一状态判断口径，让实时消费和补偿任务使用同一套可解释条件。
2. 数据层面只处理已确认受影响的存量样本，并保留修复前后的数量、状态和关联关系对比。

我没有选择直接把所有中间态记录批量推进，因为其中可能包含真实等待中的业务。先统一代码口径，再按样本范围修复，风险更可控。

## 验证：用同一张表复查前后变化

修复完成后，我按同一口径复查：

| 验证项 | 期望结果 |
| --- | --- |
| 上下游数量重量 | 同一业务单号下保持一致 |
| 状态推进 | 异常样本从中间态进入可处理状态 |
| 异步通知 | 重复消费不会产生重复记录 |
| 补偿任务 | 修复后的样本不再被错误跳过 |
| 后续处理 | 能继续生成下一步所需数据 |

同时检查正常样本，确认原有路径没有因为口径调整而被误拦截。

## 复盘：一致性问题要先找断点

数据一致性排查不能只问“缺了哪条数据”，更要问“链路在哪一步开始分叉”。稳定入口、样本对比、口径统一和修复证据，是我处理这类问题的基本顺序。
