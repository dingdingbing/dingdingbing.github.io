# 生产环境 OOM 排查复盘

这篇文章整理一次生产环境 OOM 面试回答。它包含两类真实经历：一次是元空间 OOM，一次是堆内存 OOM。文章先保留一版容易被追问击穿的回答，再把排查路径、JVM 细节和复盘方法论整理成更稳的表达。

为了适合公开展示，文中隐藏了具体公司、应用和业务表名，只保留排查思路。

## 错误示范：原始回答

> 我处理过好几次 OOM，比较经典的是元空间 OOM 和堆内存 OOM。
>
> 元空间 OOM 发生在一次应用整合之后。我们根据功能把多个应用的内容调整到一个应用里，上线几天后发生了一次元空间异常。元空间主要存储类信息、方法信息、静态常量等信息。当时暴露问题之后，我们第一时间拉下了 dump 文件，但是没有分析出来问题。后来观察同级应用的参数配置，发现这个应用元空间配置只有 256M，同级应用已经是 512M，调整后立马重启生产应用，解决了该问题。
>
> 另一次是堆内存溢出。上午 11 点左右突然大量报错，Grafana 显示 CPU 使用率 99.8%，内存使用率 90% 以上，生产环境 6 个副本里 4 个副本自动重启。第一时间拉下来的 dump 文件损坏，SkyWalking 没有记录，日志也没有记录，像是直接被容器 kill 了，所以没有查到内存溢出的代码在哪里。
>
> 我们开始审查前一天晚上修复问题的代码，代码逻辑虽然用了 `while true`，但是有 break 条件和代码逻辑限制，理论上不可能出现死循环。第二时间联系运维排查流量和应用配置，流量属于正常偏高，应用配置上容器内存只有 3G，远小于同级应用。调整到 6G 后重启应用。
>
> 但下午 2 点又发生了一次。这次拿到了完整 dump 文件，通过 MAT 解析 suspects report，发现不是近期修改的代码，而是一年前的代码。根本原因是异常数据导致查询时查了全量表数据，百万条数据全部加载到 JVM 里，导致 OOM。
>
> 最后我们修复了代码位置，同时排查其他地方是否存在 `selectList` 没有任何条件的场景，并在一些不确定的地方加上 `.last("limit 1000")` 限制，防止全表查询。此类 OOM 主要原因是无边界数据进入 JVM 内存。针对这种情况，要规范查询语句，空集合校验，列表查询必须分页，查询必须有条件。加上这些限制后，到现在没有再出现同类 OOM。

这版回答有真实经历，但面试里有几个风险。

## 锐评：这版回答的问题

### 1. 元空间 OOM 太像“调参数碰巧好了”

只说“同级应用 512M，所以我也调成 512M”不够。面试官可能继续问：

- 你怎么判断不是 ClassLoader 泄漏？
- 为什么上线几天后才 OOM？
- 元空间到底存什么？
- 静态变量在元空间吗？
- dump 里 `java.lang.Class` 很多能说明什么？

所以元空间 OOM 不能只讲参数调整，要讲清楚：

```text
配置不足和类加载泄漏怎么区分。
```

### 2. Java heap OOM 和容器 OOMKilled 混在一起了

如果日志里没有 `java.lang.OutOfMemoryError`，dump 损坏，容器直接重启，就不能直接断言是 Java heap OOM。

更严谨的判断是：

```text
第一次更像容器层 OOMKilled，JVM 没来得及完整写 dump。
第二次拿到完整 heap dump 后，才确认有大量对象进入堆内存。
```

### 3. 信息很多，但缺少排查主线

事故描述里有时间、监控、dump、SkyWalking、代码审查、运维排查、调内存、MAT、旧代码、全表查询。这些信息都重要，但要组织成：

```text
现象 -> 应急止血 -> 证据采集 -> 根因定位 -> 修复 -> 防复发
```

否则听起来像事故流水账。

### 4. `limit 1000` 不能当作主要修复

`.last("limit 1000")` 可以作为保护性兜底，但它不是根治方案。真正的修复应该是：

- 必填查询条件校验。
- 空集合直接返回。
- 列表查询必须分页。
- pageSize 设置上限。
- 查询条件为空时拒绝执行。
- 历史风险查询统一扫描和评审。

`limit 1000` 如果滥用，还可能掩盖业务错误。

## 元空间 OOM 复盘

### 元空间里到底存什么？

JDK 8 之后，元空间主要存放类加载后的元数据，例如：

- 类元数据。
- 方法和字段元数据。
- 运行时常量池相关元数据。
- 类加载器相关结构。
- JIT 编译相关元数据的一部分。

不要说“元空间存储 class 文件”。更准确是：

```text
class 文件被 JVM 加载、解析、链接后形成的类元数据存放在元空间。
```

也不要简单说“静态变量在元空间”。更稳的说法是：

> 静态变量本身通常跟随对应的 `java.lang.Class` 对象存放在堆里；编译期常量会进入 class 常量池，类加载后运行时常量池相关元数据在元空间；String 字面量和 intern 字符串在堆里的字符串常量池。

### 为什么上线几天后才出现？

普通 Spring Boot 应用的大部分 Bean 和代理类确实会在启动时创建，但运行期仍然可能继续触发类加载或类相关缓存增长。

常见原因包括：

- 低频接口上线几天后才被访问。
- 定时任务到特定周期才跑到某些逻辑。
- 三方 SDK、序列化框架、ORM 框架按需加载类或缓存元数据。
- AOP 切点首次匹配更多方法，并缓存匹配结果。
- 链路追踪 agent 对新加载类进行字节码增强。
- 动态代理、ByteBuddy、CGLIB、Javassist 等生成类。

所以“上线几天后才 OOM”一般有两类解释：

```text
1. 容量偏小，启动后接近上限，运行期低频路径和懒加载逐步补齐后触顶。
2. 存在 ClassLoader 泄漏或动态类生成失控，元空间持续增长直到 OOM。
```

### 怎么判断配置不足还是泄漏？

不能只靠“调大后不报错”下结论。更稳的是看曲线和类加载指标：

- Metaspace Used 是否持续增长。
- Loaded Class Count 是否持续增长。
- ClassLoader 数量是否持续增长。
- Full GC 后 Metaspace 是否无法回落。

如果是：

```text
启动后或业务预热后上涨到平台期，调大后长期稳定
```

更像容量配置不足。

如果是：

```text
Metaspace Used、Loaded Class Count、ClassLoader 数量持续上涨，Full GC 后不回落
```

就要怀疑 ClassLoader 泄漏、动态代理、字节码增强、脚本编译或热加载问题。

### MAT 里看到 `java.lang.Class` 怎么理解？

当时复盘 dump 时，MAT suspects 指向过类似信息：

```text
大量 java.lang.Class 实例占用一部分堆内存。
```

这不能直接等价于“元空间根因”。因为 heap dump 里看到的是堆上的 `java.lang.Class` 镜像对象，而 Metaspace OOM 爆的是 JVM native memory 里的类元数据。

Heap dump 对 Metaspace OOM 只能提供间接线索，例如：

- `java.lang.Class` 数量。
- ClassLoader 数量。
- 反射 `Method`、AOP、字节码增强相关对象。
- 框架缓存是否异常大。

更稳的表述是：

> MAT 里 `java.lang.Class` 占用较高只能说明类相关对象和缓存较多，不能直接证明元空间泄漏。真正要结合 Metaspace 曲线、Loaded Class Count、ClassLoader 数量和 Full GC 后是否回落来判断。

## 堆内存 OOM 复盘

### 现象

上午 11 点左右，线上突然大量报错：

- CPU 接近 100%。
- 内存使用率超过 90%。
- 6 个副本中 4 个发生自动重启。
- 第一次 dump 损坏，链路追踪和日志没有留下有效代码入口。

这种情况下，不能马上断言是业务代码抛出了 `Java heap space`。更可能的情况是：

```text
容器内存达到限制，被容器层 OOMKilled，JVM 没有机会完整写 dump。
```

### Java heap OOM 和容器 OOMKilled 怎么区分？

| 维度 | Java heap OOM | 容器 OOMKilled |
| --- | --- | --- |
| 应用日志 | 通常有 `java.lang.OutOfMemoryError: Java heap space` | 可能没有 Java 异常 |
| dump | JVM 可能生成完整 heap dump | dump 可能没有生成或损坏 |
| GC 日志 | 常见频繁 Full GC 后仍无法回收 | 可能来不及记录完整 JVM 异常 |
| 容器事件 | 不一定有 OOMKilled | Pod 可能显示 OOMKilled，exit code 137 |
| 内存范围 | 主要是 Java heap | 堆、元空间、Direct Memory、线程栈、native memory 总和超过 limit |

线上排查时，我会同时看：

- 应用日志。
- GC 日志。
- dump 是否完整。
- Kubernetes / 容器事件和 exit code。
- Grafana 的堆、非堆、容器内存、CPU 曲线。

### 应急止血

当时先做了两件事：

1. 审查前一晚变更代码，排除明显死循环和无限集合增长。
2. 联系运维排查流量和容器资源配置。

当时流量正常偏高，但容器内存只有 3G，低于同级应用。于是先把容器内存调整到 6G 并重启止血。

这个动作是合理的，但只能叫止血，不是根治。

原因是：

```text
如果根因是无边界查询，调大堆只能推迟 OOM。
只要异常条件仍然可能触发全表查询，数据量继续增长或并发请求增加，6G 也会被打满。
```

### 根因定位

下午问题再次出现，这次拿到了完整 dump。通过 MAT 分析，根因不是前一天变更，而是一段历史查询逻辑。

![MAT suspect overview: 单个请求线程持有大对象数组](/images/troubleshooting/oom/mat-suspect-overview.png)

_MAT suspects report 指向一个 Tomcat 请求线程持有了大量本地变量，其中核心对象是一个接近 2GB 的 `Object[]`。这个报告不是最终结论，但给出了继续沿线程栈和 retained heap 往下查的方向。_

异常数据导致查询条件失效，最终执行了近似全表查询。百万级数据从数据库返回后，被 JDBC/MyBatis 映射成 Java 对象，并放入 `List` 持有。

![MAT retained heap: ArrayList 持有 Object 数组](/images/troubleshooting/oom/mat-retained-heap.png)

_沿最短引用路径继续展开，可以看到 `ArrayList` 的 `elementData` 持有大规模 `Object[]`，并被 HTTP 请求线程保留。这说明问题不是零散小对象泄漏，而是一次请求把大量查询结果装进集合后无法释放。_

![MAT thread stack: JDBC 读取结果集](/images/troubleshooting/oom/mat-jdbc-result-read.png)

_线程栈显示请求仍停留在 MySQL JDBC 读取结果集的链路上，说明 dump 生成时应用还在从数据库读取或转换大量结果行。_

![MAT stack excerpt: MyBatis selectList 调用链](/images/troubleshooting/oom/mat-selectlist-stack.png)

_继续向上看调用链，可以看到 MyBatis / MyBatis-Plus 的 `selectList` 路径。公开文章里裁掉了内部业务包名，但保留了“无边界列表查询”这个关键证据。_

这类对象在当前请求处理链路上仍然可达，GC 无法回收，最终导致堆内存被打满。

### 为什么 CPU 会接近 100%？

CPU 接近 100% 不一定只是业务线程在运行，也可能包含 GC 压力。

这类场景中，CPU 飙高通常由多个因素叠加：

- SQL 返回大量数据。
- JDBC/MyBatis 做结果集映射和类型转换。
- 大量对象创建。
- `ArrayList` 扩容和对象引用维护。
- 大响应 JSON 序列化。
- 堆被打满后频繁 GC，甚至 Full GC。
- 多个请求同时触发类似全量查询。

所以更稳的说法是：

> 全表查询导致大量对象创建和映射，同时堆内存被打满后 GC 频繁运行，业务线程和 GC 线程共同把 CPU 拉高。

### MAT 怎么看？

MAT 的几个常用入口：

| 入口 | 作用 |
| --- | --- |
| Suspects Report | 自动生成的泄漏嫌疑报告，只能作为线索 |
| Dominator Tree | 看哪个对象支配了最多内存 |
| Retained Heap | 如果这个对象被回收，可以连带释放的总内存 |
| Path to GC Roots | 看对象为什么还不能被回收 |
| Thread Overview | 看 dump 生成时线程正在执行什么 |
| Histogram | 按类统计对象数量和占用 |

我的使用顺序一般是：

```text
先看 suspects report 找方向
再看 dominator tree 和 retained heap 找大对象
再看 path to GC roots 判断为什么回收不了
最后结合 thread overview、日志和链路追踪定位业务入口
```

如果 dump 损坏，可以退一步：

- 看容器事件和 exit code。
- 看 Grafana 的内存、CPU、GC、线程、QPS 曲线。
- 看应用日志、access log 和链路追踪。
- 看慢 SQL、数据库连接数和返回行数。
- 使用 Arthas 在线诊断，例如 `dashboard`、`thread`、`trace`、`watch`、`heapdump`。
- 必要时摘掉一个副本保现场，再用 `jmap` / `jcmd` 抓取。

生产使用 Arthas 要控制范围，避免 `trace` / `watch` 范围过大进一步压垮服务。

## 最终修复

最终不是靠调大内存解决，而是把查询边界补上。

修复动作包括：

- 必填查询条件校验。
- 空集合条件直接返回。
- 列表查询必须分页。
- pageSize 设置最大值。
- 查询条件为空时拒绝执行。
- 对历史风险点增加保护性 `limit`。
- 排查类似无条件 `selectList` 的代码。

这里要注意：

```text
limit 1000 是保护性兜底，不是主要修复。
```

真正的修复是让查询语义有边界。

## 防复发沉淀

这次问题可以沉淀成几类规范。

### 编码规范

- 列表查询必须分页。
- 查询必须有业务条件。
- 空集合直接返回，不允许拼出空条件 SQL。
- pageSize 必须有上限。
- 关键表禁止裸 `selectList`。
- 不确定查询点必须有保护性上限。

### 评审规范

Code Review 中重点看：

- 是否存在无条件查询。
- 是否存在循环内查库。
- 是否存在大集合一次性加载。
- 是否存在接口直接返回大对象列表。
- 是否存在导出、报表、批处理无分页处理。

### 监控和预案

- 统一 JVM 和容器内存基线。
- 开启 heap dump 和 GC log。
- 监控堆、非堆、Metaspace、Direct Memory、线程数。
- 监控慢 SQL、返回行数、接口耗时。
- 对容器 OOMKilled 建告警。
- 固化 OOM 后保现场、摘流量、抓 dump、分析 MAT 的流程。

## 更稳的面试回答

如果被问“你有处理过生产环境 OOM 吗”，可以这样回答：

> 我处理过几次生产 OOM，印象比较深的是两类：一次是元空间 OOM，一次是堆内存 OOM。
>
> 元空间 OOM 发生在一次应用整合之后。多个应用能力合并到一个应用里，上线几天后出现了 Metaspace OOM。元空间主要存放类加载后的元数据，比如类元数据、方法和字段元数据、运行时常量池相关元数据、类加载器相关结构。它不是直接存 class 文件，也不是存普通对象实例。
>
> 当时我们先保留现场，拉取 dump 和 JVM 参数，再对比同级应用配置，发现 `MaxMetaspaceSize` 只有 256M，而同级应用已经是 512M。应用整合后类规模、方法数量、AOP 代理和探针增强都会增加类加载压力，所以先调到 512M 重启止血。
>
> 但我不会只凭调参就认为根因解决。元空间 OOM 要区分配置不足和泄漏。如果 Metaspace Used、Loaded Class Count、ClassLoader 数量在业务预热后进入平台期，调大后稳定，说明更像容量不足；如果持续上涨，Full GC 后也不回落，就要排查 ClassLoader 泄漏、动态代理、字节码增强或脚本编译。
>
> 另一次是堆内存问题。线上突然大量报错，CPU 接近 100%，内存超过 90%，多个副本自动重启。第一次 dump 损坏，日志和链路追踪没有有效入口，所以我判断更像容器层 OOMKilled，JVM 没来得及完整写 dump。我们先审查前一天变更，排除明显死循环，再联系运维看流量和资源配置。因为容器内存低于同级应用，先扩到 6G 重启止血。
>
> 但下午再次发生后，我们拿到了完整 heap dump。通过 MAT 的 suspects report、dominator tree、retained heap 和线程信息分析，发现根因不是近期代码，而是一段历史查询逻辑。异常数据导致查询条件失效，最终近似全表查询，百万级数据被 MyBatis 映射成对象放入 List，当前请求持有这些对象，GC 无法回收，最终打满堆内存。
>
> 最终修复不是继续调大内存，而是补齐查询边界：必填条件校验、空集合直接返回、列表查询分页、pageSize 上限、无条件查询拒绝执行，并扫描历史 `selectList` 风险点。`limit 1000` 只作为保护性兜底，不是主要方案。
>
> 这次复盘后，我总结 OOM 排查不能只看“内存不够就调大”，而是先判断 OOM 类型，再保现场、看 dump、GC 日志、容器事件和监控曲线，最后从内存对象反推业务入口，并把修复沉淀成查询边界、参数基线、告警和代码评审规范。

## 方法论总结

OOM 排查可以按这条链路推进：

```text
止血：扩容、重启、摘流量，先恢复服务。
保现场：dump、GC 日志、容器事件、监控曲线、变更记录。
定类型：Metaspace、Heap、Direct Memory、线程栈、容器 OOMKilled。
找证据：MAT suspects、dominator tree、class histogram、GC log。
定位入口：从大对象、ClassLoader 或线程栈反推业务代码和请求路径。
修根因：补边界、分页、限流、释放资源、修泄漏。
防复发：参数基线、告警、压测、代码规范、风险扫描。
```

一句话总结：

> OOM 的核心不是“内存不够”，而是要判断为什么这类对象或元数据能持续进入内存、为什么不能被回收，以及如何把这类风险变成可监控、可评审、可兜底的工程规范。
