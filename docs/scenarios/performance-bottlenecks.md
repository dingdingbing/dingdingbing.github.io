# 后端系统性能瓶颈推演

## 主问题

一个 Spring Boot 应用里同时用到了 Tomcat、Dubbo、OpenFeign、Redis、RabbitMQ、MySQL。系统变慢或者吞吐上不去时，性能瓶颈可能在哪里？如果继续往深层看，JVM 又会带来哪些影响？

这个问题不能只回答“看 CPU、内存、数据库”。真实系统里，请求会穿过很多层：入口线程、业务线程、RPC 调用、HTTP 调用、缓存、消息队列、数据库连接池、数据库执行计划、对象分配、GC。任意一层排队，都会表现成接口变慢。

## 直觉答案

第一反应可能是：

- 数据库慢 SQL 是瓶颈。
- Redis 能加速，应该不会慢。
- MQ 是异步的，应该能削峰。
- JVM 主要看内存和 GC。
- Tomcat 线程数调大一点就能抗住更多请求。

这些判断都有一部分道理，但也容易被追问击穿。性能瓶颈不是“哪个组件最慢”这么简单，而是要看请求链路里哪里开始排队、哪里资源被占满、哪里超时时间互相放大。

## 真实执行场景

一次请求进入系统，可能经历下面这条链路：

```text
客户端
-> Nginx / 网关
-> Spring Boot / Tomcat
-> Controller / Service
-> Dubbo 调用内部服务
-> OpenFeign 调用外部 HTTP 服务
-> Redis 读写缓存
-> RabbitMQ 发送或消费消息
-> MySQL 查询或更新
-> JVM 对象分配、线程调度、GC
```

排查时要先问：

- 慢的是单个接口，还是整个应用？
- 是平均响应慢，还是 P99/P999 抖动？
- 是吞吐上不去，还是错误率升高？
- 是应用线程在忙，还是都在等外部资源？
- 是 CPU 满、内存满、连接池满、线程池满，还是数据库执行慢？

性能瓶颈的本质通常是：

```text
某个共享资源达到上限
-> 请求开始排队
-> 等待时间叠加
-> 超时、重试、线程占用继续放大
-> 整条链路雪崩式变慢
```

## Spring Boot / Tomcat 瓶颈

Spring Boot Web 应用常见入口是内嵌 Tomcat。Tomcat 的关键瓶颈不只是最大线程数，还包括连接数、等待队列、请求处理耗时和后端依赖耗时。

常见瓶颈：

- `maxThreads` 不够，请求进入后排队等待工作线程。
- `acceptCount` 队列堆积，队列满后新连接被拒绝。
- 业务线程被慢 SQL、远程调用、锁等待占住，导致 Tomcat 线程耗尽。
- 请求体或响应体太大，网络读写和序列化变慢。
- 接口没有超时控制，慢依赖把入口线程长期占住。

容易误解的是：Tomcat 线程数不是越大越好。线程数过大可能增加上下文切换，放大内存消耗，还会让更多请求同时打到后端依赖，把数据库、Redis 或下游服务压得更慢。

排查信号：

- Tomcat 活跃线程数接近最大值。
- 接口耗时升高，但 CPU 不一定高。
- 线程栈大量停在 JDBC、Redis、Dubbo、Feign 或锁等待。
- 网关侧出现连接等待、响应超时或 5xx。

## Dubbo 瓶颈

Dubbo 常见瓶颈在 Provider 线程池、网络通信、序列化、超时重试和下游依赖。

常见瓶颈：

- Provider 线程池被慢请求占满。
- Consumer 并发过高，把 Provider 打满。
- 超时时间设置不合理，Consumer 还在重试，Provider 其实还在执行。
- 重试导致流量放大，例如一次失败变成多次调用。
- 序列化对象过大，网络传输和 CPU 开销上升。
- Provider 内部继续访问 MySQL、Redis、MQ，真正瓶颈在更下游。

Dubbo 的危险点是“超时和重试放大”。如果下游已经慢了，重试会让请求量变成原来的数倍，Provider 线程池更快耗尽，最终表现为大量超时。

排查信号：

- Dubbo Provider 线程池活跃数、队列、拒绝数异常。
- Consumer 侧超时增多。
- Provider 侧实际执行仍在继续。
- 同一业务请求出现多次重复调用。
- 链路追踪显示耗时集中在某个 RPC 服务。

## OpenFeign 瓶颈

OpenFeign 本质是 HTTP 客户端封装。它的瓶颈通常不在 Feign 注解本身，而在 HTTP 连接池、下游响应、序列化反序列化、超时和重试。

常见瓶颈：

- 连接池不够，线程等待可用 HTTP 连接。
- 下游服务慢，入口线程一直阻塞等待响应。
- 读取大响应体，JSON 反序列化耗 CPU 和内存。
- 连接超时、读取超时设置过长，故障时线程被占住。
- 重试策略不合理，外部服务抖动时流量被放大。
- 没有隔离外部依赖，外部接口慢拖垮本应用。

排查信号：

- 线程栈停在 HTTP client 读写。
- Feign 调用 P99 明显升高。
- 下游接口响应慢或错误率高。
- 本应用 CPU 不高，但线程被大量阻塞。
- 熔断、降级或限流指标触发。

## Redis 瓶颈

Redis 很快，但不是不会成为瓶颈。它是单线程执行命令模型为主，性能问题通常来自大 key、热 key、慢命令、网络、连接数和错误使用方式。

常见瓶颈：

- 热 key 被大量并发访问，单个 key 成为集中压力点。
- 大 key 读写导致网络传输、序列化和 Redis 主线程阻塞。
- 使用 `keys`、大范围 `scan`、大集合操作等慢命令。
- 缓存击穿、穿透、雪崩，流量突然打到数据库。
- Redis 连接池耗尽，应用线程等待连接。
- value 过大，应用侧反序列化和内存占用上升。
- 持久化、主从复制、网络抖动导致延迟升高。

排查信号：

- Redis `slowlog` 出现慢命令。
- Redis CPU 高、网络出口高。
- 单个 key QPS 异常高。
- 应用侧 Redis 连接池等待增加。
- 缓存命中率下降，MySQL QPS 同时上升。

## RabbitMQ 瓶颈

RabbitMQ 是削峰和异步解耦工具，但它不能消灭压力，只是把同步压力转成异步队列。如果消费能力跟不上，问题会变成消息堆积。

常见瓶颈：

- 生产速度大于消费速度，队列堆积。
- 消费者线程数不足，或者消费逻辑太慢。
- 消费者里访问 MySQL、Redis、外部接口，真正瓶颈在消费链路下游。
- 单条消息处理时间长，`prefetch` 设置不合理。
- 消息体太大，网络和磁盘压力上升。
- 持久化消息、镜像队列、确认机制带来额外 IO 成本。
- 消费失败反复重试，形成失败消息风暴。

排查信号：

- 队列 ready 数持续增长。
- unacked 数很高，说明消息被取走但处理慢或卡住。
- 消费 TPS 低于生产 TPS。
- 消费者线程栈停在数据库、HTTP、锁等待。
- RabbitMQ 磁盘、内存、水位告警。

## MySQL 瓶颈

MySQL 是最常见的性能瓶颈，但不能一上来就只盯慢 SQL。要同时看 SQL、索引、锁、连接数、事务、Buffer Pool、磁盘 IO 和应用侧连接池。

常见瓶颈：

- SQL 没走索引，出现全表扫描。
- 返回数据量过大，MySQL、网络、JVM 都被拖慢。
- 慢 SQL 持有连接时间长，Hikari 连接池被占满。
- 行锁、间隙锁、表锁导致事务等待。
- 大事务导致 undo、redo、锁持有时间增加。
- 排序、分组、临时表、回表过多导致 CPU/IO 升高。
- 连接数过高，数据库线程和内存压力上升。
- 主从延迟导致读写不一致或读请求堆积。

排查信号：

- 慢 SQL 日志。
- `explain` 显示扫描行数大、索引不合理。
- 数据库 CPU、IO、连接数、锁等待升高。
- Hikari 活跃连接数接近最大值，等待连接线程增加。
- 接口耗时和 SQL 耗时高度一致。

## JVM 深层瓶颈

继续往深层看，JVM 不是独立于业务之外的“运行环境”，它会直接影响接口耗时和吞吐。

常见瓶颈：

- 对象创建太多，Young GC 频繁。
- 大对象、大集合、全量查询结果进入堆，触发 Full GC 或 OOM。
- JSON 序列化、反序列化创建大量临时对象。
- 线程数过多，线程栈占用内存，上下文切换增加。
- 锁竞争严重，线程阻塞或自旋消耗 CPU。
- 元空间不足，类加载、动态代理、字节码增强导致 Metaspace 压力。
- Direct Memory 使用过多，例如 Netty、NIO、压缩、文件传输。
- GC 参数和容器内存限制不匹配，被容器 OOMKilled。

排查信号：

- GC 日志显示频繁 Young GC、Full GC 或长时间 STW。
- 堆内存持续上升，Full GC 后不回落。
- 线程数异常增长，线程栈大量相同阻塞点。
- CPU 高但业务 QPS 不高，可能是 GC、锁竞争或序列化。
- 容器内存高于 JVM 堆内存，可能是非堆、Direct Memory、线程栈或 native memory。

## 怎么定位瓶颈

不要凭感觉猜瓶颈。比较稳的顺序是：

1. 看入口指标：QPS、平均耗时、P99、错误率。
2. 看资源指标：CPU、内存、GC、线程数、连接池、队列长度。
3. 看链路追踪：耗时集中在哪一段。
4. 看线程栈：线程到底在运行、等待连接、等待锁，还是等待网络。
5. 看下游指标：Redis、MQ、MySQL、Dubbo Provider、外部 HTTP 服务。
6. 看日志和慢日志：超时、拒绝、慢 SQL、慢命令、消息重试。
7. 用压测验证：逐步增加并发，看哪个指标先到上限。

一个常用判断是：

```text
CPU 高，线程都在 RUNNABLE
-> 可能是计算、序列化、GC、锁自旋。

CPU 不高，但接口慢
-> 可能是数据库、Redis、RPC、HTTP、连接池、锁等待。

连接池满
-> 继续看连接被谁持有，是慢 SQL、慢 Redis、慢 HTTP，还是事务太长。

队列堆积
-> 继续看消费能力、消费者线程、消费逻辑和下游依赖。
```

## 延伸问题

### 1. Tomcat 线程数调大能解决性能问题吗？

不一定。线程数调大只能让更多请求同时进入应用。如果瓶颈在 MySQL、Redis、Dubbo Provider 或外部 HTTP，下游会更快被打满。线程数应该和后端资源能力一起评估。

### 2. Redis 很快，为什么也会慢？

Redis 快的是单次简单命令。大 key、热 key、慢命令、网络带宽、连接池等待、序列化大对象都会让 Redis 变成瓶颈。

### 3. MQ 削峰后为什么还会出问题？

MQ 只是把压力放到队列里。如果消费者处理能力不足，消息会堆积；如果消费失败反复重试，还会形成重试风暴。削峰要同时设计消费能力、重试、死信和补偿。

### 4. CPU 高一定是代码计算太重吗？

不一定。CPU 高可能来自业务计算、JSON 序列化、GC、锁竞争、线程上下文切换、加解密、压缩、日志打印或数据库驱动结果集映射。

### 5. 为什么慢 SQL 会拖垮 Tomcat？

慢 SQL 会长时间占用数据库连接和业务线程。请求线程等不到 SQL 返回，就不能释放 Tomcat 线程。并发上来后，Tomcat 线程和 Hikari 连接池都会被占满。

## 可验证结论

可以设计一个小压测来验证瓶颈定位方法：

1. 准备一个接口，依次调用 Redis、MySQL 和一个模拟慢 HTTP 服务。
2. 分别把 MySQL 查询改慢、把 HTTP 服务延迟调高、把 Redis value 放大。
3. 用压测逐步增加并发，观察 P99、Tomcat 线程、Hikari 连接、Redis 连接、GC 和 CPU。
4. 每次只改变一个变量，看哪个指标先达到上限。
5. 抓一次线程栈，确认线程卡在 JDBC、HTTP、Redis、锁等待还是 CPU 计算。

这个实验能说明：性能瓶颈不是孤立组件问题，而是链路中最先排队的资源决定了整体吞吐。

## 面试表达版本

可以这样回答：

> 我会先把性能瓶颈放到完整调用链里看。Spring Boot 入口是 Tomcat，瓶颈可能是工作线程、连接队列、请求体响应体过大，或者线程被下游慢调用占住。Dubbo 要看 Provider 线程池、超时重试、序列化和下游依赖；OpenFeign 要看 HTTP 连接池、外部接口耗时、超时和重试；Redis 要看热 key、大 key、慢命令、连接池和缓存命中率；RabbitMQ 要看生产消费速率、ready 和 unacked 堆积、消费者处理耗时和失败重试；MySQL 要看慢 SQL、索引、锁等待、事务、连接池和返回数据量。再往下看 JVM，要关注对象分配、GC、线程数、锁竞争、堆外内存、元空间和容器内存限制。定位时我不会直接猜某个组件，而是先看 QPS、P99、错误率，再看链路追踪、线程栈、连接池、队列和下游指标，找出第一个开始排队或达到上限的资源。
