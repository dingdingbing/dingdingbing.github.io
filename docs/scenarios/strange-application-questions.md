# 奇奇怪怪的应用类问题

面试里经常会遇到一些看起来很奇怪的问题。它们表面上像是在问某个技术点，实际上是在考你能不能看见背后的本质：

- 资源有没有边界；
- 并发会不会打乱状态；
- 重试会不会造成重复执行；
- 事务能不能覆盖完整链路；
- 失败后怎么补偿；
- 数据最终怎么对回来；
- 系统被打爆前有没有保护。

如果只回答概念，很容易答偏。更稳的方式是先判断问题属于哪一类，再按“现象 -> 本质 -> 排查/设计 -> 验证”的顺序回答。

## 一、接口慢和超时类

常见问题：

- 一个接口突然从 200ms 变成 5s，你怎么排查？
- 网关报 504，但应用日志没有异常，可能是什么原因？
- CPU 不高，但接口很慢，可能卡在哪里？
- CPU 很高，接口也慢，怎么定位是哪段代码？
- 数据库没慢 SQL，但接口还是慢，可能是什么问题？
- 为什么本地很快，线上很慢？
- 一个接口偶发超时，怎么证明是下游慢、线程池满还是连接池满？
- 连接池设置越大越好吗？
- 线程池设置越大越好吗？
- 如果调用第三方接口慢，你怎么保护自己的系统？

本质：

接口慢不是一个点的问题，而是一条链路的问题。要拆成网关、应用线程、线程池、连接池、数据库、Redis、MQ、HTTP 下游、GC、CPU、文件 IO 等环节。

回答抓手：

```text
先看链路耗时分布，再看应用日志和监控。
如果 CPU 不高但接口慢，优先怀疑阻塞等待，比如数据库连接池、HTTP 下游、Redis、文件 IO、线程池队列。
如果 CPU 高，重点看线程栈、GC、死循环、序列化、加解密、压缩等 CPU 密集操作。
```

参考回答：

```text
我会先把接口耗时按链路拆开，不会一上来就只看 SQL。比如先确认网关有没有超时、请求有没有进入应用、应用日志里各阶段耗时是多少，再看数据库、Redis、MQ、HTTP 下游这些外部依赖。

如果 CPU 不高但接口慢，我会优先怀疑线程阻塞，比如数据库连接池拿不到连接、下游接口响应慢、线程池队列堆积或者文件 IO 卡住。如果 CPU 很高，我会结合 top、线程栈和 GC 日志，看是不是死循环、频繁 GC、锁竞争或者某段计算逻辑占用 CPU。最后根据定位结果做针对性处理，比如 SQL 优化、连接池调整、线程池隔离、下游超时和降级。
```

## 二、数据库和 SQL 类

常见问题：

- 一条 SQL 在测试环境很快，生产环境很慢，为什么？
- 明明加了索引，为什么没走索引？
- 为什么有时候 `limit 10` 也很慢？
- 为什么分页越往后越慢？
- `count(*)` 很慢怎么优化？
- 查询 1000 条一次查完，和 1000 次每次查 1 条，哪个更好？
- 大批量插入怎么做？
- 如何避免全表查询把 JVM 打爆？
- 表数据量大了以后，你怎么拆分或优化？
- 你们怎么设计索引？是事后加还是建表时考虑？

本质：

SQL 问题不是只看“有没有索引”，而是看数据分布、选择性、扫描行数、回表、排序、分页深度、执行计划、返回数据量，以及应用侧能不能承接这些数据。

回答抓手：

```text
先看 EXPLAIN 和实际扫描行数，再看索引选择是否符合过滤条件和排序条件。
生产和测试不一致时，要考虑数据量、数据分布、统计信息、优化器成本估算和索引设计差异。
如果查询结果很大，还要考虑 JVM 内存、网络传输和对象映射成本。
```

参考回答：

```text
SQL 慢我会先看执行计划和扫描行数，确认有没有走到合适的索引，以及索引是否同时覆盖过滤条件、排序条件和返回字段。生产和测试表现不一样时，我不会只看 SQL 文本是否相同，还会看数据量、数据分布、统计信息和优化器选择。

如果是深分页或者 limit 很慢，要看前面实际扫描了多少行；如果是全量查询，还要考虑结果集返回到应用后会不会造成网络传输、MyBatis 对象映射和 JVM 内存压力。优化手段可能包括调整联合索引、改写查询条件、延迟关联、游标分页、限制 pageSize，以及避免无条件大范围查询。
```

## 三、事务和一致性类

常见问题：

- 本地方法加了 `@Transactional`，为什么事务没生效？
- 一个方法里调用另一个加事务的方法，事务会生效吗？
- 事务里调用远程接口有什么问题？
- 事务里发 MQ 有什么风险？
- 订单成功了，但库存没扣，怎么处理？
- 支付成功了，但订单状态没变，怎么处理？
- 你怎么保证数据库和 MQ 的一致性？
- 乐观锁失败后重试，为什么可能一直失败？
- 并发更新余额，怎么保证不覆盖？
- 如果部分成功、部分失败，系统怎么补偿？

本质：

事务类问题的核心是边界。单库事务只能保证本地数据库，远程接口、MQ、缓存、第三方系统不在同一个事务里。跨系统链路要靠最终一致性、补偿、幂等、对账和告警兜住。

回答抓手：

```text
先确认事务边界在哪里，再看哪些操作不在事务内。
本地数据库可以用事务保证原子性，跨系统要设计消息、状态表、补偿任务和对账机制。
如果涉及重试，还要确认每次重试能不能读到最新数据，以及重试是否幂等。
```

参考回答：

```text
我会先确认这个问题的事务边界。如果只是单库内多张表操作，可以通过本地事务保证一致性；但如果里面包含远程接口、MQ、缓存或者第三方回调，本地事务就覆盖不到这些动作。

跨系统场景下我一般会按最终一致性处理，比如先落业务状态或本地消息表，事务提交后再发消息，消费者侧做好幂等和失败重试，同时用补偿任务和对账任务兜底。对于并发更新，比如余额、库存这类场景，我会考虑乐观锁、状态条件更新或者唯一约束，并注意重试时是否能读到最新提交数据。
```

## 四、幂等和重复提交类

常见问题：

- 用户重复点击提交按钮，怎么防止重复下单？
- MQ 消息重复消费怎么办？
- 第三方回调重复通知怎么办？
- 接口超时后客户端重试，服务端怎么保证不会重复处理？
- 幂等 key 怎么设计？
- 用 Redis 做幂等有什么风险？
- 用数据库唯一索引做幂等有什么优缺点？
- 如果第一次请求处理成功但响应失败，第二次请求来了怎么办？
- 状态机如何保证幂等？
- 幂等和防重有什么区别？

本质：

幂等不是简单加一个 Redis key。核心是识别业务唯一性，并保证同一业务动作执行一次和执行多次的最终结果一致。

回答抓手：

```text
先找业务唯一键，比如订单号、支付流水号、外部回调单号。
写操作要有唯一约束或状态机约束。
如果第一次成功但响应失败，第二次请求应该能查到第一次结果，并返回一致响应，而不是重新执行一次。
```

参考回答：

```text
幂等我会先找业务上的唯一标识，比如订单号、请求流水号、支付流水号或者第三方回调单号。然后根据业务场景选择落点：可以用数据库唯一索引防重复，也可以用状态机限制非法流转，或者用 Redis 做短时间防重。

真正要处理的是“服务端已经成功但客户端没收到响应”的情况。这个时候第二次请求不能重新执行扣款、下单、发货这类动作，而是应该根据业务唯一键查到第一次处理结果，并返回一致响应。对 MQ 或第三方回调也是一样，消费者要能识别重复消息，重复消费时直接返回成功或跳过处理。
```

## 五、MQ 类

常见问题：

- 为什么用 MQ？不用 MQ 会怎样？
- MQ 如何保证消息不丢？
- 消息重复消费怎么处理？
- 消息积压了怎么办？
- 消息顺序怎么保证？
- 消费失败怎么重试？
- 死信队列有什么用？
- MQ 消费很慢，怎么排查？
- 事务提交前发消息会有什么问题？
- 用 MQ 解耦后，怎么保证主流程和异步流程最终一致？

本质：

MQ 不是只有“异步、解耦、削峰”。真正落地时要考虑可靠投递、重复消费、顺序、积压、失败重试、死信、幂等和最终一致性。

回答抓手：

```text
先说明 MQ 解决了什么业务问题，再说明可靠性怎么保证。
生产者要考虑事务提交和消息发送顺序，消费者要考虑幂等、重试、死信和告警。
如果要求顺序，要看顺序范围，是全局顺序、订单维度顺序，还是单链路顺序。
```

参考回答：

```text
我使用 MQ 一般是为了解耦主流程和非核心耗时逻辑，或者做削峰、异步通知、跨系统流程推进。但用了 MQ 后，重点就变成消息可靠性和最终一致性。

生产端要避免事务没提交就发消息，或者事务提交了消息没发出去，可以通过事务后发送、本地消息表或可靠消息机制来保证。消费端要做好幂等，因为消息可能重复投递；失败时要有重试、死信和告警。如果业务要求顺序，我会先限定顺序范围，比如同一订单或同一主体互转链路内有序，再用单队列单消费者或按业务 key 路由到同一队列来保证。
```

## 六、Redis 缓存类

常见问题：

- 缓存穿透、击穿、雪崩分别是什么？
- 热点 key 过期导致 DB 被打爆怎么办？
- 缓存和数据库怎么保持一致？
- 先删缓存还是先更新数据库？
- 双写不一致怎么处理？
- Redis 分布式锁安全吗？
- 分布式锁过期了业务还没执行完怎么办？
- 大 key 有什么问题？
- 热 key 有什么问题？
- Redis 内存满了怎么办？

本质：

Redis 不是数据库的替代品。缓存问题核心是数据一致性、失效策略、并发击穿、热点隔离、内存边界和降级能力。

回答抓手：

```text
先区分缓存是旁路缓存还是强依赖数据源。
读多写少场景可以接受短暂不一致，但关键业务要有兜底查询、延迟双删、消息订阅或对账修正。
热点和大 key 要考虑拆分、限流、本地缓存、预热和过期时间打散。
```

参考回答：

```text
Redis 缓存我会先看它在系统里的定位。如果只是旁路缓存，那数据库仍然是最终数据源，缓存允许短暂不一致，但要控制不一致窗口；如果业务强依赖 Redis，就要考虑持久化、降级和恢复策略。

缓存一致性通常没有一个万能答案。常见做法是更新数据库后删除缓存，必要时做延迟双删或通过 MQ 订阅变更来修正。穿透可以用空值缓存或布隆过滤器，击穿可以用互斥锁或热点预热，雪崩可以把过期时间打散。大 key 和热 key 要重点治理，因为它们可能造成网络、内存和单节点压力。
```

## 七、线程池和异步类

常见问题：

- 为什么要用线程池？
- 线程池核心参数怎么设置？
- 线程池队列满了怎么办？
- `CompletableFuture` 用默认线程池有什么问题？
- 异步任务异常怎么处理？
- 多个异步任务部分失败怎么办？
- 线程池会不会导致 OOM？
- 线程池任务执行慢怎么排查？
- IO 密集型和 CPU 密集型线程数怎么估？
- 线程池隔离为什么重要？

本质：

线程池不是为了无限并发，而是为了控制并发、复用线程、隔离资源。线程池失控会把问题从“慢”变成“拖垮整个系统”。

回答抓手：

```text
先判断任务类型，是 CPU 密集、IO 密集，还是混合型。
再看线程池大小、队列长度、拒绝策略、任务耗时、异常处理和监控告警。
异步任务一定要定义失败语义：全成功才成功，还是允许部分成功。
```

参考回答：

```text
线程池不是为了无限加并发，而是为了控制并发和隔离资源。我会先判断任务类型，CPU 密集型线程数通常接近 CPU 核数，IO 密集型可以适当多一些，但也要看下游连接池和接口承载能力。

参数上要关注核心线程数、最大线程数、队列长度、拒绝策略和线程命名。异步任务还要特别处理异常，不能让异常被吞掉。比如批量合同打印这种场景，要先定义业务语义：是全成功才返回成功，还是允许部分成功并返回失败明细。否则 `CompletableFuture` 里失败任务被过滤掉，就可能产生静默缺失。
```

## 八、OOM、JVM 和 GC 类

常见问题：

- 线上 OOM 怎么排查？
- 日志里没有 OOM，但容器重启了，可能是什么？
- heap OOM 和容器 OOMKilled 怎么区分？
- Full GC 很频繁怎么排查？
- CPU 飙高和 GC 有什么关系？
- 为什么全量查询会导致 OOM？
- 堆内存调大是不是就能解决 OOM？
- Metaspace OOM 是什么？
- 线程太多为什么也可能导致 OOM？
- dump 文件怎么看？

本质：

OOM 不是“内存不够”四个字。要先判断是哪块内存，再判断是什么对象或资源持续增长，为什么不能释放，业务入口在哪里，最后把风险变成规则、监控和兜底。

回答抓手：

```text
先区分 Java heap、Metaspace、Direct Memory、线程栈和容器 OOMKilled。
再结合监控、GC 日志、容器事件、heap dump、MAT 和线程栈定位。
修复时不要只调大内存，要找到无边界查询、大对象、缓存无上限或资源泄漏的根因。
```

参考回答：

```text
线上 OOM 我会先判断类型，不会直接说调大堆内存。要看日志里有没有 Java heap space、Metaspace、Direct buffer memory，还是容器直接 OOMKilled。如果容器重启但应用日志没有 OOM，很可能是进程总内存超过容器限制，JVM 没来得及写完整 dump。

排查时我会结合监控曲线、GC 日志、容器事件、JVM 参数、heap dump 和 MAT 分析，确认是哪类对象占用最大、为什么还被引用。比如全量查询导致百万级数据被 MyBatis 映射成 List，当前请求持有这些对象，GC 回收不了，最终打满堆。修复时要补查询边界、分页、pageSize 上限、空集合直接返回，而不是只把内存调大。
```

## 九、接口设计和业务状态类

常见问题：

- 一个订单有哪些状态？状态流转怎么设计？
- 状态变更接口怎么防止乱跳？
- 取消订单和支付成功并发发生怎么办？
- 同一订单被两个业务员同时操作怎么办？
- 如何设计一个审批流？
- 如何设计一个导入任务？
- 如何设计一个批量处理接口？
- 如果批量任务部分成功怎么办？
- 状态机和 `if else` 有什么区别？
- 业务异常和系统异常怎么区分？

本质：

业务系统不是 CRUD。核心是状态、权限、并发、幂等、补偿、审计和可追踪。

回答抓手：

```text
先列出状态和合法流转，再定义谁能操作、什么时候能操作、重复操作怎么办。
状态变更最好通过状态机或明确的状态校验控制，不能让任意接口随便改状态。
批量任务要提前定义全成功、部分成功、失败重试和结果查询机制。
```

参考回答：

```text
设计业务状态时，我会先把状态和合法流转画出来，明确每个状态下允许哪些操作、由谁操作、重复操作怎么办。比如订单从待支付到已支付、已取消、已发货，不同状态之间不能随便跳。

接口实现上不能只根据前端传入状态直接更新，而是要在 SQL 或业务逻辑里带上当前状态条件，保证并发情况下状态不会乱跳。对于批量任务，还要提前定义结果语义：全成功才成功，还是允许部分成功；失败后能不能重试；用户关闭页面后任务是否继续；最终结果在哪里查询。
```

## 十、数据对账和修复类

常见问题：

- 两张表数据不一致怎么排查？
- 采购实提和销售实提数量不一致怎么办？
- 线上发现历史数据错了，怎么修？
- 修数据脚本怎么保证安全？
- 怎么验证修复结果？
- 对账任务怎么设计？
- 对账发现异常后自动修还是人工处理？
- 补偿任务重复执行怎么办？
- 对账 SQL 怎么避免影响线上性能？
- 数据修复有没有回滚方案？

本质：

数据修复不是写一条 `update`。要有筛选、备份、幂等、小批量、验证、回滚、审计和告警。

回答抓手：

```text
先通过对账 SQL 找出差异范围，再确认业务口径。
修复前备份，修复时小批量、可重复执行，修复后重新对账。
对于高风险数据，优先生成待处理清单，由人工确认或灰度修复。
```

参考回答：

```text
数据不一致我会先用对账 SQL 找出差异范围，但不会马上 update。第一步要确认业务口径，比如采购实提和销售实提到底应该按订单、明细、数量还是重量对齐。

修复前要备份受影响数据，最好先生成待修复清单。修复脚本要可重复执行、可小批量执行，并且每一步都能回滚或至少能追踪。修完以后要重新跑对账 SQL 验证结果。如果是核心交易数据，我更倾向先人工确认或灰度修复，再考虑自动补偿。
```

## 十一、分布式和微服务类

常见问题：

- 一个服务挂了，其他服务怎么不被拖垮？
- 下游接口超时，怎么降级？
- 熔断和限流有什么区别？
- 服务调用链很长，怎么排查问题？
- 分布式事务怎么解决？
- TCC、Saga、本地消息表有什么区别？
- 如何保证接口重试不会放大故障？
- 配置中心改错配置怎么办？
- 注册中心异常会影响已有调用吗？
- 微服务拆分过细有什么问题？

本质：

分布式系统最大的问题是局部失败。一个点慢、一个点挂、一个点重试失控，都可能放大成全链路故障。

回答抓手：

```text
先设置超时，再控制重试，必要时做熔断、限流和降级。
分布式事务不要一上来就说强一致，要结合业务判断是否能接受最终一致。
调用链长时，要依赖 traceId、链路追踪、日志、监控和告警定位。
```

参考回答：

```text
分布式系统里我会先默认下游可能失败，所以调用一定要有超时，重试要有次数和退避策略，不能无限重试。下游慢或者挂了时，要通过熔断、限流、降级保护自己，避免一个服务拖垮整条链路。

一致性方面要看业务要求。如果不是强一致场景，可以用本地事务 + 消息 + 补偿 + 对账实现最终一致；如果强一致要求很高，再考虑 TCC 等方案，但成本会更高。调用链很长时，traceId、链路追踪、统一日志和监控告警很重要，否则很难定位到底卡在哪个服务。
```

## 十二、文件和批处理类

常见问题：

- 批量导入 10 万行 Excel 怎么设计？
- 大文件上传怎么处理？
- 文件下载很慢怎么优化？
- 批量生成 PDF 超时怎么办？
- 多文件合并时内存会不会爆？
- 任务执行一半失败怎么办？
- 用户关闭页面任务还要继续吗？
- 怎么查看任务进度？
- 批处理任务怎么防止重复执行？
- 批处理如何限流？

本质：

批处理不要用同步接口硬扛。要考虑任务化、分页或分片、流式处理、进度记录、失败重试、结果可查询和资源限制。

回答抓手：

```text
小批量可以同步处理，大批量应该任务化。
任务表记录状态、进度、失败原因和结果文件。
处理过程要分批、限流、可重试，并避免一次性把大文件或大集合加载进内存。
```

参考回答：

```text
批处理我不会默认用一个同步接口硬扛。如果数据量小，可以同步返回；如果是 10 万行 Excel、批量 PDF、批量导入导出这种场景，更适合任务化处理，接口先返回 taskId，后台异步执行。

任务表需要记录状态、进度、成功数、失败数、失败原因和结果文件地址。处理时要分批读取、分批提交，避免一次性把大文件或大集合加载进内存。失败时要能重试，重复执行要幂等，用户关闭页面后也能通过任务记录查到最终结果。
```

## 四字主线

遇到奇怪应用题时，可以先归类成四个字：

```text
慢：接口慢、SQL 慢、线程池、连接池、下游慢
乱：并发更新、重复提交、状态乱跳、数据不一致
丢：MQ 丢消息、事务提交后消息没发、回调丢失
爆：OOM、连接池爆、线程池爆、Redis 热点、DB 被打爆
```

每次回答前先问自己五个问题：

```text
这个问题背后的资源是什么？
边界在哪里？
失败会发生在哪一步？
重复执行会不会有问题？
数据最终怎么校验回来？
```

这五个问题问完，答案通常就不会飘。
