# 高可用强一致性的设计思路

## 场景

在招聘软件上看到订单履约类 Java 后端岗位时，经常会看到这样的要求：

- 有订单从创建到完成履约的全流程经验。
- 熟悉订单审核、库存扣减、物流调度、异常订单处理。
- 有订单履约系统性能优化、高并发处理、数据一致性保障经验。
- 能独立设计并实现高可用的履约流程方案。

这些要求和我现在的工作方向比较接近。我长期参与 B2B 电商交易履约、库存、实提、结算等业务系统建设，也做过主体互转、提货履约、实提链路、SQL 优化、线上问题排查等工作。

但对于“高并发”和“强一致性”这两个词，我之前总觉得有点虚。因为我们系统实际订单并发并不算特别高，一天大概几千单，月订单量较大，但不是秒杀那种瞬时高并发场景。

我的真实经验更多是：

- 库存明细有入库数量、挂牌锁定数量、出库锁定数量等字段。
- 可用库存通过库存总量减去各种锁定数量计算。
- 修改库存时最终还是依赖数据库条件更新、事务和约束保证正确性。
- 履约链路中会通过状态字段、流水、数据比对 SQL、异常补偿来保障数据一致。

所以这个问题的关键不是硬说自己做过很高的并发，而是要能讲清楚：

> 如果订单和库存并发量上来了，我会从哪里开始设计，如何一步一步保证系统既正确，又能逐步提高可用性和吞吐量。

## 当时的理解

我最开始的理解是：

> 高并发或者强一致性，最终依赖的就是数据库的 `update` 和事务操作。

这个理解是对的，但还不够完整。

在单库、单业务边界内，数据库确实是强一致性的最后防线。比如库存扣减不能只靠 Java 代码里先查再判断，因为两个线程可能同时查到可用库存足够，然后同时扣减。

更稳的方式是把判断和修改放到同一条 SQL 里：

```sql
UPDATE inventory_detail
SET sale_lock_count = sale_lock_count + #{lockCount}
WHERE id = #{id}
  AND total_count - sale_lock_count - outbound_lock_count >= #{lockCount};
```

这条 SQL 的核心不是“更新字段”，而是：

- `WHERE` 条件表达业务约束。
- 数据库行锁保证同一行并发更新会串行执行。
- 受影响行数为 1 代表锁定成功。
- 受影响行数为 0 代表库存不足或并发下已经被别人占用。

所以强一致性在最底层通常依赖：

- 数据库事务
- 行锁
- 条件更新
- 唯一约束
- 外键或业务约束
- 合理的隔离级别

但是，如果回答只停留在“数据库事务 + update”，面试官很可能继续追问：

- 并发量很高时，数据库扛不住怎么办？
- 行锁竞争严重怎么办？
- 分布式锁能不能替代数据库事务？
- MQ 异步之后还算强一致吗？
- 跨系统调用失败怎么办？
- 重复请求、重复消费、超时重试怎么处理？
- 如何设计高可用，而不是只有正确性？

所以更完整的思路应该是分层设计。

## 关键原理

### 1. 先明确一致性边界

设计强一致性之前，第一步不是选 Redis、MQ 或分布式锁，而是先问：

> 哪些数据必须在同一个事务里同时成功或同时失败？

比如订单履约和库存场景里，可能有几类动作：

- 创建订单
- 锁定库存
- 写库存流水
- 写履约状态
- 发送 MQ
- 通知外部系统
- 生成出库凭证
- 结算

这些动作不一定都要放在一个事务里。

真正需要强一致的，通常是本地核心状态：

- 订单主状态
- 库存锁定数量
- 库存流水
- 幂等记录
- 本地消息表

而外部通知、日志记录、后续履约节点推进，可以通过 MQ、回调、补偿任务做最终一致。

所以要先把链路拆成两类：

| 类型 | 示例 | 一致性策略 |
| --- | --- | --- |
| 核心写入 | 订单创建、库存锁定、流水记录 | 本地事务强一致 |
| 后续动作 | 通知、推送、异步生成、跨系统流转 | MQ + 幂等 + 重试 + 补偿 |

面试回答时可以这样说：

> 我会先划清一致性边界。对于订单状态、库存锁定、库存流水这类必须同时正确的数据，会放在同一个本地事务里保证强一致；对于通知、推送、跨系统流转这类动作，不放在主事务里，而是通过 MQ、幂等、重试和补偿保证最终一致。

### 2. 正确性优先，数据库是最后防线

单库场景下，强一致性的最终依赖通常就是数据库层面的事务和约束。

常见手段包括：

| 手段 | 解决的问题 |
| --- | --- |
| 条件更新 | 防止超扣、超卖、并发覆盖 |
| 事务 | 保证多张表、多条记录一起提交或回滚 |
| 唯一约束 | 防止重复下单、重复请求、重复消费 |
| 行锁 | 保证同一行并发修改串行化 |
| 乐观锁版本号 | 防止并发覆盖，适合冲突不高场景 |
| 库存流水 | 方便追踪、对账和修复 |

例如库存预占可以这样做：

```sql
BEGIN;

UPDATE inventory_detail
SET sale_lock_count = sale_lock_count + 5
WHERE id = 1001
  AND total_count - sale_lock_count - outbound_lock_count >= 5;

-- 判断影响行数，影响行数为 0 则回滚

INSERT INTO inventory_lock_record (
  biz_no,
  inventory_detail_id,
  lock_count,
  status
) VALUES (
  'ORDER_001',
  1001,
  5,
  'LOCKED'
);

COMMIT;
```

这里需要注意：

- 不能先查库存再在 Java 里判断后更新。
- 不能只依赖 Redis 锁判断库存是否足够。
- 不能没有流水，否则后续很难排查库存为什么变了。
- 不能没有幂等键，否则重试可能重复锁库存。

### 3. 减小锁粒度，避免把大链路锁住

数据库事务能保证正确性，但事务不是越大越好。

高并发场景下，很多问题不是“没有锁”，而是“锁太大、锁太久”。

例如下面这些操作不应该放进库存事务里：

- 远程调用外部系统
- 发送 HTTP 请求
- 调用第三方接口
- 等待 MQ 确认
- 大量复杂查询
- 文件生成
- 慢 SQL

因为事务开启后，数据库锁会一直持有。如果事务里包含慢操作，就会导致：

- 行锁持有时间变长
- 后续请求排队等待
- 数据库连接被占用
- 连接池耗尽
- 接口超时
- 上游继续重试，进一步放大压力

所以要减小锁粒度：

- 只锁必要的库存明细行。
- 只在事务里做核心写操作。
- 事务内 SQL 尽量短、快、可命中索引。
- 不在事务里调用外部接口。
- 不把整个订单履约链路放进一个大事务。
- 可以按订单号、库存明细、会员、仓库等维度缩小影响范围。

一句话：

> 强一致性依赖数据库事务，但高可用要求我们把事务做小、把锁粒度做细、把锁持有时间做短。

### 4. 用幂等兜住重复请求和重试

高并发场景里，重复请求非常常见：

- 用户重复点击
- 前端超时重试
- 网关重试
- MQ 重复投递
- 定时任务补偿重复执行
- 接口调用方不知道服务端是否成功，于是再次请求

如果没有幂等，强一致性很容易被重复操作破坏。

常见幂等设计：

| 场景 | 幂等键 |
| --- | --- |
| 创建订单 | 业务请求号、外部订单号 |
| 锁库存 | 订单号 + 库存明细 ID |
| MQ 消费 | 消息 ID、业务单号 + 消息类型 |
| 回调处理 | 回调流水号、业务单号 + 状态 |
| 支付/结算 | 支付单号、结算单号 |

数据库唯一约束是很可靠的幂等兜底：

```sql
ALTER TABLE inventory_lock_record
ADD UNIQUE KEY uk_biz_inventory (biz_no, inventory_detail_id);
```

应用层可以先查，但不能只靠先查。真正防重复的最后一层应该是唯一约束。

面试时可以说：

> 我会把幂等作为一致性设计的一部分，而不是只作为接口防重复。尤其是 MQ 消费、库存锁定、回调处理这类场景，会用业务唯一键和数据库唯一约束兜底，保证重复请求不会造成重复扣减或重复推进状态。

### 5. 分布式锁是辅助，不是最终正确性来源

Redis 分布式锁经常会被问到，但要注意表达边界。

分布式锁适合：

- 降低同一资源的并发冲突。
- 避免大量请求同时打到数据库。
- 保护某些不能并发执行的业务流程。
- 控制同一订单、同一库存明细、同一会员维度的并发操作。

但分布式锁不应该替代数据库条件更新和唯一约束。

原因是：

- 锁可能超时释放。
- 业务执行时间可能超过锁过期时间。
- 网络抖动可能导致锁状态判断不准。
- 应用异常退出可能影响锁释放。
- 不同入口如果没有统一加锁，仍然可能绕过锁。

所以更稳的表达是：

> 分布式锁可以作为前置削峰和并发控制手段，但最终正确性仍然依赖数据库的条件更新、事务和唯一约束。即使 Redis 锁失效，数据库层也不能允许超扣或重复写入。

### 6. 高并发上来后，先削峰，再拆热点

如果并发量明显上升，不是所有问题都靠加机器解决。

订单和库存系统的压力通常来自几个点：

- 同一库存明细被大量并发占用。
- 同一会员或同一订单被重复操作。
- 下单链路里同步动作太多。
- 数据库热点行更新频繁。
- 慢 SQL 和长事务导致连接池堆积。
- MQ 消费速度跟不上生产速度。

可以从以下方向优化。

#### 6.1 主流程变短

下单或履约主流程只做最核心的事：

- 参数校验
- 幂等校验
- 订单核心状态落库
- 库存预占
- 写业务流水
- 写本地消息或发送 MQ

非核心动作异步化：

- 通知
- 统计
- 推送
- 文件生成
- 非关键状态同步
- 后续履约节点推进

#### 6.2 MQ 削峰

对于不要求立即同步完成的动作，可以通过 MQ 削峰。

但 MQ 引入的是最终一致，不是天然强一致。所以必须配套：

- 消费幂等
- 失败重试
- 死信队列
- 补偿任务
- 消息状态记录
- 业务对账

如果主流程落库成功，但消息发送失败，可以考虑本地消息表：

```text
本地事务：
1. 更新订单状态
2. 锁定库存
3. 写库存流水
4. 写待发送消息表

事务提交后：
1. 后台任务扫描消息表
2. 发送 MQ
3. 消费方幂等处理
4. 成功后更新消息状态
```

这样可以避免“业务数据提交了，但消息没发出去”的问题。

#### 6.3 热点库存拆分

如果大量请求都更新同一行库存，就会形成热点行。

可以考虑：

- 按仓库、批次、库存明细拆分库存。
- 对热点库存做库存分桶。
- 将一个大库存拆成多个可并发扣减的库存段。
- 请求先路由到不同库存桶，降低单行锁竞争。

例如原来只有一行：

```text
SKU_A total_count = 10000
```

可以拆成多个桶：

```text
SKU_A bucket_1 total_count = 1000
SKU_A bucket_2 total_count = 1000
SKU_A bucket_3 total_count = 1000
...
```

这样并发请求不再全部竞争同一行。

当然，库存分桶会增加复杂度：

- 查询总库存要聚合。
- 某个桶不足时要换桶。
- 退回库存要找到原桶。
- 对账和修复更复杂。

所以只有在热点行竞争真的明显时才需要做。

#### 6.4 同一资源队列化

对于强顺序要求的场景，可以按业务维度队列化。

例如：

- 同一订单的状态推进必须顺序执行。
- 同一主体互转链路必须按节点顺序执行。
- 同一库存明细的复杂操作不希望并发交错。

可以按 key 路由：

```text
orderId % queueCount
inventoryId % queueCount
relationId % queueCount
```

这样同一个业务 key 进入同一个队列，保证局部顺序；不同 key 分散到不同队列，提高整体吞吐。

这比“全局单队列单消费者”更可扩展。

### 7. 状态机防止状态乱跳

订单履约不是只有库存扣减，还有状态流转。

比如：

```text
待审核 -> 已审核 -> 待出库 -> 已出库 -> 已收货 -> 已结算
```

高并发或重复回调下，可能出现：

- 已取消订单又被推进履约。
- 已出库订单重复出库。
- 已结算订单再次结算。
- 中间状态被跳过。

所以需要状态机思维：

```sql
UPDATE delivery_order
SET status = 'OUTBOUND'
WHERE order_no = #{orderNo}
  AND status = 'APPROVED';
```

这条 SQL 表达的是：

> 只有当前状态是已审核，才允许变成已出库。

如果影响行数为 0，就说明状态已经变化，当前操作不能继续。

这比先查状态再在 Java 里判断更稳。

### 8. 高可用不是不失败，而是失败可恢复

很多时候，高可用不是保证每一步都不失败，而是保证失败以后：

- 能重试
- 能补偿
- 能对账
- 能定位
- 能降级
- 不会把数据写乱

订单履约系统尤其需要这些能力：

| 能力 | 作用 |
| --- | --- |
| 业务流水 | 知道每次库存和状态为什么变化 |
| 操作日志 | 知道谁在什么时候做了什么 |
| 链路追踪 | 知道一次请求经过哪些服务 |
| 对账 SQL | 发现订单、库存、实提、结算之间的数据不一致 |
| 补偿任务 | 对失败或中断的流程继续推进 |
| 告警 | 在异常扩大前发现问题 |
| 人工修复入口 | 处理少量无法自动修复的异常数据 |

所以面试时不要只讲“怎么防止失败”，还要讲“失败后怎么恢复”。

## 更多思考

### 设计可以按五层推进

面对“高并发 + 强一致性”的问题，可以按这个顺序推演：

```text
第一层：正确性
数据库事务、条件更新、唯一约束、状态机，保证数据不能错。

第二层：幂等性
请求幂等、消息幂等、回调幂等，保证重复执行不会重复生效。

第三层：锁粒度
缩短事务、缩小锁范围、避免大事务、避免事务内远程调用。

第四层：吞吐量
MQ 削峰、异步化、热点拆分、按 key 分片、局部队列化。

第五层：可恢复
流水、日志、对账、补偿、告警、人工修复，保证失败可追踪可恢复。
```

这样回答会比直接说“用分布式锁”更有层次。

### Redis、MQ、数据库分别负责什么

| 组件 | 更适合负责 | 不适合负责 |
| --- | --- | --- |
| MySQL | 最终正确性、事务、约束、核心状态 | 承接所有高峰流量 |
| Redis | 缓存、限流、分布式锁、热点前置保护 | 替代数据库最终约束 |
| MQ | 削峰、解耦、最终一致、异步推进 | 保证天然强一致 |
| 定时任务 | 补偿、重试、对账扫描 | 替代实时正确性 |

可以记一句：

> MySQL 兜正确性，Redis 降冲突，MQ 做削峰，任务做补偿，对账发现问题。

### 面试官问“你们系统怎么做的”可以这样答

> 我们系统实际不是秒杀类高并发，但订单履约和库存一致性要求比较高。库存不是简单扣一个可用数字，而是通过入库数量、挂牌锁定数量、出库锁定数量等字段表达库存占用状态，可用库存由这些字段计算。真正更新时会通过数据库条件更新和事务保证，比如在 `update` 条件里判断可用数量是否足够，更新成功才认为锁定成功，失败则说明库存不足或并发下已经被其他操作占用。同时会记录业务流水和状态字段，后续通过数据比对 SQL、日志排查和异常补偿保障履约链路的数据一致性。

### 面试官问“如果并发量上来了怎么办”可以这样答

> 如果并发量上来，我会先保证数据库层面的正确性不变，核心还是条件更新、事务、唯一约束和状态机，不能因为加了 Redis 或 MQ 就放松数据库兜底。然后会减小事务范围，避免在事务里做远程调用或慢操作，尽量缩短锁持有时间。  
>
> 在吞吐上，可以把非核心动作异步化，用 MQ 做削峰；对于同一订单或同一库存明细这类有顺序要求的资源，可以按业务 key 分片或队列化处理；如果出现热点库存行竞争，可以考虑库存拆分或分桶。最后配合幂等、失败重试、补偿任务、业务流水和定时对账，保证即使某个异步环节失败，也能被发现和恢复。

### 面试官问“分布式锁能不能解决库存一致性”可以这样答

> 分布式锁可以降低并发冲突，但我不会把它作为最终正确性的唯一来源。因为锁可能超时、释放失败，或者某些入口没有统一加锁。库存扣减最终还是要依赖数据库条件更新，比如 `update ... where 可用库存 >= 本次扣减数量`。这样即使锁失效，数据库层也不会允许超扣。Redis 锁更多是前置保护，用来减少无效竞争和数据库压力。

### 面试官问“MQ 异步之后怎么保证一致性”可以这样答

> MQ 异步之后一般就是最终一致，而不是一个本地事务里的强一致。我的思路是主流程先在本地事务里落核心状态和本地消息记录，事务提交后再投递 MQ。消费方要做幂等，消费失败要有重试和死信处理，长期失败的数据通过补偿任务扫描，另外通过对账 SQL 发现订单、库存、履约数据之间的不一致。这样可以避免业务状态成功了但后续流程丢失。

### 面试官问“怎么减小锁粒度”可以这样答

> 我会从三个方面减小锁粒度。第一，锁定对象尽量具体，比如只锁库存明细行，而不是锁整个商品或整个订单链路。第二，事务范围只包含核心数据库写入，不在事务里做远程调用、文件生成、复杂查询等慢操作。第三，SQL 要命中索引，避免因为慢 SQL 导致行锁或连接长时间占用。对于热点资源，可以再通过分桶、分片队列等方式降低同一行的竞争。

## 总结

- 强一致性的最后防线通常是数据库层面的事务、条件更新、行锁、唯一约束和状态约束。
- Redis 分布式锁、MQ、缓存都可以提升性能和可用性，但不能替代数据库最终正确性。
- 高并发设计不能只讲“加锁”，还要讲锁粒度、事务范围、热点拆分、异步削峰和失败恢复。
- 订单履约系统要特别关注幂等、状态机、库存流水、异常补偿和数据对账。
- 面试时可以诚实说明实际并发不算秒杀级，但要体现自己知道并发上来后系统应该如何演进。

最终可以记住这句话：

> 高并发解决的是压力问题，强一致性解决的是正确性问题，高可用解决的是失败后还能不能恢复。真正的设计顺序应该是先保证数据不能错，再考虑如何把流程做短、把锁做细、把流量削平、把失败补回来。
