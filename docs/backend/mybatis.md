# MyBatis 实践

## 场景：复杂查询需要可读，也需要可验证

在某批量对账任务中，需要按业务单号、状态范围、时间窗口和关联关系查询差异数据。这个查询不适合完全交给通用 ORM 推断，因为字段口径、关联条件和排序方式都需要明确表达。

MyBatis 的优势是 SQL 可控，但可控不等于可以无限堆条件。复杂 SQL 一旦没有边界，后续排查会变成“没人敢改”。

## 设计原则：先定口径，再写动态条件

我会先确认查询要回答的问题：

- 主数据来源是哪张表。
- 哪些状态应该纳入，哪些状态必须排除。
- 数量、重量、金额字段分别来自哪里。
- 一对多关系是否会放大行数。
- 查询结果是用于页面展示、批量处理还是修复核对。

确认口径后再写动态 SQL，避免为了兼容所有场景，把不相关的业务条件塞进同一个 Mapper 方法。

## 实践：让 Mapper 方法有明确责任

我更倾向于把 Mapper 方法拆到“业务问题”级别，而不是做一个万能查询。例如：

- 用于对账差异查询的方法，只返回差异判断需要的字段。
- 用于明细展示的方法，可以补充展示字段，但不承载修复判断。
- 用于批量处理的方法，必须带分页或游标式边界，避免一次扫过大范围数据。

动态条件也要有默认边界。时间范围、状态集合、业务模式这类条件不能默认无限放开；如果确实允许为空，需要在调用层有明确理由。

## 常见问题与处理

| 问题 | 风险 | 处理方式 |
| --- | --- | --- |
| 参数为空导致范围扩大 | 批量任务误处理过多数据 | 在入参层校验必要条件 |
| 一对多关联重复行 | 数量统计被放大 | 先聚合或拆分查询 |
| 动态条件过多 | 排查时难以复现 SQL | 给核心条件写清楚命名和注释 |
| 大范围查询无分页 | 影响数据库稳定性 | 固定批量大小并记录游标 |
| 字段别名含糊 | 结果映射误读 | 使用能表达业务含义的别名 |

## 验证方式

复杂 SQL 上线前，我会用小样本验证：

1. 选一条正常数据，确认查询能返回预期字段。
2. 选一条异常数据，确认差异条件能命中。
3. 选一条边界状态数据，确认不会被误纳入。
4. 对一对多场景核对行数和聚合结果。
5. 查看执行计划，确认关键过滤条件能使用索引。

## 总结

MyBatis 写得好不好，不只看 SQL 能不能跑通，还要看口径是否清楚、边界是否稳定、结果是否可验证。复杂查询最需要克制：一个 Mapper 方法只解决一个明确问题。
