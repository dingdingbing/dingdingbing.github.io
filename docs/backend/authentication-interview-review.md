# 登录认证面试复盘：Cookie、Session、JWT 和有状态/无状态

这篇文章来自一次面试复盘。

面试中被问到登录认证模块时，我的回答是：系统当时已经构建好了，我没有从 0 到 1 设计过登录认证。后面面试官继续提示了有状态的 `Session` 和无状态的 `Cookie/JWT` 方向，但我没有把 JWT、Cookie、Session、有状态/无状态这些概念讲清楚。

这说明一个问题：即使项目里没有主导做过登录模块，Java 后端也需要理解登录认证的基本原理。因为这类问题不只是考登录功能，而是在考 HTTP、分布式、缓存、安全、网关、权限校验这些基础能力。

## 面试官到底想问什么

登录认证这个问题，面试官通常不是只想问“你会不会写一个登录接口”。

他可能想继续追问：

- 用户登录成功后，服务端怎么记住这个用户？
- Cookie 和 Session 是什么关系？
- 什么是有状态登录？什么是无状态登录？
- JWT 是什么？由哪几部分组成？
- JWT 为什么适合分布式系统？
- JWT 有什么缺点？怎么让 Token 失效？
- 单点登录怎么做？
- 权限校验放在哪里？网关、拦截器还是业务服务？
- Token 被盗怎么办？
- Refresh Token 和 Access Token 有什么区别？

所以这块要准备的不是一个点，而是一条完整链路：

```text
登录 -> 签发凭证 -> 客户端保存 -> 请求携带 -> 服务端校验 -> 获取用户身份 -> 权限判断 -> 续期/退出/失效
```

## 问题

你们系统登录认证是怎么做的？

## 我的回答

当时我的回答大概是：

```text
这块系统当时已经搭建好了，我没有从 0 到 1 负责过登录认证模块。我们平时更多是使用已有的登录态，在业务接口里拿当前用户信息，做权限或者数据隔离。
```

这个回答真实，但不够好。因为面试官可以接受“不是你主导的”，但会继续看你是否理解原理。

## 最终答案

如果确实没有主导做过登录认证，可以这样回答：

```text
登录认证模块在我们系统里不是我从 0 到 1 搭建的，但我理解它的核心链路。

用户登录时，服务端校验账号密码或第三方登录凭证。校验通过后，会给客户端一个登录凭证。后续客户端每次请求都带上这个凭证，服务端通过这个凭证识别当前用户，再做权限校验和业务数据隔离。

实现方式主要有两类：一种是基于 Session 的有状态认证，服务端保存登录状态，客户端 Cookie 里只保存 sessionId；另一种是基于 Token/JWT 的无状态认证，服务端签发 Token，客户端每次请求携带 Token，服务端通过验签和解析 Token 获取用户身份。

如果是单体或传统后台系统，Session 实现简单；如果是微服务、前后端分离、移动端或者多端接入，JWT 或统一认证中心会更常见。
```

## 纠正与优化

- 可以承认“不是自己主导搭建”，但不能停在那里。
- 要把登录认证抽象成“凭证签发和凭证校验”。
- 面试官提示 Session/JWT 时，要顺着讲“有状态/无状态”。

## Cookie 是什么

## 问题

Cookie 是什么？它是有状态还是无状态？

## 我的回答

容易把 Cookie、Session、JWT 混在一起。

## 最终答案

Cookie 是浏览器保存的一小段数据。

它由服务端通过响应头设置：

```http
Set-Cookie: JSESSIONID=abc123; HttpOnly; Path=/
```

之后浏览器访问同一个域名时，会自动把 Cookie 带上：

```http
Cookie: JSESSIONID=abc123
```

Cookie 本身不是认证方案，它只是客户端保存和自动携带数据的一种机制。

Cookie 里可以放：

- `sessionId`
- 登录 Token
- 用户偏好设置
- 跟踪标识

面试可以这样说：

```text
Cookie 是浏览器端的存储和自动携带机制。它本身不等于登录认证。传统 Session 登录里，Cookie 通常保存 sessionId；JWT 登录里，也可以把 Token 放在 Cookie 里，但更多前后端分离项目会放在请求头 Authorization 里。
```

## 纠正与优化

- Cookie 不等于 Session。
- Cookie 不一定有状态，也不一定无状态，它只是承载凭证的方式。
- 是否有状态，要看服务端是否保存登录状态。

## Session 有状态认证

## 问题

Session 登录流程是什么？为什么说它是有状态的？

## 我的回答

面试官提示了有状态 Session，但当时没有完整说出流程。

## 最终答案

Session 登录流程：

1. 用户提交用户名和密码。
2. 服务端校验成功。
3. 服务端创建 Session，把用户信息放到服务端内存、Redis 或其他存储里。
4. 服务端返回 Cookie，Cookie 里保存 `sessionId`。
5. 浏览器后续请求自动携带 `sessionId`。
6. 服务端根据 `sessionId` 查 Session，拿到用户身份。
7. 如果 Session 存在且未过期，请求通过；否则要求重新登录。

为什么说它有状态？

```text
因为服务端保存了登录状态。客户端只保存 sessionId，真正的用户登录信息在服务端。
```

优点：

- 服务端可控，退出登录和踢人比较容易。
- 可以随时修改 Session 状态。
- 传统 Web 系统实现简单。

缺点：

- 分布式部署时需要 Session 共享。
- 如果 Session 存在应用内存里，请求打到另一台机器可能拿不到登录态。
- 大量用户在线时，服务端存储压力更大。

分布式场景常见方案：

- Session 存 Redis。
- Nginx 做粘性会话，但扩展性不如 Redis Session。
- 改用 Token/JWT 或统一认证中心。

## 纠正与优化

- 有状态不是说 HTTP 有状态，而是服务端保存用户登录状态。
- Session 可以存在内存，也可以存在 Redis；分布式系统里通常不会只放本机内存。

## JWT 无状态认证

## 问题

JWT 是什么？为什么说它是无状态的？

## 我的回答

JWT 当时基本没有回答上来。

## 最终答案

JWT 全称是 JSON Web Token，它是一种 Token 格式，通常由三部分组成：

```text
Header.Payload.Signature
```

例如：

```text
xxxxx.yyyyy.zzzzz
```

三部分含义：

- `Header`：声明 Token 类型和签名算法，比如 `HS256`、`RS256`。
- `Payload`：保存用户信息和过期时间等声明，比如 userId、tenantId、roles、exp。
- `Signature`：签名，用来防止 Token 被篡改。

JWT 登录流程：

1. 用户登录，服务端校验账号密码。
2. 服务端生成 JWT，把用户 ID、角色、过期时间等放入 Payload。
3. 服务端用密钥或私钥对 Header 和 Payload 做签名。
4. 客户端保存 JWT。
5. 后续请求在请求头里携带：

```http
Authorization: Bearer <token>
```

6. 服务端校验签名和过期时间。
7. 校验通过后，从 Payload 中解析用户身份。

为什么说它无状态？

```text
因为服务端不需要保存登录 Session，只要能验证 Token 签名，就能确认 Token 是否可信，并解析出用户身份。
```

## 纠正与优化

- JWT 不是加密。默认情况下 Header 和 Payload 只是 Base64Url 编码，能被解析看到。
- JWT 的核心是签名防篡改，不是隐藏内容。
- 不要在 JWT Payload 里放密码、手机号、身份证等敏感信息。

## Session 和 JWT 对比

| 对比项 | Session | JWT |
| --- | --- | --- |
| 登录状态 | 服务端保存 | 服务端通常不保存 |
| 客户端保存 | sessionId | token |
| 服务端校验 | 根据 sessionId 查 Session | 验签、校验过期时间 |
| 扩展性 | 分布式需要共享 Session | 多服务只要共享验签密钥或公钥 |
| 退出登录 | 服务端删除 Session 即可 | 需要黑名单、短过期时间等机制 |
| 服务端控制 | 强 | 弱一些 |
| 适合场景 | 传统 Web、后台系统 | 前后端分离、微服务、移动端、多端接入 |

面试可以这样说：

```text
Session 是有状态方案，服务端保存登录态，客户端 Cookie 保存 sessionId。JWT 是无状态方案，服务端签发 Token，后续通过验签解析用户身份，不需要每次查 Session。

Session 的优点是服务端可控，退出和踢人简单；JWT 的优点是扩展性好，适合微服务和多端接入。但 JWT 一旦签发，在过期前天然不容易主动失效，所以通常要配合短过期时间、Refresh Token、黑名单或版本号机制。
```

## JWT 如何失效

## 问题

JWT 无状态，那用户退出登录怎么办？

## 我的回答

当时没有回答。

## 最终答案

JWT 的一个典型难点就是主动失效。

常见方案：

1. 设置较短过期时间。
2. 使用 Access Token + Refresh Token。
3. 退出登录时把 Token 加入黑名单，黑名单放 Redis。
4. 用户表维护 tokenVersion 或 passwordVersion，JWT 里带版本号，服务端校验版本是否一致。
5. 修改密码、封禁用户时，更新版本号或加入黑名单。

面试可以这样说：

```text
JWT 本身偏无状态，所以主动失效比 Session 麻烦。常见做法是 Access Token 设置短有效期，Refresh Token 用来续期；如果需要立即退出或踢人，可以把 Token jti 放入 Redis 黑名单，或者在用户表维护 tokenVersion，校验 Token 里的版本号是否仍然有效。
```

## 纠正与优化

- 不要说“JWT 退出登录就是前端删除 Token”，这只能让当前客户端不再使用 Token，不能阻止被盗 Token 继续访问。
- 对安全要求高的系统，要有服务端失效机制。

## Access Token 和 Refresh Token

## 问题

为什么要区分 Access Token 和 Refresh Token？

## 我的回答

当时没有展开。

## 最终答案

Access Token 用来访问接口，生命周期短。

Refresh Token 用来换取新的 Access Token，生命周期更长，安全要求更高。

这样设计的原因：

- Access Token 短，泄露后的风险窗口小。
- Refresh Token 不需要每次请求都带，只在续期时使用。
- 服务端可以对 Refresh Token 做存储、轮换、失效控制。

流程：

```text
登录成功 -> 返回 Access Token + Refresh Token
访问接口 -> 带 Access Token
Access Token 过期 -> 用 Refresh Token 换新 Access Token
退出登录/风控 -> 让 Refresh Token 失效
```

面试可以这样说：

```text
Access Token 负责接口访问，过期时间短；Refresh Token 负责续期，过期时间长但使用频率低。这样可以兼顾用户体验和安全性。
```

## 权限认证和权限授权

## 问题

认证和授权有什么区别？

## 我的回答

以前容易把登录和权限都叫“认证”。

## 最终答案

认证是 Authentication：

```text
你是谁？
```

授权是 Authorization：

```text
你能做什么？
```

登录认证解决的是用户身份问题，比如 userId 是多少。

权限授权解决的是访问控制问题，比如这个 userId 能不能访问这个菜单、接口、数据范围。

面试可以这样说：

```text
认证是确认用户身份，授权是判断用户是否有权限访问某个资源。登录成功只能说明用户可信，不代表他能访问所有接口。后续还要基于角色、权限点、数据范围做授权校验。
```

常见权限模型：

- 用户。
- 角色。
- 权限点。
- 菜单。
- 数据范围。

常见实现位置：

- 网关统一认证 Token。
- 业务服务解析用户上下文。
- 拦截器或过滤器做接口权限校验。
- 业务代码做数据权限校验。

## 登录认证在微服务里怎么做

## 问题

微服务系统里登录认证放在哪里？

## 我的回答

当时没有系统回答。

## 最终答案

微服务里常见做法：

1. 认证中心负责登录、发 Token、刷新 Token、退出登录。
2. 网关统一校验 Token，拦截未登录请求。
3. 网关把用户 ID、租户 ID、角色等信息放到请求头传给下游服务。
4. 下游服务信任网关来源，同时做必要的业务权限和数据权限校验。
5. 服务之间调用也要考虑内部鉴权，避免绕过网关。

面试可以这样说：

```text
微服务里一般不会每个服务都自己做登录，而是由认证中心负责登录和签发 Token，网关统一做 Token 校验。校验通过后，网关把用户上下文传给下游服务。下游服务再结合自己的业务做权限和数据范围判断。
```

注意点：

- 下游服务不能盲目信任任意请求头，最好只信任来自网关的请求。
- 内部服务接口也要有访问控制。
- 用户上下文传递要避免被伪造。

## 面试追问清单

这类题可能继续追问：

### Cookie 和 Session 有什么区别？

```text
Cookie 存在客户端，Session 存在服务端。Cookie 可以保存 sessionId，服务端再通过 sessionId 找到对应 Session。Cookie 是一种客户端存储和传输机制，Session 是服务端保存用户状态的一种机制。
```

### JWT 能不能存敏感信息？

```text
不建议。JWT 的 Payload 默认只是 Base64Url 编码，不是加密，客户端和中间人拿到 Token 后都可以解析内容。敏感信息不要放进 Payload。
```

### JWT 被篡改怎么办？

```text
JWT 有签名。服务端校验签名时，如果 Header 或 Payload 被改过，签名就对不上，请求会被拒绝。
```

### Token 被盗怎么办？

```text
可以缩短 Access Token 有效期，使用 Refresh Token 续期；服务端维护黑名单或 tokenVersion；重要操作二次校验；传输必须使用 HTTPS；前端存储要尽量降低 XSS 风险。
```

### Cookie 放 Token 有什么风险？

```text
Cookie 会自动携带，可能有 CSRF 风险，所以要配合 SameSite、CSRF Token、Origin/Referer 校验等措施。Cookie 如果没有 HttpOnly，可能被 XSS 读取。
```

### Token 放 localStorage 有什么风险？

```text
localStorage 不会自动携带，CSRF 风险低一些，但如果页面存在 XSS，攻击脚本可以直接读取 Token。所以无论放哪里，都要重视 XSS 防护。
```

### 登录接口如何防暴力破解？

```text
可以做账号或 IP 维度限流，连续失败锁定，验证码，风险设备识别，登录日志和告警。密码存储不能明文，要加盐哈希。
```

## 面试速记

可以背这段：

```text
登录认证本质是服务端给客户端签发一个凭证，后续客户端请求带上凭证，服务端根据凭证识别用户身份。

传统 Session 是有状态方案，服务端保存 Session，客户端 Cookie 只保存 sessionId。优点是服务端控制强，退出和踢人方便；缺点是分布式下需要 Session 共享。

JWT 是无状态 Token，通常由 Header、Payload、Signature 三部分组成。服务端通过验签确认 Token 没有被篡改，再从 Payload 解析用户身份。它适合前后端分离和微服务，但主动失效比 Session 麻烦，需要短过期时间、Refresh Token、黑名单或 tokenVersion 机制。

Cookie 只是浏览器保存和自动携带数据的机制，不等于 Session。JWT 也不是加密，Payload 默认可读，不能放敏感信息。

认证解决“你是谁”，授权解决“你能访问什么”。微服务里通常由认证中心发 Token，网关统一校验，下游服务做业务权限和数据权限判断。
```

## 总结

这次面试暴露的问题是：我平时能使用已有登录态，但没有把登录认证的底层链路讲出来。

后续遇到登录认证问题，要按这个顺序回答：

1. 登录认证本质：签发凭证和校验凭证。
2. Cookie：客户端保存和自动携带机制。
3. Session：服务端保存状态，有状态认证。
4. JWT：Token 自包含，验签解析，无状态认证。
5. 分布式：认证中心、网关、Redis、Token 续期和失效。
6. 安全：HTTPS、HttpOnly、SameSite、XSS、CSRF、Token 泄露、密码加盐哈希。

如果没有主导做过登录模块，也可以这样收尾：

```text
这块在我之前的系统里是基础能力，业务开发时更多是使用已有登录态。但我理解它的核心机制：Session 是服务端有状态保存登录信息，JWT 是服务端签发并验签的无状态 Token。真正落地时还要结合网关、Redis、权限模型、Token 续期和安全防护一起设计。
```
