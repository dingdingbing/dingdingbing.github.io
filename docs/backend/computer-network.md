# 计算机网络基础：Java 后端面试与线上问题视角

这篇文章整理 Java 后端需要掌握的计算机网络基础。目标不是背完整教材，而是能把 TCP、HTTP、HTTPS、DNS、超时、连接池这些知识，和真实后端接口调用、网关超时、连接耗尽、重试放大等场景联系起来。

## 一、应该掌握到什么程度？

如果简历里写“熟悉计算机网络基础”，至少要能做到三件事：

- 能讲清 TCP/IP、HTTP/HTTPS、DNS、连接复用、超时控制等基本概念。
- 能解释 Java 后端常见问题，比如接口超时、连接池耗尽、CLOSE_WAIT 增多、网关 504、重试风暴。
- 能把网络问题和应用层行为联系起来，而不是只背三次握手、四次挥手。

简历表达可以写成：

> 熟悉计算机网络基础，了解 TCP/IP、HTTP/HTTPS、DNS、连接复用、连接超时与读取超时等机制，能够结合接口超时、连接池耗尽、网关超时、重试放大等后端场景进行分析。

## 二、TCP 基础

### 1. TCP 和 UDP 有什么区别？

最终答案：

TCP 是面向连接、可靠、有序、基于字节流的传输协议。它通过三次握手建立连接，通过序号、确认应答、重传、滑动窗口和拥塞控制保证可靠传输。

UDP 是无连接、不保证可靠、不保证顺序、面向报文的协议。它开销小、延迟低，适合对实时性要求高、允许少量丢包的场景，比如直播、音视频、DNS 查询等。

后端面试可以这样记：

- TCP：可靠，但连接维护和拥塞控制有成本。
- UDP：轻量，但可靠性需要应用层自己保证。

### 2. TCP 三次握手解决什么问题？

最终答案：

三次握手的核心是让客户端和服务端都确认双方的发送能力和接收能力正常，并同步初始序列号。

过程简化如下：

1. 客户端发送 `SYN`，表示我要建立连接。
2. 服务端返回 `SYN + ACK`，表示我收到了，也同意建立连接。
3. 客户端返回 `ACK`，表示我也收到了你的确认，连接建立。

为什么不是两次？

如果只有两次握手，服务端无法确认客户端是否收到了自己的确认。网络中历史的失效连接请求也可能让服务端误以为要建立新连接，造成资源浪费。

### 3. TCP 四次挥手和 TIME_WAIT 是什么？

最终答案：

TCP 是全双工连接，客户端和服务端两个方向的数据通道需要分别关闭，所以通常是四次挥手。

`TIME_WAIT` 一般出现在主动关闭连接的一方。它的作用主要有两个：

- 确保最后一个 `ACK` 能被对方收到。如果丢失，对方重发 `FIN` 时还能再次响应。
- 等待旧连接中的延迟报文自然过期，避免影响后续相同四元组的新连接。

面试里不要只说“TIME_WAIT 占资源”，还要能说出它存在的意义。

### 4. CLOSE_WAIT 很多通常说明什么？

最终答案：

`CLOSE_WAIT` 表示对端已经关闭连接，本机也收到了 `FIN`，但本机应用还没有调用 `close()` 关闭连接。

如果服务器上出现大量 `CLOSE_WAIT`，通常说明应用层没有正确释放连接，比如：

- HTTP 响应体没有关闭。
- Socket 没有关闭。
- 数据库、Redis、HTTP 客户端连接没有归还连接池。
- 代码异常分支没有走到资源释放逻辑。

Java 后端排查时，可以重点看连接池使用方式、try-with-resources、finally 释放逻辑、HTTP client 响应流是否关闭。

## 三、HTTP 基础

### 1. HTTP 是什么？它和 TCP 什么关系？

最终答案：

HTTP 是应用层协议，规定客户端和服务端如何表达请求和响应。TCP 是传输层协议，负责在两端之间可靠地传输字节流。

可以理解为：

- TCP 负责把数据可靠送到。
- HTTP 规定数据长什么样、请求哪个资源、返回什么状态。

一次 HTTP 请求通常建立在 TCP 连接之上。HTTP/1.1 支持 Keep-Alive，可以复用 TCP 连接，减少频繁建连成本。

### 2. 常见 HTTP 状态码怎么理解？

常见状态码：

| 状态码 | 含义 | 后端排查重点 |
| --- | --- | --- |
| 200 | 请求成功 | 正常返回 |
| 301 / 302 | 重定向 | 是否跳转到新地址 |
| 400 | 请求参数错误 | 参数格式、必填字段 |
| 401 | 未认证 | token、登录态 |
| 403 | 无权限 | 权限配置、角色资源 |
| 404 | 资源不存在 | URL、路由、接口路径 |
| 500 | 服务端异常 | 应用日志、异常堆栈 |
| 502 | 网关收到上游异常响应 | 上游服务不可用或返回异常 |
| 504 | 网关等待上游超时 | 上游接口慢、线程池/连接池阻塞 |

后端面试里，`504` 经常和网关超时、接口性能、线程池阻塞、数据库慢查询联系在一起。

### 3. GET 和 POST 有什么区别？

最终答案：

从 HTTP 语义看：

- GET 用于获取资源，应该是安全、幂等的。
- POST 通常用于提交数据、创建资源或触发业务动作，不要求幂等。

常见区别：

- GET 参数通常放在 URL 查询参数里，POST 参数通常放在请求体里。
- GET 更容易被缓存、收藏、记录在日志里。
- POST 请求体更适合传复杂结构和较大数据。

注意：GET 也可以有请求体，POST 也可以设计成幂等。真正关键的是接口语义和服务端实现，而不是“GET 一定不能传 body”这种绝对说法。

### 4. HTTP 幂等性和后端接口有什么关系？

最终答案：

幂等表示同一个请求执行一次和执行多次，对业务结果的影响一致。

比如：

- 查询订单是幂等的。
- 修改订单备注通常可以设计为幂等。
- 创建订单、扣减库存、发起支付如果没有幂等控制，多次请求可能产生重复数据或重复扣款。

后端常见幂等方案：

- 唯一业务单号。
- 数据库唯一索引。
- Redis 去重 key。
- 状态机约束。
- MQ 消费幂等表。

网络超时后，客户端或网关可能重试，所以关键业务接口必须考虑幂等。

## 四、HTTPS 基础

### 1. HTTPS 解决什么问题？

最终答案：

HTTPS = HTTP + TLS。它主要解决三类问题：

- 加密：防止内容被明文窃听。
- 身份认证：通过证书确认访问的服务端身份。
- 完整性：防止数据传输过程中被篡改。

### 2. TLS 大概流程是什么？

可以简化成：

1. 客户端发起 TLS 握手，带上支持的协议版本、加密套件和随机数。
2. 服务端返回证书、公钥信息、随机数和选定的加密套件。
3. 客户端校验证书是否合法，比如是否可信、是否过期、域名是否匹配。
4. 双方协商出会话密钥。
5. 后续 HTTP 内容使用对称加密传输。

为什么既有非对称加密又有对称加密？

- 非对称加密适合身份认证和密钥协商，但性能较低。
- 对称加密性能更好，适合传输大量业务数据。

## 五、DNS 和连接建立

### 1. 一次浏览器访问域名大概发生什么？

简化流程：

1. 浏览器检查缓存。
2. 操作系统检查本地 DNS 缓存和 hosts。
3. 向 DNS 服务器查询域名对应 IP。
4. 和目标 IP 建立 TCP 连接。
5. 如果是 HTTPS，进行 TLS 握手。
6. 发送 HTTP 请求。
7. 服务端处理并返回 HTTP 响应。

后端排查接口慢时，要知道耗时可能不只在业务代码里，也可能发生在 DNS、建连、TLS 握手、连接池等待、网关转发、上游服务处理等环节。

### 2. 连接超时和读取超时有什么区别？

最终答案：

连接超时是指客户端在规定时间内没有和服务端建立连接。常见原因包括网络不通、目标机器不可达、端口未监听、防火墙拦截等。

读取超时是指连接已经建立，请求也发出去了，但在规定时间内没有读到服务端响应。常见原因包括服务端处理慢、数据库慢查询、线程池阻塞、下游接口慢等。

Java 后端排查时，这两个超时方向完全不同：

- 连接超时优先看网络连通性、服务是否存活、端口是否开放。
- 读取超时优先看服务端处理链路、慢 SQL、线程池、连接池、下游依赖。

## 六、连接池和 Keep-Alive

### 1. 为什么 HTTP 客户端要用连接池？

最终答案：

如果每次请求都重新建立 TCP 连接，会产生三次握手、TLS 握手、端口占用和连接释放成本。连接池可以复用连接，减少建连开销，提高吞吐量。

但是连接池也可能带来问题：

- 最大连接数太小，请求会排队等待连接。
- 连接没有正确释放，导致连接池耗尽。
- 空闲连接被服务端关闭，客户端复用时失败。
- 超时时间设置不合理，慢请求长期占用连接。

面试表达可以说：

> 连接池不是越大越好，要结合 QPS、下游响应时间、实例数量和超时配置综合评估。连接池耗尽时，表面上看是接口超时，实际可能是连接没有释放或下游变慢导致连接长期占用。

### 2. 网关 504 怎么排查？

可以按这条链路排：

1. 看网关超时时间是多少。
2. 看应用日志里请求是否进入服务。
3. 如果进入服务，看业务耗时、慢 SQL、下游接口耗时。
4. 看线程池是否排队、连接池是否耗尽。
5. 看是否有重试导致流量放大。
6. 看 GC、CPU、内存是否异常。

`504` 不等于网络断了，它通常表示网关等上游服务响应超时。

## 七、常见面试问题

### 1. TCP 如何保证可靠传输？

可以从这些点回答：

- 序号机制：保证数据有序。
- 确认应答：接收方确认收到哪些数据。
- 超时重传：发送后迟迟没有 ACK 就重发。
- 滑动窗口：控制发送速度，提高吞吐。
- 拥塞控制：避免网络拥塞进一步恶化。

### 2. 为什么接口超时后不能随便重试？

最终答案：

接口超时不代表服务端没有执行成功，可能只是响应没有及时返回。如果客户端盲目重试，可能造成重复下单、重复扣款、重复发消息，也可能在下游已经很慢时进一步放大流量。

正确做法：

- 查询类接口可以谨慎重试。
- 写操作要有幂等设计。
- 重试要有次数上限、退避策略和熔断保护。
- 对核心链路要有唯一业务号或状态机约束。

### 3. 大量 TIME_WAIT 怎么办？

先判断是否真的有问题。`TIME_WAIT` 是 TCP 正常机制，不应该一看到就优化。

排查方向：

- 是否短连接过多。
- 是否没有复用连接。
- 客户端是否频繁主动关闭连接。
- 是否 QPS 突增。
- 本机端口范围和连接回收参数是否合理。

应用层优先考虑连接复用和连接池配置，不要上来就改系统参数。

## 八、总结

Java 后端复习计算机网络，重点不是背协议细节，而是能解释线上现象：

- TCP 关注连接建立、关闭、可靠传输和连接状态。
- HTTP 关注请求语义、状态码、幂等性、网关超时。
- HTTPS 关注证书、TLS、加密和身份认证。
- DNS、连接池、超时配置会直接影响接口性能和稳定性。
- 网络超时后的重试必须和幂等、限流、熔断一起考虑。
