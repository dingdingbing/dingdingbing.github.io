# Java 基础知识

这篇文章整理一轮 Java 高频基础问题复习，结构采用“问答纠偏型”：先保留我的原始回答，再给出更准确的最终答案，最后记录容易混淆或需要优化的地方。

## 一、Java 基础

### 1. `==` 和 `equals()` 有什么区别？`String` 里分别怎么表现？

我的回答：`==` 是比较符号，`equals` 是 `Object` 类的方法，`==` 两边如果是对象则比较的是对象的地址，如果比较的是基础数据类型则比较的是值是否相等。`equals` 在没有被重写的情况下比较的也是地址，但是如果对象重写了方法则按照规则进行比较。`String` 重写了 `equals` 方法，比较的是字符是否相等。

最终答案：`==` 对基本类型比较值，对引用类型比较对象引用是否指向同一个对象。`equals()` 是 `Object` 提供的方法，默认实现也是比较引用地址；如果类重写了 `equals()`，就按类定义的规则比较。`String` 重写了 `equals()`，所以比较字符串内容。

```java
String a = "abc";
String b = "abc";
String c = new String("abc");

System.out.println(a == b);      // true，字符串常量池复用
System.out.println(a == c);      // false，不同对象
System.out.println(a.equals(c)); // true，内容相同
```

纠正与优化：

- `String` 场景要同时讲清楚字符串常量池和 `new String()` 创建新对象。
- 面试表达可以按“基本类型、引用类型、是否重写 equals、String 示例”四层展开。

### 2. `String`、`StringBuilder`、`StringBuffer` 的区别是什么？

我的回答：`String` 是 `final` 声明的类，是不可变的。`StringBuilder` 和 `StringBuffer` 是没有被 `final` 修饰的，`StringBuilder` 是线程不安全的，而 `StringBuffer` 是线程安全的，在操作的时候都加上了 `synchronized` 关键字。`String` 适合声明常量，`StringBuilder` 适合拼接字符串，`StringBuffer` 适合需要考虑线程安全的情况下进行字符串拼接。

最终答案：`String` 表示不可变字符串，每次修改都会产生新对象或新内容。`StringBuilder` 和 `StringBuffer` 都表示可变字符序列，适合频繁拼接。`StringBuilder` 线程不安全，但性能更好，单线程拼接首选；`StringBuffer` 的关键方法带同步，线程安全但性能较差。

纠正与优化：

- `StringBuilder` 和 `StringBuffer` 类本身也是 `final`，关键区别不是能否继承，而是内部字符序列是否可变。
- 日常开发里大多数拼接场景优先考虑 `StringBuilder`，`StringBuffer` 现在使用较少。

### 3. 基本类型和包装类型有什么区别？自动装箱/拆箱可能带来什么坑？

我的回答：基本类型和包装类型的区别在于基本数据类型修饰词是关键字，而包装类型是 `final` 声明的类。基本数据类型声明的全局变量保存在常量池中？包装类型存储的位置是堆中？自动拆箱和装箱可能带来空指针的问题。

最终答案：基本类型是 Java 内置类型，比如 `int`、`long`、`boolean`，变量里直接保存值。包装类型是对象，比如 `Integer`、`Long`、`Boolean`，可以为 `null`，能参与泛型、集合、反射等对象体系。自动拆箱时如果包装类型为 `null`，会触发 `NullPointerException`。

```java
Integer a = null;
int b = a; // NullPointerException
```

包装类型还有缓存问题：

```java
Integer a = 127;
Integer b = 127;
System.out.println(a == b); // true

Integer c = 128;
Integer d = 128;
System.out.println(c == d); // false
```

纠正与优化：

- 基本类型不是“修饰词”，而是 Java 内置数据类型。
- 存储位置不能简单说“基本类型在常量池、包装类型在堆”。局部基本类型通常在栈帧局部变量表里，对象字段里的基本类型在对象内部，包装对象通常在堆上。
- `Integer.valueOf()` 对 `-128` 到 `127` 有缓存，这是 `==` 判断包装类型时常见的坑。

### 4. `final` 可以修饰哪些东西？分别代表什么含义？

我的回答：`final` 可以修饰类，表示类不可被继承；修饰变量，表示变量的引用不能被修改；修饰方法很少见，但是如果有的话应该是不能被重写。

最终答案：`final` 可以修饰类、方法和变量。修饰类表示不能被继承；修饰方法表示不能被子类重写；修饰变量表示只能赋值一次。对于引用变量，`final` 限制的是引用地址不能改变，不代表对象内部状态不能变。

```java
final List<String> list = new ArrayList<>();
list.add("a"); // 可以
// list = new ArrayList<>(); // 不可以
```

纠正与优化：

- “引用不能被修改”这句话容易被误解，要补充“对象内容仍然可能变化”。
- `final` 方法在框架源码里并不少见，常用于禁止子类破坏关键流程。

### 5. Java 是值传递还是引用传递？

我的回答：值传递，传递的是对象的地址副本。传的是副本的话，修改不会影响到真实的外部变量引用。

最终答案：Java 只有值传递。传基本类型时，传的是值的副本；传对象时，传的是对象引用的副本。方法内部可以通过引用副本修改同一个对象的内部状态，但不能改变外部引用本身指向哪个对象。

```java
void change(User user) {
    user.setName("new"); // 可以影响外部对象
    user = new User();   // 不能改变外部引用指向
}
```

纠正与优化：

- “地址副本”可以帮助理解，但面试时最好说“对象引用的副本”。
- 能否影响外部，关键看修改的是“对象内容”还是“引用指向”。

## 二、集合

### 6. `ArrayList` 和 `LinkedList` 的区别？分别适合什么场景？

我的回答：`ArrayList` 底层是使用数组结构实现的，`LinkedList` 是使用链表结构实现的，两者都可以保证有序，但是链表实现的 `LinkedList` 无需扩容操作，`ArrayList` 扩容需要迁移整个数组。但是依稀记得 `ArrayList` 不能保证有序，不过使用过程中其实是有序的。还有的区别就是查找遍历了，适合场景的话感觉都差不多。

最终答案：`ArrayList` 底层是动态数组，支持按下标快速访问，查询和遍历效率高，尾部追加效率高，扩容时需要复制数组。`LinkedList` 底层是双向链表，随机访问慢，已经定位到节点后插入删除快，但实际业务中定位成本和节点对象开销都较高。大多数场景默认使用 `ArrayList`。

纠正与优化：

- `ArrayList` 可以保证元素按插入顺序存储，这里的“有序”不是排序，而是遍历顺序稳定。
- 容易和 `HashMap`、`HashSet` 的无序混淆。
- `LinkedList` 理论上适合频繁头尾操作，但真实项目里并不常作为默认选择。

### 7. `HashMap` 的底层结构是什么？JDK 1.8 后有什么变化？

我的回答：`HashMap` 的底层结构是一个 `Entry` 数组，不清楚 1.8 之后的变化。

最终答案：JDK 1.8 之后，`HashMap` 底层是“数组 + 链表 + 红黑树”。key 经过 hash 计算后定位到数组桶；如果多个 key 落到同一个桶，就形成链表；当链表过长且数组容量达到条件时，链表会转为红黑树，提高查询效率。

纠正与优化：

- JDK 1.8 的关键词是“链表转红黑树”。
- 常见树化条件是链表长度达到 `8`，并且数组容量至少为 `64`，否则优先扩容。

### 8. `HashMap` 为什么线程不安全？并发场景应该用什么？

我的回答：`HashMap` 不安全是因为没有加同步，在扩容、插入等操作的时候不能保证原子性所以不安全，并发场景用 `ConcurrentHashMap`。

最终答案：`HashMap` 没有同步控制，多线程同时 `put`、扩容、修改链表或树结构时，可能出现数据覆盖、数据丢失、`size` 不准确、结构异常等问题。并发场景应该优先使用 `ConcurrentHashMap`。

纠正与优化：

- 不安全不只是“没加锁”，还要能说出具体风险表现。
- `Collections.synchronizedMap()` 是整张 Map 加锁，能保证同步，但并发性能通常不如 `ConcurrentHashMap`。

### 9. `HashMap`、`LinkedHashMap`、`TreeMap` 的区别？

我的回答：`HashMap` 插入无序，`LinkedHashMap` 插入有序，`TreeMap` 用得很少。

最终答案：`HashMap` 按 hash 存储，遍历无序，查询通常较快。`LinkedHashMap` 在 `HashMap` 基础上维护链表，可以保持插入顺序，也可以维护访问顺序，常用于 LRU 缓存。`TreeMap` 底层是红黑树，会按 key 排序，key 需要实现 `Comparable` 或传入 `Comparator`。

纠正与优化：

- `TreeMap` 虽然业务里不一定常用，但它的“按 key 排序”是核心考点。
- `LinkedHashMap` 除了插入顺序，还能通过访问顺序实现缓存淘汰。

### 10. `HashSet` 是怎么保证元素不重复的？和 `HashMap` 有什么关系？

我的回答：`HashSet` 底层是用的 set 集合实现的，set 本身就是可以保证不重复。`HashMap` 的 key 就是 `HashSet` 实现的，因此 `HashMap` 的 key 也是不重复的。

最终答案：`HashSet` 底层是用 `HashMap` 实现的。`HashSet.add(value)` 本质上是把 value 放到 `HashMap` 的 key 里，value 使用一个固定占位对象。`HashMap` 的 key 不允许重复，所以 `HashSet` 的元素也不重复。判断重复主要依赖 `hashCode()` 和 `equals()`。

纠正与优化：

- 关系要反过来记：不是 `HashMap` 的 key 由 `HashSet` 实现，而是 `HashSet` 底层使用 `HashMap`。
- `hashCode()` 定位桶，`equals()` 判断是否真的相等。

## 三、并发

### 11. 进程和线程的区别？

我的回答：进程是操作系统分配资源的最小单位，线程是操作系统执行的最小单位。这个看了好多遍但是总是记不住根本区别，总感觉进程就是线程的父亲一样的存在。

最终答案：进程是操作系统分配资源的基本单位，线程是 CPU 调度执行的基本单位。一个进程可以包含多个线程，进程拥有独立的内存空间、文件句柄等资源；同一进程内的线程共享进程资源，但每个线程有自己的程序计数器、虚拟机栈、本地方法栈等执行上下文。

纠正与优化：

- 可以记成：进程是资源容器，线程是执行路径。
- “父子关系”不够准确，更准确是“一个进程里可以有多条线程执行路径”。
- CPU 核心数决定同一时刻能真正并行执行多少线程，线程数量可以远大于 CPU 核心数，靠操作系统时间片调度切换。

### 12. 创建线程有哪些方式？

我的回答：实现 `Runnable` 接口，继承 `Callable` 接口，`new Thread`，通过线程池获取线程。

最终答案：常见方式包括继承 `Thread`、实现 `Runnable`、实现 `Callable` 并配合 `FutureTask` 或线程池使用，以及使用线程池 `ExecutorService` 提交任务。

纠正与优化：

- `Callable` 是接口，应该说“实现 `Callable`”，不是“继承 `Callable`”。
- 实际开发推荐使用线程池管理线程，不推荐频繁手动 `new Thread()`。

### 13. `synchronized` 和 `ReentrantLock` 的区别？

我的回答：`synchronized` 是 Java 关键字，通常作用于方法上锁整个方法，也作用于代码块上锁某个对象，使用简单但功能较少，支持重入功能，但是不支持公平锁和非公平锁的操作。`ReentrantLock` 是 Java 的类，实现了 AQS 抽象类，底层实现是通过 CAS 实现的，Java 的 native 方法，可实现公平锁和非公平锁，通常调用 `lock`，在 `finally` 代码块里 `unlock` 避免锁未释放。

最终答案：`synchronized` 是 JVM 层面的关键字，可以修饰方法或代码块，进入时自动加锁，退出时自动释放锁，使用简单且支持可重入。`ReentrantLock` 是 JUC 包里的显式锁，内部基于 AQS 实现，需要手动 `lock()` 和 `unlock()`，支持公平锁、非公平锁、可中断等待、超时等待以及多个 `Condition` 条件队列。

```java
lock.lock();
try {
    // business
} finally {
    lock.unlock();
}
```

纠正与优化：

- `ReentrantLock` 不是直接“实现 AQS 抽象类”，而是内部同步器继承 `AbstractQueuedSynchronizer`。
- CAS 依赖 JVM 和底层 CPU 原子指令能力，不宜简单说成 Java native 方法。

### 14. `volatile` 有什么作用？能不能保证原子性？

我的回答：`volatile` 的作用是保证可见性，当一个线程修改了被 `volatile` 修饰的变量，其他线程可以立刻感知到，获取该变量的值都通过主存获取，而不是 L1、L2 的缓存中获取，但是不能保证原子性。

最终答案：`volatile` 主要保证可见性和有序性。可见性表示一个线程修改变量后，其他线程能及时看到最新值；有序性表示禁止特定指令重排序。但 `volatile` 不保证复合操作的原子性。

```java
volatile int count = 0;
count++; // 不是原子操作
```

纠正与优化：

- “都从主存获取”是帮助理解的说法，底层还涉及内存屏障和缓存一致性协议。
- 要补充“禁止指令重排序”，这是双重检查锁等场景里的高频点。

### 15. 线程池的核心参数有哪些？任务提交后大概执行流程是什么？

我的回答：核心参数有核心线程数、最大线程数、非核心线程存活时间和单位、线程工厂类、阻塞队列、拒绝策略。任务提交之后，首先会进入到阻塞队列中，然后核心线程数进行获取任务，如果核心线程数满了，则任务会在阻塞队列中进行等待，如果阻塞队列满了，线程池则会开启新的线程进行处理任务直到最大线程数数量，如果此时已经是最大线程数并且阻塞队列也满了，则会执行拒绝策略。拒绝策略通常有直接拒绝、直接丢弃、使用当前线程去执行任务、丢弃最早的任务。阻塞队列通常有 `ArrayBlockingQueue`、`LinkedBlockingQueue`，还有延时队列 `DelayQueue`。

最终答案：线程池七大核心参数是 `corePoolSize`、`maximumPoolSize`、`keepAliveTime`、`unit`、`workQueue`、`threadFactory`、`handler`。任务提交后，执行流程是：如果运行线程数小于核心线程数，直接创建核心线程执行；如果核心线程已满，任务进入阻塞队列；如果队列满且线程数小于最大线程数，创建非核心线程执行；如果线程数也达到最大值，执行拒绝策略。

纠正与优化：

- 执行流程里第一步不是“先进入阻塞队列”，而是先看核心线程数是否已满。
- 常见拒绝策略：`AbortPolicy`、`DiscardPolicy`、`CallerRunsPolicy`、`DiscardOldestPolicy`。
- 常见队列还包括 `SynchronousQueue`、`PriorityBlockingQueue`。

## 四、JVM 内存与对象

### 16. JVM 内存区域有哪些？哪些是线程私有，哪些是线程共享？

我的回答：JVM 内存区域有堆、元空间、程序计数器、虚拟机栈、本地方法栈，前二者是线程共享，后三者是线程私有的。

最终答案：JVM 运行时数据区常见包括堆、方法区、程序计数器、虚拟机栈、本地方法栈。堆和方法区是线程共享的；程序计数器、虚拟机栈、本地方法栈是线程私有的。JDK 8 后方法区的实现通常称为元空间，元空间使用本地内存。

纠正与优化：

- 回答已经比较准确。
- 需要补一句“元空间不是堆的一部分，而是使用本地内存”。

### 17. 堆里面一般怎么分代？为什么要分代？

我的回答：一般区分为老年代和新生代，分代是为了回收垃圾更高效，因为所有的对象理想状态下都是朝生暮死，但是会存在一直存活的对象，将他们划分完之后就可以提升垃圾回收的效率。

最终答案：传统分代模型里，堆通常分为新生代和老年代。新生代又分为 Eden 区和两个 Survivor 区。分代基于两个经验：大多数对象朝生夕死；熬过多次 GC 的对象更可能继续存活。新生代对象存活率低，适合频繁 Minor GC；老年代对象存活率高，回收频率低但成本更高。

纠正与优化：

- 这题主干答对了。
- 新生代结构要记住：`Eden : Survivor From : Survivor To = 8 : 1 : 1`。

### 18. 对象创建过程大概是什么？

我的回答：对象创建的过程我还真描述不上来。

最终答案：对象创建大致流程是：类加载检查，确认类是否已经加载、解析、初始化；为对象分配内存；将对象内存初始化为零值；设置对象头，包括类型指针、GC 年龄、锁状态等；执行构造方法和字段显式赋值逻辑。

```text
类加载检查 -> 分配内存 -> 零值初始化 -> 设置对象头 -> 执行构造方法
```

纠正与优化：

- 这题需要作为固定链路记忆。
- 面试时不一定展开 TLAB、指针碰撞、空闲列表，但能补一句“分配方式取决于堆内存是否规整”会更完整。

### 19. 什么情况下对象会进入老年代？

我的回答：对象进入新生代之后，在新生代的伊甸园区被 Minor GC 一定的次数之后，比如 15 次，就会被升级到老年代中。新生代和老年代比例还行是 4:6 还是 3:7，39% 和 61%。新生代的区域划分为 1:1:8，好像是，两个伊甸园区那个 8 是啥来着？依稀记得是把 8 的区域通过 GC 之后存活的对象放到伊甸园区，但是另一个区好像是用来复制的？

最终答案：对象进入老年代的常见情况包括：对象年龄达到晋升阈值；大对象直接进入老年代；动态年龄判断导致提前晋升；Minor GC 后 Survivor 区放不下，存活对象通过空间分配担保进入老年代。新生代一般是一个 Eden 区和两个 Survivor 区，比例常见为 `8:1:1`。对象通常先分配到 Eden，Minor GC 时把 Eden 和 From Survivor 中还存活的对象复制到 To Survivor，然后清空 Eden 和 From，之后 From 和 To 角色互换。

纠正与优化：

- 不是两个 Eden，而是一个 Eden、两个 Survivor。
- `8` 是 Eden 区，两个 `1` 是 Survivor From 和 Survivor To。
- 年龄阈值常见最大为 15，是因为对象头里的年龄字段通常是 4 bit。

### 20. 判断对象是否可回收有哪些方法？Java 主要用哪种？

我的回答：通过根搜索的方式进行可达性分析，通常根节点有静态变量、正在运行的虚拟机栈，其他的回收方法不清楚。

最终答案：判断对象是否可回收主要有引用计数法和可达性分析法。引用计数法给对象维护引用数量，但解决不了循环引用问题。Java 主流 GC 使用可达性分析：从 GC Roots 出发沿引用链查找，能到达的是存活对象，不能到达的是可回收对象。

常见 GC Roots 包括：虚拟机栈中引用的对象、方法区或元空间中类静态属性引用的对象、常量引用的对象、本地方法栈中 JNI 引用的对象、被同步锁持有的对象、JVM 内部引用等。

纠正与优化：

- “根搜索”就是可达性分析，这点方向正确。
- 要补充引用计数法及其循环引用缺陷。

## 五、GC

### 21. Minor GC、Major GC、Full GC 分别是什么？

我的回答：Minor GC 是在年轻代触发的，当伊甸园区内存空间不足时触发。Major GC 是在老年代触发的，当老年代空间不足时触发。Full GC 是全局的，触发时表示老年代已经没有可分配的空间了，需要进行全局垃圾清理。这么一说 Major 和 Full 的区别好像我不是很清楚。

最终答案：Minor GC 主要回收新生代，通常在 Eden 空间不足时触发。Major GC 通常指老年代 GC。Full GC 是范围更大的回收，通常会回收整个堆，并可能处理方法区或元空间。很多资料会把老年代回收和 Full GC 混用，但概念上 Full GC 范围更大、停顿通常更重。

纠正与优化：

- 面试时可以主动说明“不同收集器和日志里叫法可能不完全一致”。
- 常见 Full GC 触发原因包括老年代空间不足、元空间不足、显式调用 `System.gc()`、空间分配担保失败等。

### 22. 常见垃圾回收算法有哪些？复制、标记清除、标记整理分别有什么优缺点？

我的回答：复制、标记清除、标记整理。复制的优点是快并且可以整理出连续的内存空间，但是由于需要复制所以可用的空间只有一半。标记清除的优点是用的全局空间，并且针对性清除，但是缺点是无法弄出完整的连续空间。标记整理是在标记清除的基础上再做一次整理，意在将空间整理出来，最后空闲空间整理成连续的内存空间，但是效率比前两者都低。一般都用复制吧？还是有什么配置项可以选择的，默认的是哪个？

最终答案：复制算法把存活对象复制到另一块空间，速度快、无碎片，但需要额外空间，适合对象存活率低的新生代。标记清除先标记存活对象，再清理不可达对象，不移动对象，但会产生内存碎片。标记整理先标记，再把存活对象向一端移动，清理边界外空间，没有碎片，但移动对象成本较高，适合老年代。

纠正与优化：

- 不是“一般都用复制”，而是新生代常用复制，老年代常用标记清除或标记整理。
- 现代收集器通常组合多种算法，业务开发更多是选择 GC 收集器和调参数，而不是直接配置某个单一算法。

### 23. 常见垃圾收集器有哪些？CMS 和 G1 大概区别是什么？

我的回答：垃圾回收器知道 G1、CMS，不清楚具体区别，这块很薄弱。

最终答案：常见收集器包括 Serial、ParNew、Parallel Scavenge、CMS、G1 等。Serial 是单线程收集器，简单但停顿明显；ParNew 是多线程新生代收集器，常和 CMS 搭配；Parallel Scavenge 更关注吞吐量；CMS 是老年代低停顿收集器，基于标记清除，会产生碎片；G1 把堆拆成多个 Region，按回收收益优先处理，目标是可预测停顿，适合服务端大堆场景。

纠正与优化：

- CMS 关键词：老年代、低停顿、并发标记清除、内存碎片、可能退化 Full GC。
- G1 关键词：Region、Garbage First、可预测停顿、JDK 9 后默认收集器。

### 24. `StackOverflowError` 和 `OutOfMemoryError` 有什么区别？

我的回答：这一题漏答。

最终答案：`StackOverflowError` 通常表示线程栈深度太深，比如无限递归导致栈帧不断增加。`OutOfMemoryError` 表示某块内存区域无法继续分配，可能发生在堆、元空间、直接内存、线程栈等区域。

```java
void test() {
    test(); // 可能导致 StackOverflowError
}
```

纠正与优化：

- `StackOverflowError` 是线程栈深度爆了。
- `OutOfMemoryError` 是某个内存区域不够用了，要结合具体错误信息判断是哪块区域。

### 25. 强引用、软引用、弱引用、虚引用分别是什么？常见使用场景是什么？

我的回答：我知道弱引用是使用 `WeakReference` 修饰的，在 `ThreadLocal` 的 key 中使用过，意在做垃圾回收的时候可以被回收，避免一直引用导致内存泄露。强引用就是我们正常声明的，还真不清楚最常见的使用场景。

最终答案：强引用是普通对象引用，只要强引用还存在，GC 不会回收对象。软引用 `SoftReference` 在内存足够时通常不回收，内存紧张时可能回收，常用于缓存思路。弱引用 `WeakReference` 在 GC 时只要对象只被弱引用关联，就会被回收，常见于 `ThreadLocalMap` 的 key、`WeakHashMap`。虚引用 `PhantomReference` 几乎不能通过引用获取对象，主要配合 `ReferenceQueue` 感知对象回收，用于堆外内存清理、资源释放监控等底层场景。

纠正与优化：

- `ThreadLocalMap` 的 key 是弱引用，只能降低 key 泄露风险；value 仍然可能泄露，所以线程池场景用完 `ThreadLocal` 要调用 `remove()`。
- 软引用过去常被用来描述缓存，但真实项目里更常使用 Caffeine、Redis 等成熟缓存方案。

## 总结

- Java 基础题要把“概念定义、典型例子、容易踩坑”一起记。
- 集合题重点是底层结构、顺序语义、扩容与并发安全。
- 并发题不要只背名词，要能说出线程上下文、锁能力差异、线程池执行流程。
- JVM 题要把内存区域、对象创建、分代、可达性分析串成一条线。
- GC 题先掌握算法和收集器的主干，再补具体参数和日志细节。
