# Spring 事务失效场景

## 场景：注解在，数据却没有回滚

在某状态流转接口中，主表更新成功后，明细表写入发生异常。代码上已经添加了 `@Transactional`，但复查数据库时发现主表状态仍然被提交，导致后续任务把这条记录识别成可继续处理。

这种问题比直接报错更危险，因为调用方看到的是失败结果，数据库却留下了部分成功的状态。

## 排查路径：先确认事务是否真的创建

我通常按四步排查：

1. 确认入口方法是否通过 Spring 代理对象调用。
2. 确认异常是否被捕获后吞掉，或者被转换成不触发回滚的类型。
3. 确认事务传播行为是否被内层方法改变。
4. 确认数据库操作是否在同一个数据源和同一个事务连接里执行。

这一步的重点是看运行证据，而不是只看注解是否存在。

## 常见失效原因与判断证据

| 失效原因 | 现象 | 判断方式 |
| --- | --- | --- |
| 同类内部调用 | 被调方法上的事务不生效 | 查看调用链是否绕过代理 |
| 异常被捕获 | 方法返回失败但事务提交 | 检查 catch 后是否继续抛出 |
| 回滚规则不匹配 | 受检异常未触发回滚 | 查看 `rollbackFor` 与异常类型 |
| 传播行为不当 | 内外事务边界不符合预期 | 对照调用层级和传播配置 |
| 多数据源误用 | 部分表提交、部分表回滚 | 确认 Mapper 使用的数据源 |

## 修复取舍：优先让边界清楚

如果是同类内部调用导致失效，我更倾向于把事务放在外层业务入口，保证一次业务动作只有一个清楚的事务边界。只有当内层方法确实需要独立提交或独立回滚时，才会讨论传播行为。

如果是异常被捕获导致提交，我会让业务异常继续向外传播，或者在确实需要转换返回值的地方显式标记回滚。这样调用方得到的结果和数据库状态保持一致。

我不建议为了修一个事务问题到处补注解。事务越分散，越难判断一次业务动作到底以哪个边界为准。

## 验证方式

修复后，我会构造三类用例：

- 明细写入失败时，主表状态必须回滚。
- 全部写入成功时，主表和明细表一起提交。
- 异常被转换成业务失败结果时，数据库状态仍符合预期。

如果涉及异步任务，还需要确认任务不会读取到已经失败但部分提交的数据。

## 总结

Spring 事务排查的关键不是“有没有注解”，而是“调用是否经过代理、异常是否继续传播、边界是否符合业务动作”。把这三件事确认清楚，事务问题通常能从猜测变成可验证的结论。
