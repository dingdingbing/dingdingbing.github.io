# 加密基础面试复盘：对称加密、非对称加密、摘要和签名

这篇文章来自一次面试复盘。

面试中被问到“对称加密和非对称加密”的区别时，我没有正面回答清楚，而是用企业微信对接项目里的加密、签名、回调校验场景做了覆盖。这个方向不算错，说明项目里确实接触过开放平台对接，但如果基础概念答不上来，面试官还是会觉得知识不够扎实。

所以这篇文章的目标是：把加密相关概念整理成 Java 后端面试能用的答案，并能和真实项目对接场景串起来。

## 问题

对称加密和非对称加密有什么区别？

## 我的回答

当时没有直接回答上来，而是讲到了企业微信对接项目：

```text
我们在企业微信对接里会涉及回调消息校验、签名验证、消息解密等流程。平台会把加密消息推给我们，我们需要根据 token、timestamp、nonce、签名等参数做校验，然后再解密消息体，处理业务逻辑。
```

这个回答能说明我接触过真实加密场景，但没有先把基础概念讲清楚。

## 最终答案

可以这样回答：

```text
对称加密和非对称加密最大的区别是密钥使用方式不同。

对称加密是加密和解密使用同一把密钥，比如 AES。它的优点是速度快，适合加密大量数据；缺点是密钥分发困难，因为通信双方必须安全地拿到同一把密钥。

非对称加密使用一对密钥：公钥和私钥。公钥可以公开，私钥必须自己保存。用公钥加密的数据，只能用对应私钥解密；用私钥签名的数据，可以用公钥验签。它的优点是解决了密钥分发和身份认证问题，缺点是性能比对称加密慢，不适合直接加密大量数据。

真实系统里通常会组合使用：用非对称加密解决密钥交换和身份认证，用对称加密加密真正的大数据内容。比如 HTTPS 握手阶段会协商出会话密钥，后续通信主要使用对称加密。
```

可以简化成一句话：

```text
对称加密快，但密钥不好安全传递；非对称加密安全性和身份认证能力更强，但性能慢，所以实际系统经常混合使用。
```

## 纠正与优化

- 面试官问基础概念时，先回答概念，再补项目经验。
- 不要一上来讲企业微信、签名、回调，否则面试官会觉得是在绕开问题。
- 要把“加密”“摘要”“签名”区分开，它们不是一回事。

## 对称加密

## 问题

什么是对称加密？适合什么场景？

## 我的回答

当时没有单独展开。

## 最终答案

对称加密是指加密和解密使用同一把密钥。

常见算法：

- `AES`：现在最常用的对称加密算法。
- `DES`：已经不安全，不建议使用。
- `3DES`：比 DES 强，但性能和安全性都不如 AES，逐渐被淘汰。

对称加密适合加密大量数据，比如文件内容、接口报文、数据库敏感字段。

优点：

- 性能高。
- 加密解密速度快。
- 适合大数据量。

缺点：

- 密钥分发困难。
- 如果密钥泄露，加密数据就不安全了。
- 多个系统之间共享同一把密钥时，密钥管理会复杂。

面试可以这样说：

```text
对称加密的核心特点是双方使用同一把密钥。它性能好，适合加密大量业务数据，比如接口报文或文件内容。它的问题是密钥怎么安全地给到对方，如果密钥在传输或配置中泄露，数据就有风险。
```

## 纠正与优化

- 对称加密不是“安全性低”，而是“密钥分发和保管风险更高”。
- AES 是面试里最常见的例子。

## 非对称加密

## 问题

什么是非对称加密？公钥和私钥分别怎么用？

## 我的回答

当时没有准确回答公钥、私钥的使用方式。

## 最终答案

非对称加密使用一对密钥：

- 公钥：可以公开给别人。
- 私钥：只能自己保存，不能泄露。

它有两个常见用途。

第一种是加密解密：

```text
别人用我的公钥加密数据，只有我能用自己的私钥解密。
```

这个场景解决的是保密性。

第二种是签名验签：

```text
我用自己的私钥对数据签名，别人用我的公钥验签。
```

这个场景解决的是身份可信和数据未被篡改。

常见算法：

- `RSA`
- `ECC`

面试可以这样说：

```text
非对称加密有公钥和私钥。公钥可以发给外部系统，私钥自己保存。如果是加密场景，一般是对方用我的公钥加密，我用私钥解密。如果是签名场景，一般是我用私钥签名，对方用我的公钥验签。
```

## 纠正与优化

- “公钥加密、私钥解密”和“私钥签名、公钥验签”要分开记。
- 非对称加密不适合直接加密大报文，通常只加密密钥、摘要或用于签名。

## 摘要算法

## 问题

MD5、SHA 这类算法算不算加密？

## 我的回答

以前容易把 MD5、SHA、AES、RSA 都放在“加密”这个大框里。

## 最终答案

严格来说，MD5、SHA 这类是摘要算法，不是加密算法。

摘要算法的特点是：

- 单向计算，不能解密还原原文。
- 相同输入得到相同摘要。
- 输入稍微变化，摘要结果会明显变化。
- 常用于完整性校验、签名原文构造、密码存储等场景。

常见算法：

- `MD5`：已经不适合安全场景。
- `SHA-1`：也不推荐用于安全场景。
- `SHA-256`：更常见于安全要求更高的场景。

面试可以这样说：

```text
MD5 和 SHA 不是加密，因为加密通常意味着可以解密还原。摘要算法是单向的，只能根据原文算出摘要，不能根据摘要还原原文。它主要用于判断数据有没有被篡改。
```

## 纠正与优化

- 加密是为了保密，摘要是为了完整性校验。
- MD5 不能再作为安全算法使用，最多用于非安全场景的快速校验。

## 数字签名

## 问题

签名和加密有什么区别？

## 我的回答

企业微信对接里会说“签名校验”，但之前没有把签名和加密的目标区分清楚。

## 最终答案

加密和签名解决的问题不同。

加密解决的是：

```text
不让别人看到内容。
```

签名解决的是：

```text
证明这个数据确实是某个发送方发来的，并且中途没有被篡改。
```

一个常见签名流程是：

1. 发送方把请求参数按规则排序。
2. 拼接成待签名字符串。
3. 对待签名字符串做摘要。
4. 用私钥或约定密钥生成签名。
5. 接收方用同样规则重新计算签名。
6. 对比签名是否一致。

如果是非对称签名：

```text
发送方用私钥签名，接收方用发送方公钥验签。
```

如果是对称签名或 HMAC：

```text
双方共享同一把 secret，发送方和接收方都用这个 secret 计算签名。
```

## 纠正与优化

- 签名不是为了隐藏内容，而是为了验证身份和防篡改。
- 开放平台对接里常见的 `timestamp`、`nonce` 还可以防重放攻击。

## 企业微信这类开放平台对接怎么讲

## 场景

企业微信、微信支付、支付宝、第三方 SaaS 平台这类系统对接，经常会涉及：

- 请求签名。
- 回调验签。
- 消息加密和解密。
- `timestamp`、`nonce` 防重放。
- `token`、`secret`、`EncodingAESKey` 等配置。

## 当时的解决方式

面试中我用企业微信对接项目做了覆盖，大概方向是：

```text
企业微信会把加密后的回调消息推给我们，我们先根据 token、timestamp、nonce、msg_signature 做签名校验，确认消息来源和内容没有被篡改。校验通过后，再用配置的 key 解密消息体，拿到真实业务数据，然后处理后续业务。
```

## 关键原理

开放平台对接里，通常不是只用一种加密算法，而是组合使用。

可以按这个顺序理解：

```text
签名校验：确认请求来源可信，参数没有被篡改。
时间戳 timestamp：判断请求是否过期。
随机数 nonce：降低重放攻击风险。
消息加密：保护消息内容，避免明文暴露。
消息解密：服务端拿到密文后还原业务数据。
```

如果面试官问企业微信为什么要这样设计，可以这样回答：

```text
因为开放平台回调是公网请求，服务端不能只相信请求 URL。签名可以验证请求确实来自可信平台，timestamp 和 nonce 可以降低重放攻击风险，消息加密可以避免敏感业务内容在传输或日志中直接暴露。
```

## 更多思考

真实项目里要注意：

- 密钥不要写死在代码里，要放配置中心或密钥管理系统。
- 日志不要打印完整密钥、明文敏感数据、完整签名原文。
- 验签失败要拒绝处理，不要为了兼容继续执行业务。
- 时间戳要设置合理过期窗口，比如 5 分钟。
- 回调处理要做幂等，因为平台可能重试推送。
- 解密成功不代表业务一定能处理成功，后续还要做状态校验和异常补偿。

## 加密、摘要、签名的区别

| 类型 | 解决问题 | 是否可逆 | 常见算法 | 典型场景 |
| --- | --- | --- | --- | --- |
| 对称加密 | 内容保密 | 可逆 | AES | 报文、文件、敏感字段加密 |
| 非对称加密 | 密钥交换、保密、身份认证 | 可逆 | RSA、ECC | HTTPS、开放平台密钥交换 |
| 摘要 | 完整性校验 | 不可逆 | SHA-256、MD5 | 文件校验、签名前摘要 |
| 数字签名 | 身份可信、防篡改 | 不是解密还原 | RSA 签名、HMAC | 开放平台接口验签 |

## 面试速记

可以背下面这段：

```text
对称加密是双方使用同一把密钥，典型算法是 AES，优点是快，适合加密大量数据，缺点是密钥分发和保管有风险。

非对称加密是一对公钥和私钥，典型算法是 RSA。公钥可以公开，私钥自己保存。公钥加密、私钥解密解决保密问题；私钥签名、公钥验签解决身份可信和防篡改问题。

摘要算法比如 SHA-256，是单向不可逆的，不是加密，主要用于完整性校验。

签名不是为了隐藏内容，而是为了证明数据来源可信、内容没有被篡改。真实系统里通常会组合使用，比如 HTTPS 用非对称加密协商密钥，再用对称加密传输数据；开放平台对接会用签名验签、timestamp、nonce、消息加密来保证安全。
```

## 总结

这次面试暴露的问题不是完全没接触过加密，而是没有把项目经验和基础概念连接好。

以后回答加密相关问题，可以按这个顺序：

1. 先讲概念：对称加密、非对称加密、摘要、签名。
2. 再讲区别：密钥、性能、用途、是否可逆。
3. 再讲项目：企业微信/开放平台如何验签、解密、防重放。
4. 最后讲工程注意事项：密钥管理、日志脱敏、幂等、重试、告警。

面试里最稳的表达是：

```text
我之前在企业微信这类开放平台对接里接触过签名校验和消息解密。基础上，对称加密适合加密大量数据，非对称加密适合密钥交换和签名验签。实际系统一般混合使用，不会只靠一种算法解决所有安全问题。
```
