# AI 使用过程中常见的坑：从一次生产故障复盘说起

## 场景

最近在对接第三方系统时，我们新建了一个工程项目。为了提高效率，我让 AI 参考另一个已有项目进行初始化。

问题也出在这里：AI 并不是完全按照我理想中的方式复制工程，它会进行“添油加醋”。比如在数据库连接 URL 上，AI 自动加了两个参数：

```properties
connectTimeout=3000
socketTimeout=5000
```

这两个参数看起来像是普通的超时优化，但对我们的系统来说非常致命。

我们的系统里有事务。生产环境初次创建数据时，由于某些 SQL 执行较慢，超过了 `socketTimeout=5000` 的限制，数据库连接被关闭。后续事务回滚时，又抛出了类似下面的异常：

```text
java.sql.SQLException: Connection is closed
    at com.zaxxer.hikari.pool.ProxyConnection.rollback(...)
    at com.xxx.LocalTxUtil.rollback(...)
Wrapped by: java.lang.reflect.UndeclaredThrowableException
```

这个异常很迷惑。单看日志，看到的是连接关闭、事务回滚失败，很难直接发现真正的根因是 SQL 慢和数据库连接 URL 的超时参数过短。

后续我们通过执行 SQL 分析、链路追踪、慢 SQL 排查，先解决了慢 SQL 问题，再定位到数据库连接配置问题，最终通过调整代码和配置解决了生产故障。

但问题并没有到此结束。这次慢 SQL 出现的原因，本质上是 AI 写的查询没有结合真实库表结构进行设计。只看代码逻辑，SQL 没有明显问题；但它使用了非索引字段，生产环境数据量一大，查询速度就变慢，最终触发了过短的 `socketTimeout`。

这件事暴露出的核心风险是：**AI 生成代码时，不一定会结合真实生产环境、库表结构、索引情况、事务边界和团队编码规范。**

## 当时的解决方式

这次排查大致经历了几个阶段：

1. 先从异常日志入手，但 `Connection is closed` 只能说明连接已经不可用，不能直接说明为什么不可用。
2. 结合链路追踪查看接口耗时，发现某些数据库查询明显偏慢。
3. 进一步分析实际执行 SQL，发现查询条件使用了非索引字段。
4. 生产数据量较大，SQL 没有命中索引，执行时间超过了 `socketTimeout=5000`。
5. SQL 超时后连接被关闭，事务回滚阶段又触发 `rollback` 异常，导致真正的慢 SQL 根因被二次异常掩盖。
6. 最终先优化慢 SQL，再移除或调整不合理的数据库连接超时配置，问题才真正解决。

这条事故链路可以总结为：

```text
AI 初始化项目时夹带 JDBC 超时参数
  -> socketTimeout=5000 过短
  -> 事务内某个查询 SQL 未走索引
  -> 生产数据量大，SQL 执行超过 5 秒
  -> 数据库连接被驱动或连接池关闭/标记不可用
  -> 事务回滚时 Connection is closed
  -> 回滚异常遮蔽了真正的慢 SQL/超时根因
```

## 关键原理

### `connectTimeout` 是什么

`connectTimeout=3000` 通常表示客户端和数据库建立连接的超时时间，也就是连接数据库地址、建立 TCP 连接、握手认证这段过程最多等 3000ms。

它主要影响的是“连不上数据库时多久失败”，比如：

```text
数据库地址不可达
网络抖动
防火墙阻断
数据库实例无响应
新建物理连接很慢
```

它不控制 SQL 执行多久。SQL 已经发出去了，查询跑 10 秒、30 秒，通常不是 `connectTimeout` 管的。

### `socketTimeout` 是什么

`socketTimeout=5000` 更危险。它通常表示连接建立成功后，客户端等待数据库返回数据的 socket 读超时时间。

也就是说，下面这些情况都有可能触发 socket 超时：

```text
SQL 执行超过 5 秒还没返回
数据库返回结果很慢
网络传输卡住
大结果集读取时间过长
```

这对事务系统非常致命。事务里如果某条 SQL 超过 `socketTimeout`，连接可能已经被驱动认为不可用了。后续框架想 rollback 时，拿到的是一个已经 closed 或 broken 的 connection，于是就出现：

```text
SQLException: Connection is closed
ProxyConnection.rollback
LocalTxUtil.rollback
UndeclaredThrowableException
```

这类异常最难受的地方是：**你看到的是 rollback 失败，不是最开始那条 SQL 为什么失败。** 真正根因被二次异常盖住了。

所以这两个参数不能随便加，尤其是：

```properties
connectTimeout=3000
socketTimeout=5000
```

看起来像“工程优化”，实际上对生产事务系统可能是灾难配置。更合理的原则是：

```text
connectTimeout 可以适度设置，用于快速发现连接不可达。
socketTimeout 必须结合业务最大 SQL 耗时、事务边界、慢 SQL 阈值、数据库负载来定。
不能由 AI 默认补充。
```

## 更多思考

### 坑一：AI 会擅自修改基础配置

让 AI “参考另一个项目初始化工程”时，它可能不只是复制结构，还会自动补充一些它认为合理的配置。

数据库、连接池、事务、MQ、Redis、线程池这类基础设施配置，不能允许 AI 自由发挥。建议建立配置白名单：

```text
允许 AI 参考：
- 项目结构
- 依赖组织
- 包命名风格
- 常规代码分层

禁止 AI 自行新增：
- 数据库 URL 参数
- 连接池参数
- 事务超时参数
- 重试参数
- 自动重连参数
- 线程池核心参数
```

对数据库连接 URL，尤其要关注这些参数：

```text
connectTimeout
socketTimeout
queryTimeout
autoReconnect
allowMultiQueries
rewriteBatchedStatements
useSSL
serverTimezone
```

建议加一条硬规则：

```text
生产 JDBC URL 禁止由 AI 自行新增超时、重试、自动重连、批量重写等参数。
所有新增连接参数必须有人工确认和压测依据。
```

### 坑二：AI 写的 SQL 只保证逻辑正确，不保证性能正确

这次慢 SQL 的根因之一，就是 AI 写的查询没有走索引。

代码上看可能没有任何逻辑问题：

```sql
select *
from order_detail
where apply_code = ?
```

但是如果 `apply_code` 不是索引字段，生产表又有大量数据，这条 SQL 就可能变成全表扫描。

AI 很容易只根据字段名和业务含义生成 SQL，却不会主动结合真实表结构、索引、数据量和访问频率做判断。

所以，AI 生成或修改 SQL 后，必须整理 SQL 清单，并逐条审查。

SQL 清单至少包含：

```text
文件路径
方法名
SQL 内容
涉及表
where 条件字段
join 字段
order by 字段
是否分页
是否在事务内执行
是否命中索引
Explain 结果
风险等级
```

Explain 时不能只看有没有索引名，要重点看：

```text
type 是否为 ALL
key 是否为 NULL
rows 是否过大
Extra 是否出现 Using filesort
Extra 是否出现 Using temporary
where 条件是否符合联合索引最左前缀
是否存在隐式类型转换
是否存在 like '%xxx'
是否对索引字段使用函数
join 字段类型或字符集是否一致
order by 是否能利用索引
是否存在深分页
```

给 AI 的提示词可以这样写：

```text
请扫描项目中所有新增或修改的 SQL，输出 SQL 清单。
结合表结构 DDL 和索引信息，判断每条 SQL 是否能命中索引。
如果缺少 DDL 或索引信息，请明确标记“无法判断”，不要猜测。
对可能全表扫描、文件排序、临时表、深分页、隐式转换的 SQL 标记为高风险。
特别标记事务内调用的 SQL。
```

### 坑三：AI 喜欢为了测试抽简单方法

AI 经常会把很简单的逻辑抽成私有方法，理由可能是“方便单元测试”或“提升复用性”。

比如：

```java
private boolean isValidStatus(Integer status) {
    return Objects.equals(status, VALID_STATUS);
}
```

如果这个方法只在一个地方使用，而且逻辑一眼就能看懂，抽出来反而会降低可读性。读代码的人需要来回跳转，业务主流程也被切碎。

建议规范：

```text
简单判断优先就地表达。
只有当逻辑有明确业务含义、被多处复用、或者能显著降低复杂度时才抽方法。
不要为了单元测试而抽生产代码方法。
测试应该围绕可观察行为，而不是为了测私有小函数重塑代码结构。
```

### 坑四：AI 写代码可能缺少有效注释

AI 有两种极端。一种是完全不写注释，复杂业务规则也没有说明；另一种是写很多废话注释：

```java
// 设置名称
vo.setName(name);

// 判断列表是否为空
if (CollectionUtils.isEmpty(list)) {
    return;
}
```

这种注释没有价值，只是在重复代码本身。

建议规范：

```text
普通赋值、简单判断、常规调用不写注释。
复杂业务规则、特殊兼容逻辑、历史原因、风险边界必须写注释。
注释解释“为什么这样做”，不要重复“代码做了什么”。
```

更好的注释应该类似：

```java
// 第三方系统历史数据中存在空状态，这里保留兼容，避免同步任务误判为失败。
if (StringUtils.isBlank(status)) {
    return DEFAULT_STATUS;
}
```

### 坑五：AI 不一定遵守项目已有工具类规范

项目中可能已经有统一工具类：

```java
CollectionUtils.isEmpty(list)
StringUtils.isBlank(name)
DateUtils.format(date)
```

但 AI 可能自己写：

```java
list == null || list.size() == 0
name == null || name.trim().length() == 0
new SimpleDateFormat("yyyy-MM-dd").format(date)
```

代码不一定错，但会破坏项目统一风格，也可能绕过已有工具类的特殊处理。

建议规范：

```text
优先使用项目已有工具类和既有调用风格。
新增工具方法前，必须先搜索项目内是否已有同类能力。
禁止为了当前一处调用新增通用工具类。
日期、金额、字符串、集合、JSON、异常处理必须使用项目约定工具。
```

### 坑六：AI 容易漏掉关联修改

比如修改 VO 字段类型：

```java
private String amount;
```

改成：

```java
private BigDecimal amount;
```

AI 可能只改字段定义，却漏掉：

```text
setAmount 的地方
BeanUtils.copyProperties
MapStruct 映射
MyBatis resultMap
JSON 序列化
Excel 导出
接口文档
单元测试
前端消费方
```

结果就是编译可能过了，但运行时数据不对，或者接口返回不符合预期。

建议规范：

```text
修改 DTO/VO/BO/Entity 字段类型、字段名、枚举值时，必须全局搜索引用。
必须检查 set/get 调用、mapper 映射、Bean copy、JSON 序列化、接口文档、单元测试、SQL resultMap 和对外接口兼容性。
不允许只修改字段定义，不修改使用方。
```

### 坑七：AI 生成的代码缺少生产环境意识

AI 生成代码往往更关注“功能是否能跑”，但生产环境还要关注：

```text
数据量
并发量
事务范围
慢 SQL
索引
连接池
超时
重试
幂等
日志
链路追踪
异常可读性
```

这次事故就是典型例子：SQL 逻辑没错，但生产数据量一大就慢。SQL 一慢，又撞上过短的 `socketTimeout`。连接一断，事务回滚再抛异常。最后日志里看到的是 `Connection is closed`，不是最原始的慢 SQL。

建议上线前增加 AI 代码准入清单：

```text
1. 是否新增或修改生产配置？
2. 是否新增数据库连接参数？
3. 是否新增或修改 SQL？
4. SQL 是否结合 DDL 和索引 explain？
5. 是否存在大表查询？
6. 是否在事务内执行慢操作？
7. 是否有远程调用放在事务内？
8. 是否有必要的日志和 traceId？
9. 异常是否保留 root cause？
10. 是否通过接近生产数据量的验证？
```

## 可以沉淀一份 AI 编码约束

建议团队维护一份 `AI-CODING-GUIDE.md`，每次让 AI 生成或修改代码前，都把这份规范作为上下文输入。

示例：

```markdown
# AI 编码约束

## 修改范围
- 只修改用户要求的范围。
- 修改字段、类型、枚举、接口返回值时，必须全局搜索引用并同步调整。
- 不允许只改定义不改使用方。

## 配置规则
- 禁止自行新增数据库 URL 参数、连接池参数、事务超时参数。
- 所有配置差异必须列出并说明原因。
- 生产配置变更必须经过人工确认。

## SQL 规则
- 新增或修改 SQL 必须输出 SQL 清单。
- 大表查询必须 explain。
- 禁止在未确认索引的字段上做高频查询。
- 事务内 SQL 必须关注执行耗时。

## 抽象规则
- 简单逻辑不要为了测试单独抽方法。
- 只有明确业务语义、多处复用、或能显著降低复杂度时才抽方法。
- 不新增无实际复用价值的工具类。

## 注释规则
- 简单代码不写废话注释。
- 复杂业务规则、历史兼容、特殊边界必须说明原因。
- 注释解释为什么，不重复代码做什么。

## 工具类规则
- 优先使用项目已有工具类。
- 新增工具方法前必须搜索已有实现。
- 日期、金额、字符串、集合、JSON、异常处理遵守项目既有规范。

## 验证规则
- 修改后必须说明验证方式。
- Java 项目至少执行编译或相关测试。
- 涉及 SQL、配置、事务的修改必须说明生产风险。
```

## 给 AI 的推荐提示词

以后不要简单说：

```text
参考 A 项目初始化 B 项目。
```

这句话太危险，AI 会自由发挥。

可以改成：

```text
请参考 A 项目初始化 B 项目，但必须遵守以下约束：

1. 只参考项目结构、依赖组织、包命名和基础编码风格。
2. 不允许自行新增数据库 URL 参数、连接池参数、事务参数、线程池参数。
3. 所有配置差异必须输出 diff，并说明原因。
4. 新增或修改 SQL 必须输出 SQL 清单。
5. SQL 必须结合表结构和索引判断是否可能慢查询；如果缺少 DDL，请标记无法判断，不要猜。
6. 修改 DTO/VO/Entity 字段时，必须全局搜索所有引用并同步修改。
7. 简单逻辑不要为了单元测试抽私有方法。
8. 优先使用项目已有工具类，不要新增无必要工具类。
9. 修改完成后，说明改了哪些文件、为什么改、如何验证、还有哪些风险。
```

## 总结

AI 可以显著提高开发效率，但它不是一个天然可靠的高级工程师。它更像一个执行速度很快、但必须被规则约束的初级开发。

这次问题暴露出的核心风险是：

```text
1. AI 会擅自新增生产敏感配置。
2. AI 写的 SQL 可能逻辑正确，但没有结合索引和数据量。
3. 事务内慢 SQL 叠加过短 socketTimeout，会导致连接关闭和回滚异常。
4. 回滚异常可能掩盖真正的 SQL 超时根因。
5. AI 可能过度抽象、缺少有效注释、不遵守工具类规范。
6. AI 修改字段或接口时，容易漏掉关联修改点。
```

使用 AI 写代码，不能只验收“功能能不能跑”，还要验收：

```text
配置是否可控
SQL 是否可解释
索引是否命中
事务是否安全
日志是否能定位根因
代码是否符合团队规范
修改是否覆盖完整影响面
```

一句话概括：

**AI 生成代码不是终点，AI 生成代码后的审查机制才是生产质量的起点。**
